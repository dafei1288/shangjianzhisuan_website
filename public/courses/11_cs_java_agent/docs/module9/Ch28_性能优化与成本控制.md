## 1. 为什么 Agent 项目这么贵

跑一个 RAG + Function Calling Agent，一次用户请求可能消耗：

| 资源 | Token | 耗时 |
|------|-------|------|
| Query Embedding | 50 tokens（input） | 50 ms |
| RAG 检索结果（5 chunks × 500 tokens）| 2500 tokens（context） | - |
| System Prompt + Tools 描述 | 1500 tokens | - |
| 对话历史（10 轮 × 300 tokens）| 3000 tokens | - |
| LLM 推理（含 CoT）| 800 tokens（output）| 2-5 s |
| **合计** | **~7850 tokens / 请求** | **3-8 s** |

按 GPT-4o 价格（input $2.5/M tokens，output $10/M tokens）算：
- 单次成本：7850 × $2.5/M + 800 × $10/M ≈ **$0.0275**
- 10000 DAU × 10 请求/天 = $2750 / 天 = **$82500 / 月**

**结论**：不优化根本跑不起。

## 2. 四层缓存策略

### 2.1 L1 - Embedding 缓存

```java
@Component
public class CachedEmbeddingModel {
    private final Cache<String, float[]> cache = Caffeine.newBuilder()
        .maximumSize(10_000)
        .expireAfterAccess(Duration.ofHours(24))
        .build();

    public float[] embed(String text) {
        String key = "emb:" + DigestUtils.md5Hex(text);
        return cache.get(key, k -> delegate.embed(text));
    }
}
```

**命中率**：用户问题中 ~30% 是「查 XX 是什么」这类高频问题，Embedding 命中率约 20-30%。

### 2.2 L2 - 检索结果缓存

```java
public List<Chunk> retrieveWithCache(String query) {
    String key = "rag:" + DigestUtils.md5Hex(query.toLowerCase().trim());
    return retrieveCache.get(key, k -> {
        var embedding = embed(query);
        return vectorStore.search(embedding, 5);
    });
}
```

**关键点**：query 归一化（去标点、小写、去空格）后再算 hash，提升命中。

### 2.3 L3 - LLM 响应缓存（最值钱）

```java
@Component
public class CachedChatClient {
    public String call(Prompt prompt) {
        String cacheKey = buildKey(prompt);  // system+user+context+tools hash
        return responseCache.get(cacheKey, k -> {
            recordCall("llm.cache.miss");
            return delegate.call(prompt);
        });
    }

    private String buildKey(Prompt prompt) {
        // 把 Tools 也纳入 key，避免不同 Tools 配置命中同一缓存
        return "llm:" + DigestUtils.md5Hex(
            prompt.getContents() + "|" + toolsSignature(prompt));
    }
}
```

**关键点**：
- **温度 = 0** 才能缓存；温度 > 0 的创意生成不可缓存
- **TTL 短**（1 小时）：业务数据变化会让旧答案失效
- **主动失效**：知识库更新时 `cache.invalidateByPrefix("llm:")`

### 2.4 L4 - 工具结果缓存

```java
@Tool(description = "查询当前股价")
public String getStockPrice(@P("股票代码") String code) {
    return toolCache.get("stock:" + code, k -> {
        recordCall("tool.stock.api");
        return stockApi.fetch(k);  // 第三方 API 限速很贵
    }, Duration.ofSeconds(10));  // 股价 10s 内复用
}
```

**关键点**：工具调用是最贵的（外部 API 限速 / 计费），缓存收益最大。

### 2.5 缓存命中率统计

| 缓存层 | 典型命中率 | 节省 |
|--------|-----------|------|
| Embedding | 20-30% | Embedding 调用 |
| 检索结果 | 15-25% | 向量库查询 |
| LLM 响应 | 5-15% | LLM 调用 ⭐⭐⭐ |
| 工具结果 | 30-50% | 外部 API 调用 |

整体成本可降 **40-60%**。

## 3. 模型路由（Model Router）

### 3.1 核心思想

不是所有问题都需要 GPT-4 / DeepSeek-V3。把简单问题丢给小模型（GPT-4o-mini / DeepSeek-Turbo / Qwen-Turbo），成本能降一个数量级。

```
┌──────────────────────────────────────────────┐
│  用户 Query                                   │
└────────────┬─────────────────────────────────┘
             ↓
       [Router 分类器]
             ↓
   ┌─────────┼─────────┐
   ↓         ↓         ↓
 简单      中等      复杂
   ↓         ↓         ↓
Qwen-Turbo  DS-V3    GPT-4
$0.05/M    $0.5/M   $5/M
```

### 3.2 Router 实现

#### 方案 A：基于规则

```java
public String routeModel(String query) {
    // 1. 长度短 → 小模型
    if (query.length() < 30) return "qwen-turbo";

    // 2. 含特定关键词
    if (query.contains("翻译") || query.contains("总结")) {
        return "qwen-turbo";
    }

    // 3. 含代码 / 推理 / 多步 → 大模型
    if (query.contains("代码") || query.contains("分析")) {
        return "deepseek-v3";
    }

    return "deepseek-v3";  // 默认中等
}
```

**优点**：零成本、可解释。
**缺点**：覆盖不全。

#### 方案 B：基于 Embedding 分类

```java
// 离线构建：简单问题 / 复杂问题 各 100 条样例 → Embedding
public String routeModel(String query) {
    float[] qEmb = embed(query);
    double simpleSim = maxSimilarity(qEmb, simpleExamples);
    double complexSim = maxSimilarity(qEmb, complexExamples);

    if (simpleSim > 0.85 && simpleSim > complexSim) return "qwen-turbo";
    if (complexSim > 0.85) return "deepseek-v3";
    return "deepseek-v3";  // 默认中等
}
```

**优点**：自动学习用户问题分布。
**缺点**：要维护样例库。

#### 方案 C：小模型当 Router

```java
public String routeModel(String query) {
    String prompt = """
    判断下面用户问题的难度：
    - 简单（0）：翻译、总结、问候、查询
    - 中等（1）：单轮分析、解释
    - 复杂（2）：多步推理、代码生成、长文写作

    用户问题：%s
    难度（0/1/2）：
    """.formatted(query);

    String result = smallModel.call(prompt);  // 用最便宜的模型
    return switch (result.trim()) {
        case "0" -> "qwen-turbo";
        case "2" -> "deepseek-r1";
        default -> "deepseek-v3";
    };
}
```

**优点**：准确率最高（90%+）。
**缺点**：每次多花 ~10 tokens。

### 3.3 A/B Test 验证

## 4. Prompt 压缩

### 4.1 三种压缩方式

#### 方式 1：上下文裁剪（最有效）

```java
// ❌ 坏：把 10 轮历史全塞进去（3000 tokens）
List<Message> history = chatMemory.all();

// ✅ 好：只保留最近 3 轮 + 摘要
String summary = summarizeOldTurns(history.subList(0, history.size() - 6));
List<Message> recent = history.subList(history.size() - 6, history.size());
List<Message> compressed = List.of(
    user(summary),  // 摘要 100 tokens
    recent...        // 最近 3 轮 ~900 tokens
);
```

省 **60%+** Token。

#### 方式 2：检索相关历史（Memory RAG）

```java
// 不按时间，按相关性选历史
List<Message> relevant = chatMemory.all().stream()
    .map(m -> Map.entry(m, similarity(queryEmb, embed(m.text()))))
    .sorted((a, b) -> Double.compare(b.getValue(), a.getValue()))
    .limit(3)
    .map(Map.Entry::getKey)
    .toList();
```

适合长对话场景（客服会话、长程任务）。

#### 方式 3：用 LLMLingua

```java
// 用小模型给 Prompt 打分，删除低信息量的 token
String compressed = LLMLingua.compress(prompt, ratio = 0.5);
// "请帮我总结下面这篇文章的核心观点，用 100 字以内..."
// → "总结下文核心观点 100字以内..."
```

省 **30-50%** Token，质量损失通常 <5%。

### 4.2 实战案例

| 场景 | 原始 Token | 压缩后 | 节省 |
|------|-----------|--------|------|
| 10 轮对话历史 | 3000 | 1200（摘要+近 3 轮） | 60% |
| RAG Context（5 chunks） | 2500 | 1500（chunk 去重） | 40% |
| Tools 描述（10 个工具） | 800 | 500（按需注入） | 38% |
| System Prompt | 500 | 300（去冗余） | 40% |

## 5. 关键代码：完整的 Token 监控

### 5.1 Advisor 拦截统计

```java
public class TokenMetricAdvisor implements BaseAdvisor {

    @Override
    public AdvisedResponse aroundCall(AdvisedRequest req,
                                       CallAdvisorChain chain) {
        long start = System.currentTimeMillis();
        AdvisedResponse resp = chain.nextAroundCall(req);

        Usage usage = resp.response().getMetadata().getUsage();
        metrics.record("llm.token.input", usage.getPromptTokens());
        metrics.record("llm.token.output", usage.getCompletionTokens());
        metrics.record("llm.latency",
            System.currentTimeMillis() - start);
        metrics.record("llm.cost.estimate",
            calcCost(req.model(), usage));

        return resp;
    }

    private double calcCost(String model, Usage u) {
        Map<String, double[]> pricing = Map.of(
            "deepseek-v3", new double[]{0.0014, 0.0028},   // per 1K
            "deepseek-r1", new double[]{0.0055, 0.022},
            "gpt-4o", new double[]{0.0025, 0.01});
        double[] p = pricing.get(model);
        return u.getPromptTokens() * p[0] / 1000
             + u.getCompletionTokens() * p[1] / 1000;
    }
}
```

### 5.2 关键指标

| 指标 | 阈值 | 含义 |
|------|------|------|
| `llm.token.input.p99` | < 5000 | 单次输入 token |
| `llm.token.output.p99` | < 2000 | 单次输出 token |
| `llm.latency.p99` | < 8s | 单次推理延迟 |
| `llm.cache.hit_rate` | > 0.15 | LLM 响应缓存命中 |
| `llm.error_rate` | < 0.01 | 调用失败率 |
| `llm.cost.daily` | 看预算 | 日累计成本 |

| 优化项 | 难度 | 节省 | 何时做 |
|--------|------|------|--------|

## 常见问题 Q&A

**Q1：缓存和用户隐私冲突怎么办？**

A：用户敏感数据（手机号 / 身份证）在算 hash 前先脱敏。或者按用户 ID 隔离缓存（`cacheKey = "llm:" + userId + ":" + hash`），多用户场景命中略低但安全。

**Q2：模型路由用什么分类器最好？**

A：MVP 阶段用规则（关键词 + 长度），上线后积累了 ~10000 条标注数据再训 Embedding 分类。**别一上来就上 BERT 分类器**，运维成本不值。

**Q3：Prompt 压缩损失多少质量？**

A：摘要历史基本无损（人话都看摘要）；LLMLingua 类压缩在 RAG / Summarization 任务上 5% 损失；推理任务（数学 / 代码）建议别压，会丢关键步骤。

**Q4：DeepSeek 的 Batch API 半价，Agent 能用吗？**

A：**不能**。Batch 是异步的（几小时返回），Agent 需要实时响应。Batch 适合：日报生成、批量打标签、历史数据回填这类**离线任务**。

## 本章小结

- **缓存是第一优化**：LLM 响应缓存命中率 5-15% 就能省大钱，工具结果缓存命中率 30-50%
- **模型路由最有效**：把简单问题路由到小模型，整体成本能降 50%+
- **Prompt 压缩必做**：历史摘要 + 相关性检索，省 30-60% Token
- **可观测先于优化**：先有 Token / Latency / Cache 指标，再决定优化方向
