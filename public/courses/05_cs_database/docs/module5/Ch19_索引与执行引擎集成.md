# Ch19：索引与执行引擎集成

## 学习目标

- 理解 IndexScan 算子的实现原理

- 理解索引维护策略（INSERT/DELETE/UPDATE）
- 了解优化器如何选择 SeqScan vs IndexScan

---

## 1. 为什么需要 IndexScan

SeqScan 每次都要扫描全表，代价 O(N)。有了 B+ 树索引后：

- **等值查询** `WHERE id = 42`：O(log N) 定位到叶子节点
- **范围查询** `WHERE score BETWEEN 80 AND 95`：O(log N + K)，K 为结果行数

IndexScan 算子封装了"查索引 → 回表"的逻辑。

### 1.1 有索引不等于一定该走索引

这是很多初学者最容易形成的错误直觉：只要建了索引，查询就应该更快。

真实情况更复杂，因为 IndexScan 不是“免费跳过数据”，它通常包含两段成本：

1. 先在索引里定位或扫描
2. 再按 RecordId 回表取真实 Tuple

当命中行很多时，第二段随机回表的代价可能比顺序扫全表还糟。所以优化器真正比较的不是“有没有索引”，而是“索引链路总代价和全表扫描总代价谁更低”。

## 2. IndexScan 算子实现

```java
public class IndexScan implements Operator {
    private final HeapFile heap;
    private final BPlusTree index;
    private final Object lo, hi;
    private Iterator<RecordId> ridIter;

    @Override
    public void open() {
        List<RecordId> rids = index.rangeScan(lo, hi);
        ridIter = rids.iterator();
    }

    @Override
    public Tuple next() {
        if (!ridIter.hasNext()) return null;
        RecordId rid = ridIter.next();
        return heap.fetchTuple(rid);  // 回表
    }
}
```

## 3. 主键索引 vs 二级索引

### 主键索引（聚簇索引）

- 叶子节点直接存储完整 Tuple
- 数据按主键顺序物理存储
- 每张表只能有一个
- 主键查询无需回表

```
B+Tree(id) → Tuple(id=42, name="Alice", score=90)
```

### 二级索引（非聚簇索引）

- 叶子节点存储 RecordId（pageId, slotId）
- 需要回表获取完整数据（两次 I/O）
- 每张表可以有多个

```
B+Tree(score) → RecordId(3, 7) → 回表 → Tuple
```

### 覆盖索引（Covering Index）

若查询列全部在索引中，无需回表：

```sql
-- 索引 (score, name)，查询只需 score 和 name
SELECT name FROM students WHERE score > 80;
-- 直接从索引返回，不回表
```

### 3.1 覆盖索引为什么这么重要

覆盖索引的价值，不只是“少一次回表”，而是它把一次可能充满随机 I/O 的访问，压缩成了沿索引结构本身完成的查询。

这通常带来三层收益：

1. 少一次堆表访问
2. 少一次缓冲池命中/缺页判断
3. 更容易维持顺序访问模式

所以很多数据库性能优化，表面上是在“补一个索引”，本质上是在努力把查询变成覆盖索引查询。

## 4. 索引维护策略

每次写操作必须同步维护索引：

```java
// INSERT
void insert(Tuple t) {
    RecordId rid = heapFile.insertTuple(t);
    for (BPlusTree idx : indexes) {
        idx.insert(t.getKey(idx.keyCol), rid);
    }
}

// DELETE
void delete(RecordId rid) {
    Tuple t = heapFile.fetchTuple(rid);
    for (BPlusTree idx : indexes) {
        idx.delete(t.getKey(idx.keyCol), rid);
    }
    heapFile.deleteTuple(rid);
}
```

索引越多，写入代价越高——这是索引数量的权衡点。

### 4.1 索引集成真正引入的是“写放大”

到这一章，索引不再只是一个独立数据结构，而是数据库写路径的一部分。

这意味着每次 INSERT/DELETE/UPDATE 都不只是改主数据，还可能要：

1. 更新一个或多个索引页
2. 触发页分裂或合并
3. 记录额外的 WAL 日志
4. 增加锁竞争范围

所以索引集成的代价，绝不只是多占磁盘，而是把读优化收益换成了写路径复杂度和写放大。

## 5. 优化器的选择

优化器根据**选择率**（selectivity）决定是否使用索引：

```
选择率 = 满足条件的行数 / 总行数

若选择率 < 阈值（如 10%）：使用 IndexScan
若选择率 ≥ 阈值：使用 SeqScan（回表代价超过全表扫描）
```

## 5.1 优化器真正关心的是“选择率之后还剩多少随机访问”

为什么很多数据库在选择率高时宁可全表扫描？因为索引扫描的瓶颈常常不在树高，而在回表。

举个直觉化的判断：

1. 如果只命中几行，`O(log N)` 找到它们很划算
2. 如果命中 30%、50%、70% 的行，回表几乎会把整张表随机读一遍
3. 这时顺序扫描反而更符合磁盘和缓冲池的物理特性

所以“选择率阈值”本质上是在估算：为了这些命中结果，我到底要付出多少随机 I/O。

## 7. 小结

索引是存储层与执行引擎的桥梁：

- IndexScan 算子：查索引 → 得 RecordId → 回表
- 主键索引无需回表，二级索引需要
- 写操作必须维护所有相关索引
- 优化器根据选择率选择扫描方式

## 常见问题 Q&A

**Q1: 什么时候不该建索引？**
A: 小表（内存装得下，全表扫描很快）。频繁更新的列（索引维护成本 > 查询收益）。区分度低的列（如性别，索引选择性差）。

**Q2: 为什么索引不是自动创建的？**
A: 索引加速查询但减慢写入。数据库不替你做这个权衡。需要根据查询模式手动选择。

**Q3: 索引如何影响查询优化器？**
A: 优化器会估算全表扫描代价 vs 索引扫描代价，选成本低的。索引统计信息（行数、页数、区分度）是优化的基础。
