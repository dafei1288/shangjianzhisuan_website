## 1. 删除的三种情况

删除一个键后，若节点键数 ≥ ⌈(m-1)/2⌉，直接删除即可。否则需要修复：

### 情况 1：直接删除（无下溢）

节点删除后仍满足最少键数要求，直接删除，更新父节点分隔键。

### 情况 2：借键（Redistribute）

兄弟节点有多余的键（键数 > ⌈(m-1)/2⌉），从兄弟借一个键：

**从右兄弟借**：
```
1. 将右兄弟最小键移到当前节点末尾
2. 更新父节点中分隔该两节点的键为右兄弟新的最小键
```

**从左兄弟借**：
```
1. 将左兄弟最大键移到当前节点开头
2. 更新父节点中分隔该两节点的键为当前节点新的最小键
```

### 情况 3：合并（Merge）

兄弟节点也只有最少键数，无法借键，需要合并：

```
1. 将当前节点所有键合并到左（或右）兄弟
2. 删除父节点中对应的分隔键
3. 若父节点也下溢，递归向上处理
```

### 1.1 为什么删除总比插入更让人头疼

插入时，B+ 树主要面对的是“太满了怎么办”；删除时，面对的却是“删掉之后还能不能保持所有不变式”。

这让删除天然比插入更复杂，因为它往往同时影响三层关系：

1. 当前节点自己的键数是否合法
2. 兄弟节点能不能支援
3. 父节点的分隔键是否还正确

所以删除不是简单地“把键拿掉”，而是在删除之后继续做一轮结构修复。

## 2. 叶子节点 vs 内部节点的删除差异

| | 叶子节点 | 内部节点 |
|--|---------|---------|
| 存储内容 | 实际数据（或 RecordId）| 分隔键 + 子节点指针 |
| 合并后 | 更新叶子链表指针 | 下拉父节点分隔键 |
| 借键后 | 更新父节点分隔键 | 旋转父节点分隔键 |

### 2.1 父节点分隔键为什么总要跟着变

学生写删除逻辑时最容易漏掉的一件事，就是：即使当前叶子页里的数据已经改对了，父节点里的分隔键也可能已经失真。

原因很简单，B+ 树父节点存的不是“随便某个键”，而是子树边界信息。只要子节点最小键变化了，父节点就必须同步更新，否则：

1. 查找路径可能走错分支
2. 范围查询可能漏页或多扫页
3. 后续插入/删除会在错误边界上继续累积问题

所以删除修复的难点，很多时候不在当前页，而在“边界信息是否仍然真实”。

## 3. 叶子链表

B+ 树叶子节点通过双向链表连接，支持高效范围查询：

```
叶子链表: [1,3] ↔ [5,7] ↔ [9,11] ↔ [13,15]
```

**范围查询** `WHERE id BETWEEN 5 AND 12`：
1. 从根节点查找 key=5 所在叶子
2. 沿链表向右扫描，直到 key > 12

合并时需要更新链表指针：
```java
// 合并 right 到 left
left.next = right.next;
if (right.next != null) right.next.prev = left;
```

### 3.1 叶子链表让 B+ 树不只是“能查到”，而是“能顺着扫”

如果只有树结构没有叶子链表，B+ 树当然也能做范围查询，但每跨一个叶子页都得重新回到父节点甚至根节点找下一段范围，代价会很差。

叶子链表的价值就在于：一旦定位到范围起点，后面就可以像扫有序文件一样顺着叶子页连续往右读。

这也是为什么数据库最终偏爱 B+ 树而不是普通平衡二叉树。它关心的不只是单点查找，更关心范围扫描、顺序访问和页级 I/O 友好性。

## 4. 删除算法伪代码

```
delete(node, key):
    if node is leaf:
        remove key from node
        if node.size < minKeys:
            fixUnderflow(node)
    else:
        child = findChild(node, key)
        delete(child, key)
        update separator key in node if needed
        if child.size < minKeys:
            fixUnderflow(child)

fixUnderflow(node):
    sibling = rightSibling(node) or leftSibling(node)
    if sibling.size > minKeys:
        redistribute(node, sibling)
    else:
        merge(node, sibling)
        if parent.size < minKeys and parent != root:
            fixUnderflow(parent)
        if root.size == 0:
            root = root.children[0]  // 树高减 1
```

## 5. 树高变化

- **插入**：分裂可能使树高 +1（根节点分裂）
- **删除**：合并可能使树高 -1（根节点只剩一个子节点）

树高变化是 B+ 树自平衡的核心机制。

## 7. 小结

B+ 树删除的核心是维护**最少键数不变式**：

```
叶子节点：键数 ≥ ⌈(m-1)/2⌉
内部节点：键数 ≥ ⌈m/2⌉ - 1
```

违反时优先借键（代价小），无法借键时合并（可能向上传播）。叶子链表是 B+ 树支持范围查询的关键结构。下一章将 B+ 树与执行引擎集成。

## 常见问题 Q&A

**Q1: 为什么删除比插入复杂？**
A: 插入只需分裂（向上传播）。删除可能导致合并或借用，需要处理更多边界情况（根节点特殊处理、欠满但不合并等）。

**Q2: B+ 树的最小填充率是多少？**
A: 除根外，每个节点至少半满（ceil(m/2) 个键）。这是 B+ 树平衡的保证。实际数据库通常允许欠满到 1/3 以减少频繁合并。

**Q3: 页分裂对性能影响有多大？**
A: 页分裂需要写两页（分裂后的两个新页）+ 更新父页，一次分裂至少 3 次 I/O。批量插入时用 bulk loading 可以完全避免分裂。

## 删除过程追踪示例

下面用一个小例子串起 B+ 树删除后的借位与合并过程。假设叶子节点最多容纳 4 个 key，最少需要 2 个 key：

```text
删除前：
Root: [30]
Left leaf : [10, 20]
Right leaf: [30, 40, 50]
```

现在删除 `20`：

```text
Step 1: 在叶子节点中删除 key
Left leaf: [10]

Step 2: 检查下溢
Left leaf 只有 1 个 key，低于最小数量 2，触发再平衡。

Step 3: 优先向兄弟节点借位
Right leaf 有 3 个 key，可以借出最小 key=30。
Left leaf : [10, 30]
Right leaf: [40, 50]

Step 4: 更新父节点分隔 key
父节点原来用 30 作为右叶子的最小 key，现在右叶子最小 key 变成 40。
Root: [40]
```

如果右兄弟也只有最小数量，就不能借位，需要合并：

```text
Left leaf : [10]
Right leaf: [40]
合并后：
Merged leaf: [10, 40]
父节点删除对应分隔 key，必要时继续向上处理下溢。
```

这个过程的关键不是“删除一个 key”，而是删除后仍要维持三个约束：所有叶子在同一层、节点 key 数量在合法范围内、父节点分隔 key 与子节点最小 key 保持一致。
