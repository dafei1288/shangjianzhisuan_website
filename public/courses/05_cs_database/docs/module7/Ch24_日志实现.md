## 1. LogRecord 格式设计

### 1.1 为什么需要固定格式

日志是数据库最关键的数据——没有日志，崩溃后无法恢复。日志格式必须：
- **紧凑**：写入速度直接影响事务延迟
- **自描述**：恢复时没有元数据，日志本身必须包含所有信息
- **有序**：LSN 保证日志的全局顺序

### 1.2 日志记录格式

```
┌──────┬──────┬──────┬──────┬──────────┬──────────────────────────┐
│ LSN  │TxnId │ Type │PageId│ Offset   │ Data                     │
│ 8B   │ 8B   │ 1B   │ 4B   │ 4B       │ variable                 │
└──────┴──────┴──────┴──────┴──────────┴──────────────────────────┘

对于 UPDATE 类型，Data 部分进一步展开：
┌──────────────┬──────────────┬──────────┬──────────┐
│ beforeLen    │ beforeImage  │ afterLen │ afterImage│
│ 4B           │ variable     │ 4B       │ variable │
└──────────────┴──────────────┴──────────┴──────────┘
```

### 1.3 代码实现

```java
public class LogRecord {
    public long lsn;           // Log Sequence Number
    public long txnId;         // 事务 ID
    public LogType type;       // 日志类型
    public int pageId;         // 修改的页 ID
    public int offset;         // 页内偏移
    public byte[] beforeImage; // 修改前的值（用于 Undo）
    public byte[] afterImage;  // 修改后的值（用于 Redo）

    enum LogType {
        BEGIN(0), UPDATE(1), COMMIT(2), ABORT(3), CHECKPOINT(4);

        public final int code;
        LogType(int code) { this.code = code; }
    }

    // 序列化为字节数组
    public byte[] serialize() {
        ByteArrayOutputStream baos = new ByteArrayOutputStream();
        DataOutputStream dos = new DataOutputStream(baos);
        dos.writeLong(lsn);
        dos.writeLong(txnId);
        dos.writeByte(type.code);
        if (type == LogType.UPDATE) {
            dos.writeInt(pageId);
            dos.writeInt(offset);
            dos.writeInt(beforeImage.length);
            dos.write(beforeImage);
            dos.writeInt(afterImage.length);
            dos.write(afterImage);
        }
        return baos.toByteArray();
    }

    // 从字节数组反序列化
    public static LogRecord deserialize(byte[] data) { ... }
}
```

## 2. LSN 与页面关系

### 2.1 LSN 的全局递增

```
日志文件（顺序追加）：
  LSN=1: BEGIN txn=101
  LSN=2: UPDATE txn=101 page=5 offset=12 before="Alice" after="Bob"
  LSN=3: UPDATE txn=102 page=3 offset=8  before=100 after=80
  LSN=4: COMMIT txn=101
  LSN=5: UPDATE txn=102 page=7 offset=20 before="X" after="Y"
  LSN=6: COMMIT txn=102
  ...
```

### 2.2 pageLSN 机制

每个数据页头部记录 `pageLSN`——最后一次修改该页的日志 LSN：

```
数据页头: [pageId=5][pageLSN=2][...]
数据页头: [pageId=3][pageLSN=3][...]
```

**恢复时判断是否需要 Redo**：

```
if log.LSN > page.pageLSN:
    需要 Redo（该修改还未反映在磁盘页上）
else:
    跳过（修改已在磁盘页上，Redo 幂等）

为什么重要？
  - 避免重复执行已落盘的修改
  - Redo 是幂等的：执行多次和一次效果相同
```

## 3. 日志写入流程

### 3.1 WAL 原则在实现中的体现

```
WAL（Write-Ahead Logging）：
  数据页写入磁盘前，对应的日志必须先写入磁盘

实现流程：
  1. 修改内存中的数据页（pageLSN 更新为新 LSN）
  2. 将日志记录追加到日志缓冲区
  3. 事务提交时，flush 日志缓冲到磁盘（fsync）
  4. 数据页可以稍后异步刷盘（不急）

关键：步骤 3 必须在步骤 4 之前
  → 保证崩溃后，所有已提交事务的修改都能通过日志恢复
```

### 3.2 LogManager 实现

```java
public class LogManager {
    private long nextLSN = 1;
    private final RandomAccessFile logFile;
    private final List<LogRecord> buffer = new ArrayList<>();

    // 追加日志记录（只写入内存缓冲）
    public synchronized long append(LogRecord record) {
        record.lsn = nextLSN++;
        buffer.add(record);
        return record.lsn;
    }

    // 将日志刷到磁盘（fsync 确保持久化）
    public synchronized void flush(long upToLSN) throws IOException {
        for (LogRecord r : buffer) {
            if (r.lsn <= upToLSN) {
                byte[] data = r.serialize();
                // 写入长度前缀 + 数据
                logFile.writeInt(data.length);
                logFile.write(data);
            }
        }
        // 移除已刷盘的记录
        buffer.removeIf(r -> r.lsn <= upToLSN);
        // fsync！这是事务持久性的保证
        logFile.getFD().sync();
    }

    // 读取所有日志（用于恢复）
    public List<LogRecord> readAll() throws IOException { ... }
}
```

### 3.3 事务提交流程

```java
public void commit(long txnId) {
    // 1. 写入 COMMIT 日志
    long commitLSN = logMgr.append(
        new LogRecord(txnId, LogType.COMMIT)
    );
    // 2. 强制刷盘（WAL 保证）
    logMgr.flush(commitLSN);
    // 3. 释放锁
    lockMgr.releaseAll(txnId);
    // 注意：数据页不需要此时刷盘，可以异步进行
}
```

## 4. Checkpoint 机制

### 4.1 为什么需要 Checkpoint

```
没有 Checkpoint：
  崩溃恢复需要从日志开头重放到末尾
  如果日志有 100GB → 恢复需要几小时

有 Checkpoint：
  只需从最后一个 Checkpoint 开始重放
  如果每 5 分钟做一次 Checkpoint → 最多重放 5 分钟的日志
```

### 4.2 Sharp Checkpoint（简单）

```
1. 停止接受新事务
2. 等待所有活跃事务完成
3. 将所有脏页刷盘（force all dirty pages）
4. 写入 CHECKPOINT 日志记录
5. 恢复接受新事务

优点：实现简单
缺点：停顿时间长（脏页可能很多）

适用：小型数据库、维护窗口期
```

### 4.3 Fuzzy Checkpoint（ARIES 使用）

```
不停事务，记录状态快照：

1. 写入 CHECKPOINT-BEGIN（记录当前活跃事务列表）
2. 记录脏页表（Dirty Page Table）——哪些页被修改过
3. 后台异步将脏页刷盘
4. 所有脏页刷完后写入 CHECKPOINT-END

恢复时：
  从最后一个完成的 CHECKPOINT-BEGIN 开始
  使用脏页表加速 Redo（只 Redo 脏页）
  使用活跃事务列表确定需要 Undo 的事务

优点：不停服务
缺点：实现复杂
```

### 4.4 Checkpoint 日志格式

```java
public class CheckpointLogRecord extends LogRecord {
    Set<Long> activeTxns;      // 活跃事务列表
    Map<Integer, Long> dirtyPages; // 脏页表: pageId → recLSN

    // recLSN = 第一次导致该页变脏的日志 LSN
    // Redo 时只从 recLSN 开始处理该页
}
```

## 5. 日志写入性能分析

### 5.1 为什么日志是顺序 I/O

```
随机 I/O（数据页写入）：需要 seek 到指定位置 → 8-10ms
顺序 I/O（日志追加）：直接追加到文件末尾 → 0.1ms

差距 100 倍！这就是 WAL 的核心优势：
  事务提交只需等日志 fsync（顺序），不等数据页刷盘（随机）
```

### 5.2 组提交（Group Commit）

```
优化：多个事务同时提交时，只 fsync 一次

T1: COMMIT → flush(LSN=100)
T2: COMMIT → flush(LSN=101)  ← 和 T1 合并成一次 fsync
T3: COMMIT → flush(LSN=102)  ← 也合并

一次 fsync 提交 3 个事务 → 吞吐量提升 3 倍
```

## 小结

| 要点 | 说明 |
|------|------|
| LogRecord | 固定头部 + 变长 Data（含 before/after image）|
| LSN | 全局递增，用于标识日志和判断 Redo |
| pageLSN | 页面最后修改的 LSN，Redo 时跳过已应用的修改 |
| flush + fsync | 提交时必须调用，保证持久性 |
| Checkpoint | 缩短恢复范围：Sharp（停顿）/ Fuzzy（不停顿）|

## 常见问题 Q&A

**Q1: 日志为什么要先写入磁盘，数据页反而可以晚点写？**
A: 这是 WAL 的核心思想：只要日志已经持久化，系统崩溃后就能根据日志重放或回滚数据页变化。数据页可以延迟刷盘以提升性能，但日志必须先保证恢复依据存在。

**Q2: redo log 和 undo log 的区别是什么？**
A: redo log 用来重做已经提交但可能尚未写入数据页的修改；undo log 用来撤销未提交事务造成的影响。一个面向“把该做的补上”，一个面向“把不该留下的撤回”。

**Q3: 为什么日志记录里要包含 LSN？**
A: LSN 是日志顺序的全局坐标。恢复时数据库需要知道哪些日志已经应用到数据页、哪些还没应用；并发写入时也要靠 LSN 判断顺序和幂等性。没有 LSN，恢复过程很难可靠排序。
