## 1. 崩溃场景：数据为什么会丢失

### 1.1 内存与磁盘的"鸿沟"

数据库运行时，数据始终在**内存（BufferPool）**和**磁盘（Disk）**之间流动。理解这个流动是理解 WAL 的关键：

```
                        ┌──────────────┐
    写操作 ─────────────→│  BufferPool  │ ← 内存中的数据页
                        │  (内存，快)   │
                        └──────┬───────┘
                               │
                          某个时刻刷盘
                               │
                               ▼
                        ┌──────────────┐
                        │    磁盘文件   │ ← 持久化的数据页
                        │  (磁盘，慢)   │
                        └──────────────┘
```

**核心矛盾**：内存快但不持久，磁盘持久但慢。数据库为了性能，总是先改内存，延迟写磁盘。

### 1.2 崩溃导致数据丢失的三种场景

**场景 1：已提交但未刷盘**
```
时间线：
  T1: 事务开始
  T2: 修改 BufferPool 中的 Page_A ← 内存已改
  T3: 事务提交，返回"成功"给客户端 ← 客户端认为数据已持久化
  T4: 💥 崩溃！
  T5: 重启后 Page_A 在磁盘上还是旧值 ← 已提交的数据丢失！
```
这违反了 **Durability（持久性）**。

**场景 2：未提交但已刷盘**
```
时间线：
  T1: 事务开始
  T2: 修改 BufferPool 中的 Page_B ← 内存已改
  T3: BufferPool 满了，Page_B 被提前刷到磁盘 ← 磁盘也有了
  T4: 💥 崩溃！（事务未提交）
  T5: 重启后磁盘上 Page_B 是未提交的脏数据 ← 脏数据持久化了！
```
这违反了 **Atomicity（原子性）**。

**场景 3：部分写入（Torn Write）**
```
时间线：
  T1: 正在将 Page_C 写入磁盘（一个页 4KB）
  T2: 写到 2KB 时 💥 断电！
  T3: 磁盘上 Page_C 前半部分是新数据，后半部分是旧数据 ← 页面损坏！
```

### 1.3 JimSQL 的简单方案及其问题

在 Ch20-Ch22 中我们实现了事务和 MVCC，但没有处理崩溃恢复：

```java
// 无 WAL 的事务提交（不安全）
public void commit(Transaction tx) {
    tx.setStatus(Status.COMMITTED);
    // 如果在这里崩溃，内存中的修改全部丢失
    // 但客户端已经收到"提交成功"
    bufferPool.flushAll();  // 延迟刷盘，崩溃后数据丢失
}
```

**问题**：`commit` 返回成功和 `flushAll` 实际完成之间有一个"脆弱窗口"。

## 2. WAL 原则：先记后做

### 2.1 核心思想

**Write-Ahead Logging（WAL）**：在修改数据页之前，必须先将修改意图（日志记录）写入持久化的日志文件。

```
无 WAL 的写流程：
  修改内存页 → 提交 → 延迟刷盘
  ⚠ 提交和刷盘之间崩溃 = 数据丢失

有 WAL 的写流程：
  写日志到 WAL 文件（顺序写，快） → 修改内存页 → 提交（日志已 fsync） → 延迟刷盘
  ✅ 崩溃后可以重放日志恢复数据
```

### 2.2 WAL 保证什么

| 保证 | 说明 |
|------|------|
| 已提交不丢 | 事务提交时日志已落盘，崩溃后可重放恢复 |
| 未提交可回 | 如果未提交事务的修改已刷盘，可通过日志回滚 |
| 写入原子性 | 日志记录是原子的（带 CRC 校验），不存在半写问题 |

### 2.3 WAL 日志记录的格式

每条日志记录包含恢复所需的全部信息：

```
┌─────────────────────────────────────────────┐
│ WAL Record                                   │
├──────┬──────┬───────┬────────┬──────┬───────┤
│ LSN  │ TxID │ Type  │ PageID │ Off  │ Data  │
│ 4B   │ 4B   │ 1B    │ 4B     │ 2B   │ Var   │
├──────┴──────┴───────┴────────┴──────┴───────┤
│ LSN: 日志序列号（Log Sequence Number）        │
│ TxID: 事务 ID                                │
│ Type: BEGIN / UPDATE / COMMIT / ABORT        │
│ PageID: 修改的页号                            │
│ Offset: 页内偏移                              │
│ Before: 修改前的值（用于 Undo）               │
│ After: 修改后的值（用于 Redo）                │
└─────────────────────────────────────────────┘
```

## 3. 顺序写 vs 随机写：WAL 为什么快

### 3.1 磁盘 I/O 的本质差异

WAL 之所以高效，关键在于日志是**顺序追加（Append-Only）**：

| 操作 | I/O 模式 | 寻道时间 | 典型速度 |
|------|----------|----------|----------|
| 写 WAL 日志 | 顺序追加 | 无需寻道 | ~100-500 MB/s |
| 写数据页 | 随机写 | 每次寻道 ~5ms | ~100 IOPS (HDD) |
| SSD 随机写 | 随机写 | 无机械寻道 | ~50K IOPS |
| SSD 顺序写 | 顺序写 | 无需寻道 | ~2 GB/s |

**关键洞察**：即使 SSD 也存在顺序写优于随机写的特性（减少写放大、利于垃圾回收）。

### 3.2 为什么不能直接刷数据页

```
事务 T1 修改了 100 个分散在不同页的数据项：

方案 A（直接刷盘）：
  - 需要随机写 100 个页 = 100 次随机 I/O
  - 每次约 5ms（HDD）= 500ms

方案 B（WAL）：
  - 顺序追加 100 条日志记录 ≈ 1 次顺序 I/O
  - 约 0.1ms（合并后顺序写）
  - 快 5000 倍！
```

## 4. Redo 与 Undo：崩溃恢复的两大武器

### 4.1 Redo（重做）—— 恢复已提交的修改

**场景**：事务已提交，但修改的数据页还没刷盘就崩溃了。

```
崩溃前：
  WAL: [T1 BEGIN] [T1 UPDATE Page3 Offset=20 Before=50 After=100] [T1 COMMIT]
  磁盘: Page3 的 Offset=20 仍然是旧值 50

崩溃恢复：
  1. 扫描 WAL，找到已提交的事务 T1
  2. 重做 T1 的修改：将 Page3 Offset=20 改为 100
  3. 数据恢复！
```

### 4.2 Undo（撤销）—— 回滚未提交的修改

**场景**：事务未提交，但修改的页已被 BufferPool 刷到磁盘（Steal 策略允许这种情况）。

```
崩溃前：
  WAL: [T2 BEGIN] [T2 UPDATE Page5 Offset=8 Before=200 After=300]
  磁盘: Page5 的 Offset=8 已经是 300（被提前刷盘）
  T2 没有 COMMIT 记录

崩溃恢复：
  1. 扫描 WAL，发现 T2 没有 COMMIT → 未提交事务
  2. 撤销 T2 的修改：将 Page5 Offset=8 恢复为 200
  3. 脏数据被清理！
```

### 4.3 完整恢复流程

```
崩溃后重启
    │
    ▼
阶段 1: 分析（Analysis）
  - 扫描 WAL，找出所有事务的状态
  - 标记：已提交 / 未提交 / 进行中
    │
    ▼
阶段 2: Redo（重做）
  - 从最早的脏页开始，重放所有已提交事务的日志
  - 恢复到崩溃前的内存状态
    │
    ▼
阶段 3: Undo（撤销）
  - 回滚所有未提交事务的修改
  - 确保只有已提交的修改被保留
    │
    ▼
  数据库恢复到一致状态
```

## 5. 缓冲池策略：Force/Steal 组合

### 5.1 两个维度的选择

**Force vs No-Force**（提交时是否强制刷盘）：

| 策略 | 提交时行为 | 需要 Redo | 性能 |
|------|-----------|-----------|------|
| Force | 所有脏页必须刷盘 | 不需要 | 差（随机 I/O） |
| No-Force | 只需日志落盘 | 需要 | 好（延迟刷盘） |

**Steal vs No-Steal**（是否允许提前刷未提交的脏页）：

| 策略 | 未提交脏页 | 需要 Undo | 内存利用率 |
|------|-----------|-----------|-----------|
| Steal | 可以提前刷盘 | 需要 | 高（灵活淘汰） |
| No-Steal | 不能刷盘 | 不需要 | 低（内存受限） |

### 5.2 四种组合对比

| 组合 | Redo | Undo | 复杂度 | 使用者 |
|------|------|------|--------|--------|
| No-Force + Steal | ✅ 需要 | ✅ 需要 | 最高 | **InnoDB、PostgreSQL**（主流） |
| No-Force + No-Steal | ✅ 需要 | ❌ 不需要 | 中等 | 某些嵌入式数据库 |
| Force + Steal | ❌ 不需要 | ✅ 需要 | 中等 | 很少使用 |
| Force + No-Steal | ❌ 不需要 | ❌ 不需要 | 最低 | 早期简单数据库 |

**为什么主流选择 No-Force + Steal？**

性能最好但最复杂。Force 模式每次提交都要随机写脏页，性能无法接受。No-Steal 模式限制 BufferPool 灵活性，内存压力大。现代数据库宁愿用 Redo + Undo 的复杂性换取性能。

## 常见问题 Q&A

**Q1：WAL 日志会不会无限增长？**

A：不会。数据库通过 **检查点（Checkpoint）** 机制截断旧日志。检查点时，将所有脏页刷盘并记录检查点位置，之前的日志就可以安全删除。Ch25 会详细讲。

**Q2：WAL 的 fsync 会不会成为性能瓶颈？**

A：是潜在瓶颈。每次提交都 fsync 一次日志，I/O 延迟约 1-5ms。优化手段包括：
- **组提交（Group Commit）**：攒一批事务一起 fsync
- **异步刷盘**：降低持久性保证换取性能
- **使用电池保护的写缓存（BBWC）**：硬件级加速

**Q3：NoSQL 数据库也用 WAL 吗？**

A：大多数是。MongoDB 使用 oplog（操作日志），Cassandra 使用 commitlog，Redis 使用 AOF（Append Only File），本质都是 WAL 思想。区别在于日志格式和恢复策略可能更简单。

**Q4：WAL 和 Binlog 有什么区别？**

A：
- **WAL（Redo Log）**：物理日志，记录"哪个页哪个偏移改了什么"，用于崩溃恢复
- **Binlog**：逻辑日志，记录"执行了什么 SQL"，用于主从复制
- MySQL InnoDB 同时维护两者，各有用途

## 小结

| 要点 | 说明 |
|------|------|
| 核心问题 | 崩溃导致已提交数据丢失 / 未提交数据残留 |
| WAL 原则 | 先写日志（顺序写，快），再写数据（延迟刷盘） |
| Redo | 重做已提交事务的修改（解决 No-Force） |
| Undo | 撤销未提交事务的修改（解决 Steal） |
| 主流策略 | No-Force + Steal（性能最好，需 Redo + Undo） |
| 性能优势 | 顺序写日志比随机写数据快 1-2 个数量级 |
