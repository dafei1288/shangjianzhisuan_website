---

## 1. 连接的语义

```sql
SELECT s.name, sc.subject, sc.grade
FROM students s JOIN scores sc ON s.id = sc.student_id
WHERE sc.grade > 80;
```

连接将两张表的行按条件配对，是关系数据库最核心的操作，也是性能优化的重点。

### 1.1 为什么 Join 经常决定一条 SQL 的生死

单表查询通常还能靠索引、过滤条件和缓冲池撑住；但一旦进入 Join，系统需要面对的就不再是“如何读一张表”，而是“如何避免中间结果爆炸”。

Join 之所以关键，是因为它会同时放大三个成本：

1. 扫描成本：左右两侧都要读
2. 匹配成本：要判断哪些行能连上
3. 中间结果成本：一旦匹配很多，输出会迅速膨胀

所以数据库优化器大量工作都围绕 Join 展开，并不是因为 Join 概念难，而是因为它最容易把一个本来可接受的查询变成灾难性执行计划。

## 2. 嵌套循环连接（Nested Loop Join）

**最简单的实现**，适用于任意连接条件：

```
for each tuple r in left (outer):
    for each tuple s in right (inner):
        if r.key == s.key:
            emit(r ⊕ s)
```

**复杂度**：O(|R| × |S|）

**优化**：Block NLJ——外层按块读取，减少内层重复扫描次数：
```
for each block B of left:
    for each tuple s in right:
        for each tuple r in B:
            if r.key == s.key: emit(r ⊕ s)
```

### 2.1 为什么数据库还保留 NLJ

看完复杂度后，很多同学会觉得：既然 NLJ 是 `O(|R| × |S|)`，是不是可以完全淘汰？

不能。NLJ 仍然保留在数据库里，主要因为它有三点现实价值：

1. 适用于任意连接条件，不局限于等值连接
2. 实现最简单，边界条件最少
3. 当一侧结果极小，或者另一侧能走索引时，实际效果并不差

所以 NLJ 更像数据库里的“通用兜底方案”，不是最快，但覆盖面最大。

## 3. 哈希连接（Hash Join）

**两阶段**：Build（构建哈希表）+ Probe（探测）

```
// Build phase: 对较小的表（right）建哈希表
HashMap<Key, List<Tuple>> hashTable
for each tuple s in right:
    hashTable[s.key].add(s)

// Probe phase: 扫描左表，探测哈希表
for each tuple r in left:
    matches = hashTable.get(r.key)
    for each s in matches:
        emit(r ⊕ s)
```

**复杂度**：O(|R| + |S|）

**关键**：选择较小的表作为 Build 侧，减少内存占用。

### 3.1 Build 侧为什么通常选小表

哈希连接的核心不是“用了哈希，所以快”，而是它把一次全局两两比较，变成了：

1. 先把一侧组织成便于查找的结构
2. 再让另一侧逐行去探测

这就决定了 Build 侧的选择非常重要。通常选小表，是因为：

1. 哈希表更容易放进内存
2. 构建成本更低
3. Probe 时缓存局部性更好

如果 Build 侧选错，大表进哈希表不仅会拖慢构建，还可能直接触发 spill，把 `O(N+M)` 的理想情况打回现实世界里的复杂 I/O 问题。

## 4. 排序归并连接（Sort-Merge Join）

**前提**：两侧输入已按连接键排序

```
sort R by key; sort S by key
i = 0; j = 0
while i < |R| and j < |S|:
    if R[i].key == S[j].key:
        emit all matching pairs
        advance i and j
    elif R[i].key < S[j].key: i++
    else: j++
```

**复杂度**：O(|R| log |R| + |S| log |S|）（含排序）

**优点**：输出有序，适合后续 ORDER BY；可利用已有索引跳过排序。

### 4.1 Sort-Merge Join 的价值在“顺序性”

Sort-Merge Join 不一定总比 Hash Join 快，但它有一个 Hash Join 很难替代的优势：**输出天然保持有序语义**。

这意味着在某些执行计划里，Sort-Merge Join 虽然前面付出了排序代价，却可能节省后面更多代价，例如：

1. 后续还要 `ORDER BY`
2. 后续还要做排序聚合
3. 输入本来就来自索引扫描，已经接近有序

所以判断 Join 算法时，不能只盯单步复杂度，还要看整个算子树里的顺序是否能复用。

---

## 5. 三种算法对比

| 算法 | 时间复杂度 | 空间复杂度 | 适用场景 |
|------|-----------|-----------|---------|
| NLJ | O(N×M) | O(1) | 小表，任意条件 |
| Hash Join | O(N+M) | O(min(N,M)) | 等值连接，无序输入 |
| Sort-Merge | O(N log N + M log M) | O(1) | 等值连接，已排序或需有序输出 |

---

## 6. 算子树中的连接

```
Filter(grade > 80)
  └─ HashJoin(s.id = sc.student_id)
       ├─ SeqScan(students)      ← probe side（大表）
       └─ SeqScan(scores)        ← build side（小表）
```

优化器负责选择连接算法和连接顺序（Join Ordering）。

## 8. 小结

- NLJ 简单通用，但 O(N×M) 在大表上不可接受
- Hash Join 是 OLAP 场景的首选，O(N+M) 时间
- Sort-Merge Join 适合已排序输入或需要有序输出
- 连接顺序（哪张表做 Build 侧）对性能影响巨大

## 常见问题 Q&A

**Q1: 为什么 Nested Loop Join 最慢？**
A: 每行外表都扫描一遍内表，O(M*N)。但只需 O(1) 额外内存，适合小表连接。

**Q2: Hash Join 一定能用吗？**
A: 连接条件必须是等值（=）。非等值连接（>、<）只能用 Nested Loop。这也是等值连接最常见的优化场景。

**Q3: 连接顺序为什么重要？**
A: `A JOIN B JOIN C`，如果 A 结果集 10 行，B 结果集 10000 行，先连接 A 能大幅减少中间结果。查询优化器的核心工作就是选连接顺序。
