## 1. ORDER BY

```sql
SELECT name, score FROM students ORDER BY score DESC LIMIT 10;
```

排序算子（OrderBy）是**阻塞算子**，必须消费所有输入后才能输出。

### 1.1 为什么排序在数据库里这么“重”

很多应用代码里也会排序，所以学生容易低估数据库排序的难度。但数据库里的排序和普通集合排序差别很大：

1. 输入可能远大于内存
2. 排序结果往往要继续喂给下游算子
3. 排序顺序会影响后续 DISTINCT、GROUP BY、Merge Join、LIMIT

所以数据库里的排序不是一个简单工具函数，而是一个会重塑整条执行链路的数据重排操作。

### 内存排序

数据量小于缓冲池时，直接在内存中排序：

```java
public void open() {
    child.open();
    buffer = new ArrayList<>();
    while (child.hasNext()) buffer.add(child.next());
    child.close();
    buffer.sort(comparator);  // Java TimSort, O(N log N)
    cursor = 0;
}
```

### 外部归并排序（External Merge Sort）

数据量超过内存时，分两阶段：

**Phase 1 — 生成有序归并段（Sorted Runs）**：
```
将输入分成大小为 B 的块
对每块在内存中排序，写入临时文件 run_0, run_1, ...
```

**Phase 2 — 多路归并**：
```
用优先队列（最小堆）对所有 run 文件做 K 路归并
每次从堆顶取最小值输出，从对应 run 补充下一个元素
```

**复杂度**：O(N log N)，I/O 次数 = O(N/B × log_{B}(N/B))

### 1.2 外部排序真正利用的是什么

外部排序最核心的思想，不是“把文件拆小再排”，而是利用了磁盘顺序 I/O 比随机 I/O 便宜得多这一物理事实。

它通过两步把问题转成顺序访问友好的形式：

1. 先把大输入切成若干能放进内存的小块，各自排好
2. 再用多路归并把这些有序段顺序读出来、顺序合并

这就是为什么排序虽然看起来复杂，但它其实非常“数据库底层”：它始终在围绕页、缓冲区和顺序 I/O 组织算法。

## 2. DISTINCT

去重有两种实现：

### 基于排序
```
sort input
output first element of each group of duplicates
```

### 基于哈希
```java
Set<Tuple> seen = new HashSet<>();
for each tuple t:
    if seen.add(t): emit(t)
```

哈希去重 O(N) 时间，但需要 O(N) 空间；排序去重 O(N log N) 时间，O(1) 额外空间。

### 2.1 DISTINCT 为什么经常跟排序绑定

`DISTINCT` 表面上只是“去重”，但如果输入被排过序，相同值天然就会挨在一起，这会让去重从“记住见过谁”变成“比较当前值和前一个值”。

所以排序和去重常常形成非常自然的组合：

1. 先排序，让重复值聚拢
2. 再线性扫描，每组只保留一条

这也是为什么很多数据库会在 `ORDER BY`、`DISTINCT`、`GROUP BY` 之间尝试共享同一份排序结果。

## 3. LIMIT / OFFSET

```sql
SELECT * FROM students ORDER BY score DESC LIMIT 10 OFFSET 20;
```

LIMIT 算子包装在 OrderBy 之上：

```java
public Tuple next() {
    // 跳过 offset 行
    while (skipped < offset && child.hasNext()) {
        child.next(); skipped++;
    }
    if (returned >= limit) return null;
    Tuple t = child.next();
    returned++;
    return t;
}
```

## 4. Top-N 优化

`ORDER BY score DESC LIMIT 10` 不需要完整排序，只需维护大小为 N 的最小堆：

```java
PriorityQueue<Tuple> heap = new PriorityQueue<>(N, comparator);
for each tuple t:
    heap.offer(t);
    if heap.size() > N: heap.poll();  // 淘汰最小值
// heap 中剩余 N 个最大值
```

**复杂度**：O(M log N)，M 为总行数，N 为 LIMIT 值。当 N << M 时远优于完整排序。

## 4.1 Top-N 优化的本质：承认你根本不需要全序

完整排序的目标是得到“所有行的完整顺序”，但很多查询其实只想要前 10、前 100，甚至前 1 条。

这时继续做全排序就很浪费，因为你为大量最终会被丢弃的尾部数据支付了排序代价。Top-N 优化的本质，就是把目标从“求全序”降级成“维护一个当前最优候选集”。

这类思路在数据库里很常见：只要最终需求比完整问题更弱，执行器就应该尽量避免做完整工作。

## 7. 小结

| 算子 | 是否阻塞 | 时间复杂度 | 空间复杂度 |
|------|---------|-----------|-----------|
| OrderBy（内存）| 是 | O(N log N) | O(N) |
| OrderBy（外部）| 是 | O(N log N) | O(B) |
| Distinct（哈希）| 否（流式）| O(N) | O(N) |
| Limit | 否 | O(1) | O(1) |
| Top-N | 是 | O(M log N) | O(N) |

排序是查询性能的重要瓶颈，优化器会尽量利用索引顺序避免显式排序。下一模块进入索引。

## 常见问题 Q&A

**Q1: 为什么不直接用内存排序？**
A: 数据量可能超过内存。外部排序将数据分批读入内存排序后写出归并段，再归并。这是数据库处理大数据的标准模式。

**Q2: DISTINCT 和 GROUP BY 有什么关系？**
A: `SELECT DISTINCT a, b FROM t` 等价于 `SELECT a, b FROM t GROUP BY a, b`。DISTINCT 本质是不带聚合函数的 GROUP BY。

**Q3: 排序的 I/O 成本怎么算？**
A: 两路归并排序的 I/O 次数 = 2N * ceil(log₂(M))，其中 N 是总页数，M 是内存能放的页数。增加缓冲页可以显著减少归并趟数。
