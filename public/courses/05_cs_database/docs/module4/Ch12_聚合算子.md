## 1. 为什么需要聚合

SQL 聚合函数将多行数据归约为单个值：

```sql
SELECT COUNT(*), AVG(score), MAX(score) FROM students;
SELECT dept, COUNT(*), AVG(salary) FROM employees GROUP BY dept;
```

聚合是 OLAP 查询的核心，也是执行引擎中最复杂的算子之一。

### 1.1 聚合真正难的不是函数多，而是状态管理

很多同学第一次看聚合，会觉得无非就是实现几个函数：`COUNT`、`SUM`、`AVG`。但数据库里的聚合难点其实不在函数名，而在于它必须在执行过程中维护一份**跨多行的中间状态**。

对执行引擎来说，Filter 和 Projection 更像“逐行改写”；而 Aggregate 更像“先把很多行压缩进状态，再把状态产出成更少的结果行”。

这意味着聚合算子天然要回答三个问题：

1. 状态放哪里：内存中的哈希表，还是排序后的当前分组状态
2. 什么时候更新：每读到一行就更新一次
3. 什么时候产出：所有相关行都看完之后才能 finalize

理解了这三点，才算真正理解为什么聚合会成为执行流水线里的一个特殊节点。

## 2. 聚合函数类型

| 函数 | 语义 | 初始值 | 更新逻辑 |
|------|------|--------|---------|
| COUNT(*) | 行数 | 0 | +1 |
| COUNT(col) | 非 NULL 行数 | 0 | +1（非 NULL）|
| SUM(col) | 求和 | 0 | +val |
| AVG(col) | 平均值 | (0, 0) | sum+val, cnt+1 |
| MIN(col) | 最小值 | +∞ | min(cur, val) |
| MAX(col) | 最大值 | -∞ | max(cur, val) |

## 3. 哈希聚合

**适用场景**：无序输入，GROUP BY 列基数不太大

**算法**：
```
HashMap<GroupKey, AggState> hashTable

for each tuple t in child:
    key = extract(t, groupByCols)
    state = hashTable.getOrCreate(key)
    state.update(t, aggFuncs)

for each (key, state) in hashTable:
    emit(key + state.finalize())
```

**复杂度**：O(N) 时间，O(K) 空间（K = 分组数）

### 3.1 哈希聚合为什么快，但不一定稳

哈希聚合通常是默认首选，因为它不要求输入有序，时间复杂度也更漂亮。但它的前提其实很强：**分组状态必须能放进内存**。

如果 `GROUP BY` 基数很大，例如按用户、订单、时间戳这类高区分度列分组，哈希表会迅速膨胀。这时问题就不再是 CPU，而是：

1. 内存是否够用
2. 是否要 spill 到磁盘
3. 哈希冲突和扩容是否会引入额外开销

所以哈希聚合不是“永远更优”，而是“在分组状态可控时非常高效”。

## 4. 排序聚合

**适用场景**：输入已按 GROUP BY 列排序（或配合 ORDER BY）

**算法**：
```
sort input by groupByCols
currentKey = null, state = new AggState()

for each tuple t:
    key = extract(t, groupByCols)
    if key != currentKey:
        if currentKey != null: emit(currentKey + state.finalize())
        currentKey = key
        state = new AggState()
    state.update(t, aggFuncs)
emit(currentKey + state.finalize())
```

**优点**：空间 O(1)，可流式处理；**缺点**：需要排序 O(N log N)

### 4.1 排序聚合的价值，不只是省内存

很多人会把排序聚合简单理解成“哈希聚合的低内存版”。这不完整。

排序聚合还有两个重要优势：

1. 如果输入本身就按分组键有序，几乎不需要额外代价
2. 聚合结果天然按分组键有序，后续 `ORDER BY` 或 Merge Join 更容易接上

这就是为什么数据库优化器不会只盯着单个算子最优，而是会考虑整条执行链路的组合代价。

## 5. Volcano 模型中的聚合

聚合算子是**阻塞算子**（blocking operator）——必须消费完所有输入才能产出第一行：

```java
public void open() {
    child.open();
    // 消费所有输入，建立哈希表
    while (child.hasNext()) {
        Tuple t = child.next();
        updateHashTable(t);
    }
    child.close();
    // 将哈希表转为迭代器
    resultIter = hashTable.values().iterator();
}

public Tuple next() {
    return resultIter.hasNext() ? buildTuple(resultIter.next()) : null;
}
```

对比 Filter/Projection（流式算子），聚合无法 pipeline，是查询性能的关键瓶颈。

## 5.1 为什么聚合经常成为执行计划的“断点”

聚合算子最重要的执行特征是：它经常会打断上游的流式处理。

以 `GROUP BY dept` 为例，上游 `SeqScan` 可以一行一行吐数据，但聚合算子通常不能立刻把每一行转成结果，因为它还不知道这个分组后面会不会继续出现更多行。

所以从执行计划角度看，聚合的代价往往不仅是它自己消耗了多少 CPU/内存，还包括：

1. 它阻断了上游的 pipeline
2. 它可能迫使系统物化中间结果
3. 它会改变后续算子的输入规模与顺序

这也是数据库里聚合优化很重要的原因。

## 6. AVG 的实现细节

AVG 不能直接累加平均值，需要保存 (sum, count)：

```java
class AvgState {
    long sum = 0;
    int count = 0;
    void update(int val) { sum += val; count++; }
    double finalize() { return count == 0 ? 0.0 : (double) sum / count; }
}
```

## 8. 小结

| 对比项 | 哈希聚合 | 排序聚合 |
|--------|---------|---------|
| 时间复杂度 | O(N) | O(N log N) |
| 空间复杂度 | O(K) | O(1) |
| 适用场景 | 无序输入 | 已排序输入 |
| 流式处理 | 不支持 | 支持 |

聚合算子是阻塞算子，是查询流水线的断点。下一章实现连接算子。

## 常见问题 Q&A

**Q1: 为什么聚合必须消费完所有输入？**
A: 聚合结果依赖全局信息（COUNT 需要总行数，MAX 需要比较所有值）。不像 Filter 可以逐行处理。

**Q2: GROUP BY 没有索引怎么办？**
A: 只能用哈希聚合，内存开销 O(K)。分组数很多时可能内存不足，需要 spill to disk。

**Q3: NULL 在聚合中怎么处理？**
A: COUNT(*) 包含 NULL，COUNT(col) 忽略 NULL。SUM/AVG 忽略 NULL。NULL + 5 = NULL。
