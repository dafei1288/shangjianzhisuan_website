## 1. 列存储（Columnar Storage）

JimSQL 使用行存储（Row Store）：每行数据连续存储。

```
行存储: [id=1, name=Alice, score=90] [id=2, name=Bob, score=75] ...
列存储: [id: 1,2,3,...] [name: Alice,Bob,...] [score: 90,75,...]
```

### 列存储的优势

**OLAP 查询**（分析型，读少量列）：

```sql
SELECT AVG(score) FROM students;  -- 只需读 score 列
```

- 行存储：读取所有列（包括不需要的 id, name）
- 列存储：只读 score 列，I/O 减少 3 倍

**压缩**：同一列数据类型相同，压缩率高（Run-Length Encoding, Delta Encoding）。

### 列存储的劣势

- 点查询（读整行）需要从多列重组，代价高
- 写入需要更新多个列文件

**结论**：OLTP 用行存，OLAP 用列存。

## 2. LSM Tree（Log-Structured Merge Tree）

B+ 树的写入是随机 I/O，在写密集场景下性能差。LSM Tree 将随机写转为顺序写：

```
写入流程:
1. 写入内存 MemTable（有序跳表）
2. MemTable 满后，顺序写入磁盘 SSTable（Sorted String Table）
3. 后台 Compaction：合并多个 SSTable，删除过期版本

读取流程:
1. 查 MemTable
2. 查各层 SSTable（从新到旧）
3. 用 Bloom Filter 跳过不含目标键的 SSTable
```

**代表产品**：RocksDB、LevelDB、Cassandra、HBase

**写放大**：Compaction 会重写数据，写放大系数通常为 10-30x。

## 3. 分布式数据库

单机数据库的瓶颈：存储容量、计算能力、可用性。

### 分片（Sharding）

将数据按某个键分散到多个节点：

```
按 user_id % 4 分片:
节点0: user_id = 0, 4, 8, ...
节点1: user_id = 1, 5, 9, ...
节点2: user_id = 2, 6, 10, ...
节点3: user_id = 3, 7, 11, ...
```

**挑战**：跨分片 Join、分布式事务（2PC）、数据倾斜。

### 共识算法（Raft/Paxos）

多副本之间保持一致性：

```
Leader 接收写请求 → 复制到 Follower → 多数派确认 → 提交
```

**代表产品**：TiDB（基于 Raft）、CockroachDB、Google Spanner

---

## 4. 向量数据库

AI 时代的新需求：存储和检索高维向量（Embedding）。

```
传统查询: WHERE id = 42  （精确匹配）
向量查询: 找最相似的 K 个向量  （近似最近邻，ANN）
```

**应用场景**：语义搜索、推荐系统、图像检索、RAG（检索增强生成）

**核心算法**：HNSW（Hierarchical Navigable Small World）、IVF（倒排文件索引）

**代表产品**：Milvus、Pinecone、Weaviate、pgvector

## 6. 小结

数据库技术的演进方向：

| 方向 | 解决的问题 | 代表产品 |
|------|-----------|---------|
| 列存储 | OLAP 查询性能 | ClickHouse, DuckDB |
| LSM Tree | 写密集场景 | RocksDB, Cassandra |
| 分布式 | 水平扩展 | TiDB, CockroachDB |
| 向量数据库 | AI 语义检索 | Milvus, pgvector |
| HTAP | OLTP+OLAP 混合 | TiDB, SingleStore |

JimSQL 是学习数据库原理的起点，真实世界的数据库在每个模块上都有数十年的工程积累。

## 7. 扩展方向深度分析

### 7.1 列存储实现要点

```
行存页面布局:
  [Header][Slot1: id=1,name=Alice,score=90][Slot2: id=2,name=Bob,score=75]

列存页面布局:
  Page_id:   [1][2][3][4]...     ← 4 字节 × N
  Page_name: [Alice][Bob][...]   ← 变长，需要偏移表
  Page_score: [90][75][...]      ← 4 字节 × N

优势：
  SELECT AVG(score) FROM students
  行存：读 3 列 × N 行 = 3N 个值
  列存：只读 1 列 × N 行 = N 个值 → I/O 减少 66%

压缩策略：
  Run-Length Encoding: [A,A,A,B,B] → (A,3)(B,2)
  Delta Encoding: [100,101,105,106] → [100,+1,+4,+1]
  Dictionary: ["Alice","Alice","Bob"] → [0,0,1] + {0:"Alice",1:"Bob"}
```

### 7.2 LSM Tree 写入放大分析

```
Level 0: MemTable（内存）→ 满后刷盘为 SSTable
Level 1: SSTable 合并（每 10MB 合并一次）
Level 2: SSTable 合并（每 100MB 合并一次）
...

写入放大计算：
  1 次用户写入 →
    L0 刷盘 1 次 +
    L0→L1 合并（重写 L1 数据）+
    L1→L2 合并（重写 L2 数据）+ ...
  典型写放大: 10-30x

优化：RocksDB 的 LevelDB 结构，每层大小递增（10x），
  总写放大 ≈ level × size_ratio
  例如 6 层 × 10 倍 ≈ 10-15x
```

### 7.3 分布式事务（两阶段提交 2PC）

```
参与者: NodeA（订单库）、NodeB（库存库）
协调者: Transaction Coordinator

Phase 1: Prepare
  TC → NodeA: "准备好提交 T1 了吗？"
  NodeA: 锁定资源 → 写 Prepare 日志 → 回复 "READY"
  TC → NodeB: "准备好提交 T1 了吗？"
  NodeB: 锁定资源 → 写 Prepare 日志 → 回复 "READY"

Phase 2: Commit
  TC: 写决策日志 "COMMIT"
  TC → NodeA: "提交 T1"
  NodeA: 提交 → 释放锁 → 回复 "ACK"
  TC → NodeB: "提交 T1"
  NodeB: 提交 → 释放锁 → 回复 "ACK"

问题：如果 TC 在 Phase 2 崩溃，参与者会一直持有锁（阻塞）
优化：Paxos/Raft 选出新协调者继续提交
```

### 7.4 向量检索实现

```
HNSW（Hierarchical Navigable Small World）:

第 0 层（所有向量）：[v1]—[v2]—[v3]—[v4]—[v5]—[v6]
                      |         |              |
                     [v7]—[v8]—[v9]—[v10]

第 1 层（部分向量）：[v1]————[v5]
                     |        |
                    [v3]————[v9]

第 2 层（少量向量）：[v1]————[v9]

查询过程（从顶层开始贪心搜索）：
  层 2: v1 → v9（更近）→ 下沉
  层 1: v9 → v3（更近）→ v5 → 下沉
  层 0: v3 → v2 → v1 → 返回 Top-K

复杂度: O(log N)，远优于暴力搜索的 O(N)
```
