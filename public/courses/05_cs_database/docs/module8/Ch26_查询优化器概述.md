## 1. 优化器的位置

### 1.1 查询处理流水线

```
SQL 字符串
  ↓
词法分析（Lexer）    → Token 流
  ↓
语法分析（Parser）   → AST（抽象语法树）
  ↓
语义分析（Binder）   → 逻辑计划（Logical Plan）
  ↓
★ 查询优化器（Optimizer）★ → 物理计划（Physical Plan）
  ↓
执行引擎（Executor） → 结果集
```

### 1.2 为什么需要优化器

```
同一 SQL 可以有多种执行方式：

SELECT s.name, sc.score
FROM students s JOIN scores sc ON s.id = sc.student_id
WHERE sc.score > 80;

执行方式 1：先 Join 后过滤
  SeqScan(students) × SeqScan(scores) → Filter(score>80)
  中间结果：10000 × 100000 = 10亿行 → 再过滤到 20000 行

执行方式 2：先过滤后 Join（谓词下推）
  SeqScan(students) × Filter(score>80, SeqScan(scores))
  中间结果：10000 × 20000 = 2亿行 → 小了 5 倍

执行方式 3：使用索引 + 过滤
  IndexScan(scores, score>80) × SeqScan(students)
  中间结果：10000 × 20000 = 2亿行，但扫描更快

优化器的任务：从所有可能的执行方式中选择代价最小的。
```

## 2. RBO vs CBO

### 2.1 两种优化策略

| 维度 | RBO（Rule-Based） | CBO（Cost-Based） |
|------|-------------------|-------------------|
| 决策依据 | 预定义的规则 | 数据统计 + 代价估算 |
| 需要统计信息 | 不需要 | 需要 |
| 优化质量 | 可预测，但可能不是最优 | 更优，但依赖统计准确性 |
| 实现难度 | 低 | 高 |
| 典型用法 | 谓词下推、列裁剪 | Join 顺序、索引选择 |

### 2.2 实际数据库的做法

```
大多数数据库（MySQL、PostgreSQL）= RBO + CBO 混合：

Step 1: RBO 优化（逻辑变换）
  → 谓词下推、列裁剪、常量折叠
  → 消除冗余算子

Step 2: CBO 优化（物理选择）
  → 枚举 Join 顺序
  → 选择索引 vs 全表扫描
  → 选择 Join 方法（Hash/Sort-Merge/Nested-Loop）
```

## 3. 谓词下推（Predicate Pushdown）

### 3.1 核心思想

将 Filter 算子尽量下推到数据源附近，尽早减少中间结果集大小。

### 3.2 下推示例

```
优化前（逻辑计划）：
  Filter(score > 80)
    └─ HashJoin(s.id = sc.student_id)
         ├─ SeqScan(students)
         └─ SeqScan(scores)

优化后（谓词下推）：
  HashJoin(s.id = sc.student_id)
    ├─ SeqScan(students)
    └─ Filter(score > 80)        ← 下推到 Join 之前
         └─ SeqScan(scores)

效果：
  scores 表有 100000 行，score > 80 有 20000 行
  Filter 下推后，Join 只需处理 20000 行而非 100000 行
  → 中间结果从 10亿 行减少到 2亿 行
```

### 3.3 下推规则

```
规则 1: Filter → Join
  Filter 可以推过 Join 到相关的一侧
  条件：过滤条件只涉及一侧的列

规则 2: Filter → Project
  Filter 可以推过 Project（列投影）
  条件：过滤条件涉及的列在 Project 的输出中

规则 3: Filter → Aggregate
  Filter 可以推过 Aggregate
  条件：过滤条件不依赖聚合结果
```

### 3.4 代码实现

```java
public class PredicatePushdown implements OptimizationRule {
    @Override
    public PlanNode optimize(PlanNode plan) {
        if (plan instanceof FilterNode filter) {
            if (filter.child() instanceof JoinNode join) {
                // 尝试将条件下推到 Join 的左侧
                if (onlyUsesColumns(filter.predicate(), join.left().outputColumns())) {
                    return new JoinNode(
                        join.type(),
                        new FilterNode(filter.predicate(), join.left()),
                        join.right(),
                        join.condition()
                    );
                }
                // 尝试将条件下推到 Join 的右侧
                if (onlyUsesColumns(filter.predicate(), join.right().outputColumns())) {
                    return new JoinNode(
                        join.type(),
                        join.left(),
                        new FilterNode(filter.predicate(), join.right()),
                        join.condition()
                    );
                }
            }
        }
        return plan;  // 无法下推，返回原计划
    }
}
```

## 4. 列裁剪（Column Pruning）

### 4.1 核心思想

只读取查询需要的列，减少 I/O 和内存占用。

### 4.2 裁剪示例

```sql
SELECT name FROM students WHERE score > 80;
```

```
优化前：SeqScan 读取所有列（id, name, age, score, class, ...）
优化后：SeqScan 只读取 name 和 score 列

效果（假设 students 表有 20 列，每列平均 50 bytes）：
  优化前：每行读取 20 × 50 = 1000 bytes
  优化后：每行读取 2 × 50 = 100 bytes
  → I/O 减少 90%
```

### 4.3 列传播

```
列需求从查询顶部向下传播：

SELECT s.name        ← 需要 {name}
FROM students s
WHERE s.score > 80   ← 还需要 {score}

向上传递需求：
  Filter: 需要 {score}
  SeqScan: 需要 {name, score}

SeqScan 只读取这两列。
```

## 5. 常量折叠（Constant Folding）

### 4.1 核心思想

在编译时计算常量表达式，减少运行时计算。

```sql
SELECT * FROM products WHERE price > 100 * 1.08;  -- 税后价格
```

```
优化前：每行都计算 100 * 1.08
优化后：直接替换为 price > 108

更多例子：
  WHERE age + 0 = 18     → WHERE age = 18
  WHERE 1 = 1            → 移除条件（恒真）
  WHERE name LIKE '%'    → 移除条件（恒真）
  WHERE 1 = 0            → 返回空集（恒假）
```

## 6. 代价模型（CBO）

### 6.1 代价公式

```java
public class CostEstimator {

    double estimateCost(PlanNode plan) {
        return cpuCost(plan) + ioCost(plan);
    }

    double cpuCost(PlanNode plan) {
        if (plan instanceof SeqScanNode scan) {
            return scan.estimatedRows() * CPU_PER_ROW;
        }
        if (plan instanceof HashJoinNode join) {
            // Build hash table: left side rows
            double buildCost = join.left().estimatedRows() * HASH_BUILD_COST;
            // Probe: right side rows
            double probeCost = join.right().estimatedRows() * HASH_PROBE_COST;
            return buildCost + probeCost
                 + cpuCost(join.left()) + cpuCost(join.right());
        }
        // ... 其他算子
    }

    double ioCost(PlanNode plan) {
        if (plan instanceof SeqScanNode scan) {
            return scan.estimatedPages() * PAGE_READ_COST;
        }
        if (plan instanceof IndexScanNode scan) {
            // B+Tree 高度 + 叶子页
            double height = Math.log(scan.estimatedRows()) / Math.log(FANOUT);
            return height * INDEX_READ_COST
                 + scan.estimatedRows() * selectivity(scan) * PAGE_READ_COST;
        }
        // ...
    }
}
```

### 6.2 选择性估算

```
等值条件 (col = value):
  selectivity = 1 / NDV(col)    -- NDV = Number of Distinct Values

范围条件 (col > value):
  selectivity ≈ (max - value) / (max - min)

AND 条件:
  selectivity = sel(cond1) × sel(cond2)

NOT 条件:
  selectivity = 1 - sel(cond)

示例：
  students 表 10000 行，score 有 101 个不同值（0-100）
  WHERE score > 80
  selectivity = (100 - 80) / (100 - 0) = 0.2
  估算结果行数 = 10000 × 0.2 = 2000 行
```

| 要点 | 说明 |
|------|------|
| RBO | 基于规则，不依赖统计信息，简单可预测 |
| CBO | 基于代价，依赖统计信息，更优但更复杂 |
| 谓词下推 | 将 Filter 推到数据源附近，减少中间结果 |

## 常见问题 Q&A

**Q1: 查询优化器是不是一定会找到最优执行计划？**
A: 不一定。真实数据库通常在有限时间内寻找“足够好”的计划，因为所有可能计划的组合非常庞大。优化器依赖统计信息和代价模型，统计不准或模型简化时，就可能选出次优计划。

**Q2: 规则优化和代价优化有什么区别？**
A: 规则优化基于确定的等价变换，例如谓词下推、投影裁剪；代价优化会比较多个候选计划的估算成本，例如不同连接顺序或索引选择。前者像整理表达式，后者像在多个可行方案中做权衡。

**Q3: 为什么小型教学数据库也要学习优化器？**
A: 因为优化器连接了 SQL、统计信息、执行算子和存储结构。即使 JimSQL 只实现简化版本，学生也能理解数据库为什么不是“照着 SQL 顺序执行”，而是会重排、裁剪和选择更低成本的路径。
