## 1. 为什么需要统计信息

```sql
SELECT * FROM orders WHERE amount > 1000;
```

优化器需要知道：满足 `amount > 1000` 的行占总行数的比例（选择率），才能决定用 SeqScan 还是 IndexScan。

没有统计信息，优化器只能猜测，可能选出极差的执行计划。

## 2. 基本统计信息

```java
class TableStats {

}
```

## 3. 直方图

直方图将列的值域划分为若干桶（bucket），记录每个桶的行数：

### 等宽直方图（Equal-Width）

```
值域 [0, 100] 分为 10 个桶，每桶宽度 10：
桶0: [0,10)   → 50 行
桶1: [10,20)  → 120 行
桶2: [20,30)  → 80 行
...
```

**估算** `WHERE score BETWEEN 25 AND 35`：
```
桶2 的 [25,30) 部分：80 × (5/10) = 40 行
桶3 的 [30,35) 部分：60 × (5/10) = 30 行
估算总计：70 行
```

### 等频直方图（Equal-Frequency）

每个桶包含相同数量的行，桶的宽度不同。对倾斜分布更准确。

## 4. 选择率估算

| 谓词类型 | 估算公式 |
|---------|---------|
| `col = v` | 1 / distinctCount |
| `col > v` | (max - v) / (max - min) |
| `col BETWEEN a AND b` | (b - a) / (max - min) |
| `col IN (v1, v2, ...)` | n / distinctCount |
| `p1 AND p2` | sel(p1) × sel(p2)（独立假设）|
| `p1 OR p2` | sel(p1) + sel(p2) - sel(p1) × sel(p2) |

## 5. Join 代价估算

```
HashJoin(R ⋈ S):
  输出行数 = |R| × |S| × joinSelectivity
  代价 = cost(R) + cost(S) + |R| × hashCost + outputRows × tupleCost
```

**Join 顺序**：对于 n 张表的 Join，有 n! 种顺序。优化器用动态规划找最优顺序：

```
dp[{R,S}] = min(
    cost(R) + cost(S) + joinCost(R,S),
    cost(S) + cost(R) + joinCost(S,R)
)
dp[{R,S,T}] = min(
    dp[{R,S}] + joinCost({R,S}, T),
    dp[{R,T}] + joinCost({R,T}, S),
    dp[{S,T}] + joinCost({S,T}, R)
)
```

```sql
EXPLAIN SELECT s.name, sc.grade
```

## 8. 小结

统计信息是 CBO 的基础：

- **直方图**：描述列的值分布，支持范围查询选择率估算
- **选择率**：决定过滤后的行数，影响 Join 代价
- **Join 顺序**：动态规划找最优顺序，避免中间结果集爆炸
- **EXPLAIN**：展示优化器选择的执行计划和代价估算

统计信息需要定期更新（ANALYZE），否则优化器会基于过时数据做出错误决策。

## 常见问题 Q&A

**Q1: 为什么需要代价模型？**
A: 同一查询可能有多种执行计划。全表扫描 vs 索引扫描、不同连接顺序，代价可能差 1000 倍。代价模型帮助选最优计划。

**Q2: 代价估算准确吗？**
A: 不完全准确。基于统计信息的估算有误差（假设均匀分布、列独立等）。但比随机选择好得多，绝大多数情况能选到好计划。

**Q3: 统计信息什么时候更新？**
A: 通常在大量写入后手动 `ANALYZE`。有些数据库（如 PostgreSQL）有自动统计信息收集进程。

## 9. 代价模型详解

### 9.1 I/O 代价模型

```
SeqScan 代价:
  cost = pageCount × seqIOCost
  其中 seqIOCost ≈ 1.0（顺序 I/O，预读优化）

IndexScan 代价:
  cost = treeHeight × randomIOCost + matchingRows × randomIOCost
  其中 randomIOCost ≈ 4.0（随机 I/O，无预读）

示例（10000 行，每页 100 行，B+ 树高度 3）：
  SeqScan: 100 页 × 1.0 = 100.0
  IndexScan(WHERE id=5): 3 × 4.0 + 1 × 4.0 = 16.0  ← 选索引
  IndexScan(WHERE age>30, 70%匹配): 3×4 + 7000×4 = 28012 ← 不如全表扫描
```

### 9.2 CPU 代价模型

```
Filter 代价:
  cpuCost = inputRows × filterCost
  filterCost ≈ 0.01（简单的列比较）

Join 代价:
  HashJoin: buildCost(buildSide) + probeCost(probeSide × matchRate)
  NestedLoop: outerRows × innerCost

综合代价 = IO代价 + CPU代价 × cpuWeight
  cpuWeight 通常为 0.01（I/O 是主要瓶颈）
```

### 9.3 选择率估算实战

```
表 orders: 100000 行，status 有 5 种值，amount 范围 [10, 9999]

Q1: WHERE status = 'SHIPPED'
  选择率 = 1/5 = 0.2
  估算行数 = 100000 × 0.2 = 20000

Q2: WHERE amount > 5000
  选择率 = (9999-5000)/(9999-10) ≈ 0.5
  估算行数 = 100000 × 0.5 = 50000

Q3: WHERE status = 'SHIPPED' AND amount > 5000
  选择率 = 0.2 × 0.5 = 0.1（独立假设）
  估算行数 = 10000

实际可能偏离：如果 SHIPPED 订单金额普遍偏高，
实际选择率可能是 0.15。这就是直方图和 MCVE（Most Common Values）的价值。
```

## 10. 动态规划 Join 排序

```
4 表 Join: A(100行) ⋈ B(1000行) ⋈ C(50行) ⋈ D(500行)

单表代价:
  dp[{A}] = 1.0, dp[{B}] = 10.0, dp[{C}] = 0.5, dp[{D}] = 5.0

两表组合（6 种）:
  dp[{A,B}] = dp[{A}] + dp[{B}] + hashJoin(A,B) = 11 + 10 = 21
  dp[{A,C}] = dp[{A}] + dp[{C}] + hashJoin(A,C) = 1.5 + 1 = 2.5  ← 最优两表
  dp[{A,D}] = ...
  dp[{B,C}] = ...
  dp[{B,D}] = ...
  dp[{C,D}] = ...

三表组合（4 种）:
  dp[{A,B,C}] = min(
    dp[{A,B}] + joinCost({A,B}, C),
    dp[{A,C}] + joinCost({A,C}, B),   ← 通常最优（{A,C} 最小）
    dp[{B,C}] + joinCost({B,C}, A)
  )

四表（1 种）:
  dp[{A,B,C,D}] = min(
    dp[{A,B,C}] + joinCost({A,B,C}, D),
    dp[{A,B,D}] + joinCost({A,B,D}, C),
    dp[{A,C,D}] + joinCost({A,C,D}, B),
    dp[{B,C,D}] + joinCost({B,C,D}, A)
  )

复杂度: O(3^n)，n=表数。n>10 时需要启发式剪枝。
```
