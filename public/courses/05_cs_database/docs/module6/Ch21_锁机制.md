## 核心概念

### 1. 为什么需要锁

上一章我们了解了并发事务可能导致脏读、不可重复读、幻读等问题。锁机制是解决这些问题的经典方案：**通过限制并发访问，保证事务的隔离性**。

锁的基本思想：
- 读操作之前，先获取读锁（共享锁）
- 写操作之前，先获取写锁（排他锁）
- 操作完成后，释放锁
- 如果锁被其他事务持有，则等待

### 2. 共享锁与排他锁

#### 2.1 共享锁（Shared Lock，S Lock）

- 也称为**读锁**
- 多个事务可以同时持有同一资源的共享锁
- 持有共享锁的事务只能读取，不能修改
- 语义：**"我在读这个数据，其他人也可以读，但不能改"**

```
T1 持有 row_1 的 S Lock
T2 也可以获取 row_1 的 S Lock（共享，不冲突）
T3 想获取 row_1 的 X Lock → 必须等待（T1、T2 释放后才能获取）
```

#### 2.2 排他锁（Exclusive Lock，X Lock）

- 也称为**写锁**
- 同一时刻只有一个事务可以持有某资源的排他锁
- 持有排他锁的事务可以读取和修改
- 语义：**"我在修改这个数据，其他人既不能读也不能改"**

```
T1 持有 row_1 的 X Lock
T2 想获取 row_1 的 S Lock → 必须等待
T3 想获取 row_1 的 X Lock → 必须等待
```

#### 2.3 锁相容矩阵

| 请求\持有 | 无锁 | S Lock | X Lock |
|----------|------|--------|--------|
| S Lock   | 授予 | 授予   | 等待   |
| X Lock   | 授予 | 等待   | 等待   |

规则总结：
- **S-S 相容**：多个读者可以并发
- **S-X 不相容**：读写互斥
- **X-X 不相容**：写写互斥

```java
// 锁相容性检查
boolean isCompatible(LockType held, LockType requested) {
    if (held == LockType.NONE) return true;
    if (held == LockType.SHARED && requested == LockType.SHARED) return true;
    return false;  // X-S, X-X, S-X 都不相容
}
```

### 3. 两阶段锁协议（2PL）

#### 3.1 2PL 的规则

两阶段锁协议（Two-Phase Locking，2PL）规定：

**阶段一：增长阶段（Growing Phase）**
- 事务可以获取锁，但不能释放任何锁
- 事务持有的锁数量单调递增

**阶段二：收缩阶段（Shrinking Phase）**
- 事务可以释放锁，但不能获取任何新锁
- 事务持有的锁数量单调递减

```
时间线：
T1: 获取锁A → 获取锁B → 获取锁C → 释放锁A → 释放锁B → 释放锁C
    |←────── 增长阶段 ──────→|←──────── 收缩阶段 ──────────→|
                              ↑
                         锁点（Lock Point）
                    （持有锁数量最多的时刻）
```

**违反 2PL 的例子**：

```
T1: 获取锁A → 释放锁A → 获取锁B  ← 错误！释放后又获取新锁
```

#### 3.2 2PL 为什么能保证可串行化

**定理**：遵循 2PL 的事务调度是可串行化的。

**直觉理解**：
- 每个事务都有一个"锁点"（持有锁最多的时刻）
- 按照锁点的顺序排列事务，就是一个等价的串行执行顺序
- 因为在锁点之前，事务持有所有需要的锁，不会被其他事务干扰

**反例（不遵循 2PL 时）**：

```
T1: 读A(获取S锁) → 释放S锁 → 读B(获取S锁) → 释放S锁
T2:                    写A(获取X锁) → 写B(获取X锁)

可能的执行顺序：
T1 读A=10 → T2 写A=20 → T2 写B=20 → T1 读B=20
结果：T1 看到 A=10, B=20（不一致！）
```

#### 3.3 严格 2PL（Strict 2PL）

实践中通常使用**严格 2PL**：所有锁在事务提交或回滚时才释放。

优点：
- 避免级联回滚（Cascading Rollback）
- 实现更简单

```
严格 2PL：
T1: 获取锁A → 获取锁B → 操作 → COMMIT → 释放锁A → 释放锁B
```

### 4. 死锁

#### 4.1 死锁的产生

死锁（Deadlock）是指两个或多个事务互相等待对方释放锁，导致所有事务都无法继续执行。

**经典死锁场景**：

```
T1: 持有 row_A 的 X Lock，等待 row_B 的 X Lock
T2: 持有 row_B 的 X Lock，等待 row_A 的 X Lock

T1 等 T2 释放 row_B
T2 等 T1 释放 row_A
→ 永远等待，死锁！
```

死锁的四个必要条件（Coffman 条件）：
1. **互斥**：资源不能被共享（X Lock 的特性）
2. **持有并等待**：事务持有已有的锁，同时等待新锁
3. **不可抢占**：锁不能被强制剥夺
4. **循环等待**：存在等待环

#### 4.2 等待图（Wait-for Graph）

等待图是检测死锁的核心数据结构：
- **节点**：每个活跃事务是一个节点
- **边**：如果 T1 在等待 T2 持有的锁，则添加边 T1 → T2
- **死锁检测**：等待图中存在**环**，则存在死锁

```
等待图示例：
T1 → T2 → T3 → T1  （环！死锁）

T1 → T2 → T3       （无环，无死锁）
```

```java
// 等待图的环检测（DFS）
boolean hasCycle(Map<Long, Set<Long>> waitGraph) {
    Set<Long> visited = new HashSet<>();
    Set<Long> inStack = new HashSet<>();
    for (Long node : waitGraph.keySet()) {
        if (dfs(node, waitGraph, visited, inStack)) {
            return true;
        }
    }
    return false;
}

boolean dfs(Long node, Map<Long, Set<Long>> graph,
            Set<Long> visited, Set<Long> inStack) {
    if (inStack.contains(node)) return true;   // 发现环
    if (visited.contains(node)) return false;  // 已访问，无环
    visited.add(node);
    inStack.add(node);
    for (Long neighbor : graph.getOrDefault(node, Collections.emptySet())) {
        if (dfs(neighbor, graph, visited, inStack)) return true;
    }
    inStack.remove(node);
    return false;
}
```

#### 4.3 死锁处理策略

检测到死锁后，必须打破死锁。常见策略：

**选择牺牲者（Victim Selection）**：
- 选择代价最小的事务回滚
- 代价评估标准：
  - 事务已执行的操作数（操作越少，回滚代价越小）
  - 事务持有的锁数量
  - 事务的优先级（低优先级先回滚）
  - 事务已等待的时间（等待越久，越不应该回滚）

```java
// 选择牺牲者：选择操作数最少的事务
Transaction selectVictim(List<Transaction> deadlockCycle) {
    return deadlockCycle.stream()
        .min(Comparator.comparingInt(tx -> tx.operationCount))
        .orElseThrow();
}
```

**死锁预防（Prevention）**：
- **Wait-Die**：老事务等待年轻事务，年轻事务遇到老事务持有的锁时直接回滚
- **Wound-Wait**：老事务抢占年轻事务的锁（年轻事务回滚），年轻事务等待老事务

### 5. 锁粒度

#### 5.1 三种粒度

| 粒度 | 描述 | 并发度 | 锁开销 |
|------|------|--------|--------|
| 行锁 | 锁定单行记录 | 高 | 高（锁对象多） |
| 页锁 | 锁定一个数据页（通常 4KB/8KB） | 中 | 中 |
| 表锁 | 锁定整张表 | 低 | 低（锁对象少） |

**权衡**：
- 锁粒度越细，并发度越高，但锁管理开销越大
- 锁粒度越粗，并发度越低，但锁管理简单

#### 5.2 意向锁（Intention Lock）

当使用多粒度锁时，需要意向锁来提高效率。

**问题**：T1 持有 row_1 的 X Lock，T2 想获取 table 的 X Lock。T2 需要检查 table 下所有行是否有锁，代价很高。

**解决方案**：意向锁。在获取行锁之前，先在表上加意向锁。

- **IS（Intention Shared）**：打算在子节点加 S Lock
- **IX（Intention Exclusive）**：打算在子节点加 X Lock

```
T1 获取 row_1 的 X Lock 之前，先在 table 上加 IX Lock
T2 想获取 table 的 X Lock，发现 table 上有 IX Lock → 等待
（不需要遍历所有行！）
```

意向锁相容矩阵：

| 请求\持有 | IS | IX | S  | X  |
|----------|----|----|----|----|
| IS       | 相容 | 相容 | 相容 | 不容 |
| IX       | 相容 | 相容 | 不容 | 不容 |
| S        | 相容 | 不容 | 相容 | 不容 |
| X        | 不容 | 不容 | 不容 | 不容 |

## 代码讲解

### 5.1 LockManager 核心设计

```java
public class LockManager {
    // 每个资源的锁状态
    private final Map<String, LockState> lockTable = new ConcurrentHashMap<>();
    // 等待图（用于死锁检测）
    private final Map<Long, Set<Long>> waitGraph = new ConcurrentHashMap<>();

    static class LockState {
        LockType type = LockType.NONE;  // 当前锁类型
        Set<Long> holders = new HashSet<>();  // 持有者事务 ID
        Queue<LockRequest> waitQueue = new LinkedList<>();  // 等待队列
    }

    static class LockRequest {
        long txId;
        LockType requestedType;
        // 用于阻塞等待
        CountDownLatch latch = new CountDownLatch(1);
    }
}
```

### 5.2 获取锁的逻辑

```java
void acquireLock(long txId, String resource, LockType type) throws InterruptedException {
    synchronized (this) {
        LockState state = lockTable.computeIfAbsent(resource, k -> new LockState());

        if (isCompatible(state, type)) {
            // 直接授予锁
            state.holders.add(txId);
            if (type == LockType.EXCLUSIVE) state.type = LockType.EXCLUSIVE;
            else if (state.type == LockType.NONE) state.type = LockType.SHARED;
        } else {
            // 加入等待队列
            LockRequest req = new LockRequest(txId, type);
            state.waitQueue.add(req);
            // 更新等待图
            for (Long holder : state.holders) {
                addWaitEdge(txId, holder);
            }
            // 检测死锁
            if (hasCycle()) {
                state.waitQueue.remove(req);
                throw new DeadlockException("Deadlock detected for tx " + txId);
            }
            // 等待锁释放
            req.latch.await();
        }
    }
}
```

## 常见问题

**Q1：2PL 能防止所有并发问题吗？**

A：严格 2PL（Strict 2PL）可以防止脏读和不可重复读，但对于幻读，需要使用范围锁（Gap Lock）。普通 2PL 可能导致级联回滚：T1 读了 T2 写的数据，T2 回滚后 T1 也必须回滚。严格 2PL 通过在提交时才释放锁来避免这个问题。

**Q2：死锁检测的频率应该多高？**

A：这是一个权衡。检测太频繁会消耗 CPU；检测太少会导致事务长时间等待。实践中，MySQL InnoDB 默认每秒检测一次死锁（`innodb_deadlock_detect=ON`）。也可以设置锁等待超时（`innodb_lock_wait_timeout`），超时后自动回滚，作为死锁检测的补充。

**Q3：为什么 InnoDB 默认使用行锁而不是表锁？**

A：行锁的并发度更高。在 OLTP 场景中，大量事务并发修改不同行，行锁允许这些事务并发执行。表锁会让所有事务串行化，严重影响吞吐量。但行锁的管理开销更大，对于全表扫描或批量操作，表锁反而更高效。

**Q4：锁升级（Lock Upgrade）是什么？**

A：锁升级是指将已持有的 S Lock 升级为 X Lock。例如，事务先读取一行（获取 S Lock），然后决定修改它（需要 X Lock）。锁升级可能导致死锁：T1 和 T2 都持有某行的 S Lock，都想升级为 X Lock，互相等待对方释放 S Lock。解决方案是使用**更新锁（U Lock）**：读取时获取 U Lock（与 S 相容，与 X 不相容），修改时升级为 X Lock。

## 本章小结

本章深入讲解了数据库锁机制的核心内容：

- **共享锁（S Lock）** 允许并发读取，**排他锁（X Lock）** 保证写操作的独占性。锁相容矩阵定义了哪些锁可以共存。

- **两阶段锁协议（2PL）** 通过"先加锁后释放"的规则保证事务调度的可串行化。严格 2PL 在提交时才释放所有锁，避免级联回滚。

- **死锁** 是并发系统中不可避免的问题。通过**等待图**检测死锁（图中有环则有死锁），然后选择代价最小的事务作为牺牲者回滚。

- **锁粒度** 是并发度和开销的权衡。行锁并发度高但开销大，表锁开销小但并发度低。意向锁解决了多粒度锁的兼容性检查问题。
