## 核心概念

### 1. 自动修复闭环

传统开发流程是"写代码 -> 手动跑测试 -> 看报错 -> 手动改代码"的循环。Agent 自动修复将这个过程自动化：

```
1. 运行测试，获取输出
2. 解析错误，提取类型 + 文件 + 行号
3. 将错误信息交给 LLM 生成修复
4. 应用修复到代码
5. 回到步骤 1，直到测试全部通过或达到最大迭代次数
```

这为什么重要：Agent 的价值在于自我验证和自我修复。没有 feedback loop 的 Agent 只是代码生成器。测试输出是最可靠的反馈信号，闭环使 Agent 从"一次性生成"升级为"迭代优化"。

### 2. TestRunner

`TestRunner` 通过 subprocess 执行 pytest/unittest 命令，捕获 stdout+stderr，默认 60 秒超时。解析策略双重兼容：pytest 格式匹配 `"2 passed, 1 failed"` 用正则提取；unittest 格式匹配 `"Ran 3 tests"` + `"OK"` 作为兜底。核心数据结构 `TestResult` 包含 total/passed/failed/errors 计数、原始 output、failures 详情列表。

### 3. ErrorParser：错误分类与定位

`ErrorKind` 枚举定义 7 种错误类型：

| 类型 | 对应异常 | 修复策略 |
|------|---------|-------------|
| SYNTAX | SyntaxError | 定位行号，检查括号/冒号/缩进 |
| TYPE | TypeError | 分析操作数类型，检查函数参数 |
| ASSERTION | AssertionError | 比较期望值与实际值 |
| IMPORT | ImportError / ModuleNotFoundError | 检查模块名和安装状态 |
| ATTRIBUTE | AttributeError | 检查对象属性/方法是否存在 |
| RUNTIME | 其他运行时错误 | 需结合 traceback 分析 |
| UNKNOWN | 无法分类 | 返回原始错误信息 |

文件定位策略：从错误行向前回溯最多 10 行，寻找 `File "...", line N` 模式，提取文件路径和行号。每个 `ErrorInfo` 包含错误类型、消息、文件路径、行号和前后 3 行上下文 traceback。

### 4. FixLoop：修复迭代循环

```python
for i in range(max_iterations):    # 默认最多 5 轮
    test_result = test_runner.run(test_path)
    if test_result.failed == 0 and test_result.errors == 0:
        return FixResult(success=True)       # 测试全部通过
    errors = ErrorParser().parse(test_result.output)
    if not errors:
        break                                 # 无法解析，退出
    new_source = edit_fn(current, errors)     # 调用修复函数
    if new_source == current:
        break                                 # 收敛检测：代码无变化
    current = new_source                      # 继续迭代
```

`edit_fn` 是回调函数，签名为 `Callable[[str, list[ErrorInfo]], str]`，由调用者决定修复策略（LLM 生成 / 规则替换 / 模板修补）。收敛检测提供两个退出条件：修复函数返回值与上一次相同（LLM 认为无法继续），或解析不到任何错误。

### 5. LintRunner：集成 lint 工具

`LintRunner` 执行 ruff/pylint 命令，解析两种输出格式：ruff 格式 `main.py:5:10: F841 message` 和 pylint 格式 `main.py:10: [C0301] message`，输出结构化 `LintIssue` 列表。支持 `ruff check --fix` 自动修复格式化、未使用导入等问题。在 FixLoop 中可先调用 lint --fix 预处理，再进入测试修复循环。

## 代码实现

### 数据结构

```python
class ErrorKind(Enum):
    SYNTAX = "syntax"; TYPE = "type"; ASSERTION = "assertion"
    IMPORT = "import"; ATTRIBUTE = "attribute"; RUNTIME = "runtime"; UNKNOWN = "unknown"

@dataclass
class TestResult:
    total: int = 0; passed: int = 0; failed: int = 0; errors: int = 0
    output: str = ""; failures: list[dict] = field(default_factory=list)

@dataclass
class ErrorInfo:
    kind: ErrorKind; message: str
    file_path: str = ""; line_no: int = 0; traceback: str = ""

@dataclass
class FixResult:
    success: bool; iterations: int
    test_results: list[TestResult] = field(default_factory=list)
    fixes_applied: list[str] = field(default_factory=list)

@dataclass
class LintIssue:
    file_path: str; line: int; col: int; code: str; message: str; severity: str = "error"
```

### TestRunner 关键方法

```python
class TestRunner:
    def run(self, test_path="") -> TestResult:
        cmd = f"{self.command} {test_path}".strip()
        proc = subprocess.run(cmd, shell=True, capture_output=True, text=True,
                              cwd=self.cwd, timeout=self.timeout)
        return self.parse_output(proc.stdout + proc.stderr)

    def parse_output(self, output):
        result = TestResult(output=output)
        for pattern, attr in [(r"(\d+) passed","passed"),(r"(\d+) failed","failed"),(r"(\d+) error","errors")]:
            m = re.search(pattern, output)
            if m: setattr(result, attr, int(m.group(1)))
        result.total = result.passed + result.failed + result.errors
        return result
```

### ErrorParser 关键方法

```python
class ErrorParser:
    PATTERNS = [(ErrorKind.SYNTAX,r"SyntaxError: (.+)"), (ErrorKind.TYPE,r"TypeError: (.+)"),
                (ErrorKind.ASSERTION,r"AssertionError: (.+)"), (ErrorKind.IMPORT,r"ImportError: (.+)"),
                (ErrorKind.IMPORT,r"ModuleNotFoundError: (.+)"), (ErrorKind.ATTRIBUTE,r"AttributeError: (.+)")]

    def parse(self, output):
        errors, lines = [], output.splitlines()
        for i, line in enumerate(lines):
            for kind, pattern in self.PATTERNS:
                if (m := re.search(pattern, line)):
                    fp, ln = self._extract_location(lines, i)
                    errors.append(ErrorInfo(kind=kind, message=m.group(1) if m.lastindex else line.strip(),
                                            file_path=fp, line_no=ln,
                                            traceback="\n".join(lines[max(0,i-3):i+3])))
                    break
        return errors
```

### FixLoop 完整实现

```python
class FixLoop:
    def __init__(self, test_runner, max_iterations=5):
        self.test_runner = test_runner
        self.max_iterations = max_iterations

    def run(self, source, edit_fn, test_path="") -> FixResult:
        result, current = FixResult(success=False, iterations=0), source
        for i in range(self.max_iterations):
            result.iterations = i + 1
            tr = self.test_runner.run(test_path)
            result.test_results.append(tr)
            if tr.failed == 0 and tr.errors == 0:
                result.success = True; return result
            errors = ErrorParser().parse(tr.output)
            if not errors: break
            new_source = edit_fn(current, errors)
            if new_source == current: break
            current = new_source
            result.fixes_applied.append(f"Iteration {i+1}: fixed {len(errors)} error(s)")
        return result
```

### 自动修复为什么经常卡在最后几步

很多人第一次做自动修复循环，会觉得“既然能读测试输出，那多跑几轮总能修好”。真实情况通常不是这样。FixLoop 最容易卡住的不是第一轮，而是后两类情况：

1. **错误表象变了，但根因没变**
   - 例如先修掉 `ImportError`，下一轮又暴露出 `AttributeError`
   - 看起来像在前进，实际上只是把更深的错误翻了出来
2. **修复动作开始互相打架**
   - 第 1 轮为了过测试硬编码返回值
   - 第 2 轮又因为 lint 或其他测试失败，被迫回头重改

所以一个成熟的自动修复系统不能只关心“还剩几个红测”，还要关心：

- 当前错误是否比上轮更聚焦
- 新改动是否引入了新的失败类别
- 是否已经进入“反复改同一区域但收益很小”的收敛区

这也是为什么 `max_iterations`、收敛检测、错误分类和原始 traceback 保留都很重要。它们不是锦上添花，而是防止 Agent 陷入无限修补循环的基本约束。

## 常见问题 Q&A

**Q1：为什么自动修复要优先依赖测试，而不是直接让 LLM 看代码猜哪里错了？**

A：因为测试给的是外部可验证约束，代码猜测给的是内部主观判断。前者能形成稳定闭环，后者容易变成“越改越偏”的自由发挥。

**Q2：如果测试本身是错的、脆弱的或不稳定的，FixLoop 会怎样？**

A：FixLoop 会被误导。它只能保证“朝着当前测试定义的目标优化”，不能判断测试规范本身是否合理。所以在生产环境里，自动修复通常只对可信测试集开放，且要区分 flaky test 和真实失败。

**Q3：为什么收敛检测里要检查 `new_source == current`？**

A：因为这通常意味着修复器已经拿不出新的有效动作了。继续迭代只会浪费预算和时间，还可能在日志里制造“做了很多事”的假象。

**Q4：测试通过之后还需要跑 lint 吗？**

A：需要。测试主要验证行为是否正确，lint 和格式检查则保证代码风格、未使用导入、潜在静态错误等工程质量问题。两者解决的问题不同，不能互相替代。

## 本章小结

测试驱动的自动修复（TDD with AI）是 AI Agent 最有价值的应用场景之一：
- **红绿循环**：Agent 读取失败测试 → 分析原因 → 修改代码 → 验证通过
- **错误定位**：利用堆栈跟踪和测试覆盖率缩小可疑代码范围
- **修复策略**：从简单到复杂——先尝试常见修复模式，失败则深入分析

这种"测试即规范"的模式让 Agent 的修改有明确的验证标准，大幅减少手动审查成本。下一章进入向量检索与语义搜索。
