# Ch19：Goal 模式

## 学习目标

- 理解 Goal 模式与普通交互的区别，以及为什么需要自主规划能力
- 掌握 `/goal` 命令的使用方法和参数选项

- 了解 Goal 模式与 Sub-Agent 并行模式的适用场景对比

## 1. 为什么需要 Goal 模式

### 1.1 单步交互的局限

在普通 REPL 模式下，你每次输入一条指令，Codex 执行一步。这对简单任务足够，但面对复杂任务时存在明显问题：

| 维度 | 普通模式 | Goal 模式 |
|------|----------|-----------|
| 交互频率 | 每步需人工输入 | 一次输入，自主执行 |
| 规划能力 | 无（单步推理） | 有（多步规划 + 子目标拆分） |
| 上下文 | 依赖人类记忆 | 自动维护任务上下文 |
| 适用规模 | 1-2 步任务 | 5-50 步复杂任务 |
| 人类负担 | 高（需要逐步指导） | 低（只需设定目标） |

### 1.2 核心思想：从"指令驱动"到"目标驱动"

普通模式是指令驱动（Imperative）：你告诉 Codex **每一步做什么**。
Goal 模式是目标驱动（Declarative）：你告诉 Codex **最终要达到什么状态**，它自主规划路径。

```
指令驱动（普通模式）：
  你: "打开 src/api/auth.ts"
  你: "找到 handleLogin 函数"
  你: "在 try 块后添加 catch"
  你: "运行测试"
  你: "提交代码"
  → 5 次人工输入

目标驱动（Goal 模式）：
  你: /goal "auth 模块的所有函数都需要错误处理，确保测试通过"
  Codex 自主完成上述所有步骤 + 更多
  → 1 次人工输入
```

### 1.3 Goal 模式的执行流程

```
用户输入目标
    │
    ▼
┌─────────────────────────┐
│ 1. 目标解析与拆分        │  ← Codex 分析目标，拆分为子任务
│    目标 → 子任务列表     │
└────────┬────────────────┘
         │
    ┌────▼────────────────┐
    │ 2. 子任务执行循环    │  ← 对每个子任务：
    │    ├─ 选择工具       │     read/write/bash
    │    ├─ 执行操作       │
    │    ├─ 观察结果       │
    │    └─ 判断完成       │
    └────┬────────────────┘
         │
    ┌────▼────────────────┐
    │ 3. 结果验证         │  ← 检查目标是否真正达成
    │    ├─ 运行测试       │
    │    ├─ 检查文件状态   │
    │    └─ 生成报告       │
    └────┬────────────────┘
         │
         ▼
    输出完成报告
```

**关键区别**：Goal 模式不只是"循环执行"，它还包含**规划**和**验证**两个关键阶段。

## 2. 使用方法

### 2.1 基本语法

```bash
# 在 REPL 中启动 Goal 模式
> /goal 确保项目所有测试通过，如果有失败的就修复

# Codex 开始自主执行
📋 目标：确保所有测试通过
  Step 1/5: 运行测试... 3 个失败
  Step 2/5: 分析失败原因...
  Step 3/5: 修复 test A...
  Step 4/5: 修复 test B...
  Step 5/5: 修复 test C... 运行测试 → 全部通过 ✅

目标完成！修复了 3 个失败的测试。
```

### 2.2 目标描述的最佳实践

目标描述的质量直接决定执行效果。以下是编写好目标的要点：

**好的目标描述：**
```
/goal "确保 src/api/ 目录下所有 .ts 文件的导出函数都有 JSDoc 注释，
      @param 和 @returns 必须完整，参数类型必须与签名一致"
```
- ✅ 范围明确（`src/api/` 目录）
- ✅ 条件具体（JSDoc + @param + @returns）
- ✅ 可验证（类型一致性可检查）

**差的目标描述：**
```
/goal "改善代码质量"
```
- ❌ 范围模糊（哪个文件？哪个目录？）
- ❌ 条件不明确（什么是"质量"？）
- ❌ 不可验证（怎么算完成？）

### 2.3 目标描述模板

```bash
# 模板：范围 + 动作 + 条件 + 验证
/goal "在 <范围> 中 <动作>，要求 <条件>，完成后 <验证方式>"

# 实例 1：批量重构
/goal "在 src/components/ 中把所有 class 组件改为函数组件，
      使用 hooks 替代生命周期方法，完成后运行 npm test 确保通过"

# 实例 2：安全加固
/goal "扫描项目中所有 SQL 查询，确保都使用参数化查询，
      修复所有字符串拼接 SQL 的地方，完成后运行安全检查"

# 实例 3：性能优化
/goal "分析 src/utils/ 中所有函数的执行时间，
      对超过 100ms 的函数进行优化，优化后重新测试确保不引入 bug"
```

## 3. 适合 Goal 模式的任务

### 3.1 任务适用性分析

| 适合 | 不适合 |
|------|--------|
| "确保所有 lint 错误修复" | "修改第 42 行" |
| "给所有 API 添加错误处理" | "查看这个文件" |
| "把所有 class 组件改成函数组件" | "解释这段代码" |
| "重构整个 auth 模块" | "运行 npm test" |

**判断标准**：需要多步执行、有明确完成条件的任务适合 Goal 模式。

### 3.2 四种典型 Goal 场景

**场景 1：批量修复（最常见）**
```bash
/goal "修复项目中所有 TypeScript 类型错误，每个错误都要有正确的类型标注"
# Codex 会：扫描 → 发现错误 → 逐个修复 → 验证
```

**场景 2：代码迁移**
```bash
/goal "把项目从 JavaScript 迁移到 TypeScript，先改配置文件，
      再逐个添加类型定义，最后确保所有测试通过"
# Codex 会：改 tsconfig → 改后缀 → 加类型 → 修错误 → 验证
```

**场景 3：标准化/规范化**
```bash
/goal "确保所有 React 组件文件名使用 PascalCase，
      导出方式统一为 named export，完成后运行 lint 验证"
# Codex 会：扫描组件 → 检查命名 → 重命名文件 → 更新导入 → 验证
```

**场景 4：代码审查 + 自动修复**
```bash
/goal "审查 src/ 下所有文件的代码风格，统一缩进为 2 空格，
      字符串使用单引号，末尾加分号"
# Codex 会：扫描 → 发现不一致 → 批量修改 → 验证
```

## 4. 进度监控与控制

### 4.1 实时进度显示

Goal 模式执行时会显示详细进度：

```
📋 目标：确保所有 API 端点都有错误处理
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[Step 1/8] 扫描路由文件...
  ✓ 发现 6 个路由文件，23 个端点

[Step 2/8] 分析错误处理覆盖...
  ⚠ 12 个端点缺少 try-catch

[Step 3/8] 修复 auth/routes.ts (3 个端点)...
  ✓ 已添加错误处理

[Step 4/8] 修复 user/routes.ts (4 个端点)...
  ✓ 已添加错误处理

...
```

### 4.2 中断与恢复

```bash
# 中断当前步骤（不丢失已完成的工作）
Ctrl+C

# Codex 会显示已完成和剩余步骤
⚠ Goal 被中断
  已完成: 4/8 步
  已修改: auth/routes.ts, user/routes.ts
  
  继续执行请输入: /goal continue
  回滚修改请输入: /goal rollback
```

### 4.3 配合 AGENTS.md 设置边界

在 `AGENTS.md` 中设定 Goal 模式的安全边界：

```markdown
## Goal 模式约束

- 不允许删除文件
- 不允许修改 package.json 的 dependencies
- 不允许直接推送到 main 分支
- 每次修改不超过 20 个文件
- 数据库迁移文件必须手动确认
```

## 5. Goal 模式 vs Sub-Agent 模式

Ch18 学了 Sub-Agent 并行模式，这里对比两者的适用场景：

| 维度 | Goal 模式 | Sub-Agent 模式 |
|------|-----------|----------------|
| 任务关系 | 串行依赖（A → B → C） | 并行独立（A ‖ B ‖ C） |
| 执行者 | 单个 Agent 循环 | 多个 Agent 同时 |
| 上下文 | 完整共享 | 各自独立 |
| 适用 | 有序的修复/重构 | 独立的代码审查/测试 |
| 速度 | 串行执行 | 并行更快 |

**组合使用**：复杂项目可以先用 Sub-Agent 并行分析，再用 Goal 模式串行修复。

```
# 高级用法：Sub-Agent 分析 + Goal 模式修复
/sub-agent "分析前端代码质量" "分析后端代码质量" "分析测试覆盖率"
# 获取三个报告后...

/goal "根据分析报告，修复优先级最高的 10 个问题"
```

## 6. 常见问题与陷阱

### 6.1 目标过于模糊

```
❌ /goal "优化项目"
→ Codex 不知道从哪开始，可能做无关紧要的改动

✅ /goal "将 src/utils/ 中执行时间超过 100ms 的函数优化到 50ms 以下"
→ 范围、条件、验证方式都明确
```

### 6.2 目标范围过大

```
❌ /goal "重构整个项目"
→ 可能修改几百个文件，难以验证，回滚困难

✅ /goal "重构 src/api/auth.ts 和 src/api/user.ts，提取公共逻辑到 shared.ts"
→ 范围可控，影响面有限
```

### 6.3 缺少验证条件

```
❌ /goal "给所有函数加注释"
→ 怎么算"有注释"？注释质量如何？

✅ /goal "给 src/api/ 下所有导出函数添加 JSDoc，
      包含 @param 和 @returns，完成后运行 tsc 确保类型正确"
→ 有明确的验证方式
```

## 常见问题 Q&A

**Q1：Goal 模式可以中途修改目标吗？**

A：可以。按 `Ctrl+C` 中断后，输入新的 `/goal` 命令即可。Codex 会基于当前文件状态重新规划。已完成的部分不会被回滚（除非你手动回滚或使用 `/goal rollback`）。

**Q2：Goal 模式修改了不该改的文件怎么办？**

A：有三种恢复方式：
1. **Git 回滚**：`git checkout -- <file>`（推荐，前提是修改前已 commit）
2. **Goal rollback**：`/goal rollback` 回滚本轮所有修改
3. **手动撤销**：在 IDE 中用 undo

建议在运行 Goal 前先 `git commit`，确保有回滚点。

**Q3：Goal 模式执行时间有限制吗？**

A：受两个因素限制：
- **Token 上限**：Goal 的完整对话历史不能超过模型上下文窗口
- **步数限制**：Codex 内部有最大步数限制（默认 50 步），防止无限循环
如果目标过于复杂导致超出限制，建议拆分为多个小 Goal。

**Q4：Goal 模式和 full-auto 审批模式有什么区别？**

A：它们在不同层面工作：
- **审批模式**（Suggest/Auto/Full-Auto）：控制每一步是否需要人工确认
- **Goal 模式**：控制 Codex 是否自主规划多步任务

可以组合使用：`/goal` + `--approval suggest` 表示 Codex 自主规划但每步需确认。

|------|------|
| 核心思想 | 从指令驱动到目标驱动 |

| 目标描述 | 范围 + 动作 + 条件 + 验证 |
