## 1. 为什么需要 Sub-Agent

### 1.1 单 Agent 的瓶颈

Codex CLI 默认是单 Agent 串行执行——一次只做一件事。对于简单任务这没问题，但面对大型项目时会遇到瓶颈：

| 场景 | 单 Agent | 多 Agent 并行 |
|------|----------|---------------|
| 代码审查（前端+后端+测试） | 串行审查，耗时长 | 同时审查，速度快 3 倍 |
| 多文件重构 | 一个一个改 | 分组并行改 |
| Bug 搜索 | 逐文件排查 | 同时搜多个模块 |
| 文档生成 | 写完一个写下一个 | 多个文档同时写 |

### 1.2 什么是 Sub-Agent

Sub-Agent 是从主 Agent 分离出来的独立执行单元，每个 Sub-Agent 有自己的：
- **独立的上下文**：可以专注于特定任务，不受其他任务干扰
- **独立的工具权限**：可以限制只能读取某些文件
- **独立的生命周期**：启动 → 执行 → 返回结果 → 销毁

```
┌─────────────────────────────────┐
│          主 Agent (Orchestrator) │
│  接收任务 → 拆分 → 调度 → 汇总   │
└───────┬─────────┬───────────────┘
        │         │
   ┌────▼───┐ ┌───▼────┐ ┌────────┐
   │Sub-A1  │ │Sub-A2  │ │Sub-A3  │
   │审查前端│ │审查后端│ │审查测试│
   └────────┘ └────────┘ └────────┘
        │         │          │
        └─────────┴──────────┘
                  │
            结果汇总给主 Agent
```

### 1.3 并行 vs 串行的本质区别

```
串行执行（单 Agent）：
  时间 → T1 ──→ T2 ──→ T3 ──→ 完成
  总时间 = T1 + T2 + T3

并行执行（Sub-Agent）：
  时间 → T1 ──→
       → T2 ──→  汇总 → 完成
       → T3 ──→
  总时间 = max(T1, T2, T3) + 汇总时间
```

## 2. 使用方法

### 2.1 基本语法

```bash
# 同时启动多个 Sub-Agent
> /sub-agent "分析 src/frontend/ 的代码质量" "分析 src/backend/ 的代码质量"

# 两个 Agent 同时开始工作
🤖 Sub-Agent 1: 分析前端代码质量...
🤖 Sub-Agent 2: 分析后端代码质量...

# 各自完成后汇总
📊 Sub-Agent 1 结果: 前端发现 8 个问题（3 高优）
📊 Sub-Agent 2 结果: 后端发现 5 个问题（2 高优）

📋 汇总报告:
  前端: 缺少错误处理(3)、未使用变量(2)、类型缺失(3)
  后端: SQL 注入风险(1)、缺少索引(1)、未处理异常(3)
  建议优先修复: SQL 注入风险（安全）> 缺少错误处理（稳定性）
```

### 2.2 限制 Sub-Agent 权限

```bash
# 只读权限（适合审查任务）
> /sub-agent --readonly "审查 src/api/ 的安全性"

# 限制文件范围
> /sub-agent --scope "src/utils/" "为所有工具函数添加单元测试"

# 组合使用
> /sub-agent --readonly --scope "src/api/" "检查所有端点是否有输入验证"
```

### 2.3 多 Sub-Agent 协作

```bash
# 三个 Sub-Agent 分别负责不同维度
> /sub-agent \
    "代码质量：检查所有函数的圈复杂度，标记超过 10 的" \
    "安全性：扫描所有用户输入处理，标记未验证的" \
    "性能：分析所有数据库查询，标记 N+1 问题"

# 结果按严重程度排序
🚨 严重 (3):
  - SQL 注入风险: src/api/user.ts:45
  - SQL 注入风险: src/api/order.ts:78
  - N+1 查询: src/services/product.ts:120

⚠️ 警告 (5):
  - 圈复杂度过高: src/utils/validator.ts:23 (CC=15)
  ...
```

## 3. 任务设计原则

### 3.1 什么任务适合并行

**核心判断标准：任务之间是否独立？**

```
✅ 可并行的任务（互相不依赖）：
  - 审查不同目录的代码
  - 为不同文件写测试
  - 检查不同维度的质量（安全/性能/可读性）
  - 生成不同模块的文档

❌ 不可并行的任务（有依赖关系）：
  - 先改配置文件再改代码（配置是代码的前提）
  - 先写接口再写实现（实现依赖接口）
  - 先修复 Bug 再重构（重构依赖正确的代码）
```

### 3.2 任务拆分的粒度

| 粒度 | 示例 | 评价 |
|------|------|------|
| 太粗 | "审查整个项目" | 单个 Sub-Agent 负担太重 |
| 适中 | "审查前端代码质量" | 范围明确，结果有用 |
| 太细 | "审查 index.ts 第 10 行" | 并行开销大于收益 |

**经验法则**：每个 Sub-Agent 的工作量应在 1-5 分钟之间。太少不值得并行，太多串行即可。

### 3.3 结果汇总策略

多个 Sub-Agent 的结果可能重叠或冲突，需要汇总策略：

```
1. 去重：多个 Agent 可能发现同一问题
2. 排序：按严重程度或优先级排列
3. 归因：标记每个问题由哪个 Agent 发现
4. 行动建议：自动生成修复计划
```

## 4. 资源与限制

### 4.1 资源消耗

每个 Sub-Agent 都会消耗独立的 Token 和 API 配额：

| 资源 | 单 Agent | 3 个 Sub-Agent |
|------|----------|----------------|
| API 调用 | 串行 | 并行（3 倍并发） |
| Token 消耗 | 1x | 约 3x |
| 执行时间 | T1+T2+T3 | max(T1,T2,T3) |
| 上下文窗口 | 共享 | 各自独立 |

### 4.2 最佳实践

1. **Sub-Agent 数量控制在 2-5 个**：过多会导致 API 限流
2. **避免写冲突**：不要让多个 Agent 同时修改同一文件
3. **只读任务最适合并行**：审查、分析、搜索等
4. **写操作需要协调**：如果必须并行写，确保不同文件

## 5. 实战案例

### 案例：大型项目的全面代码审查

```bash
# 项目结构
my-project/
├── src/
│   ├── api/        # API 路由
│   ├── services/   # 业务逻辑
│   ├── models/     # 数据模型
│   └── utils/      # 工具函数
├── tests/
└── docs/

# 启动 4 个 Sub-Agent 分别审查
> /sub-agent \
    --readonly --scope "src/api/" \
    "检查所有端点是否有：输入验证、错误处理、正确的 HTTP 状态码" \
    \
    --readonly --scope "src/services/" \
    "检查业务逻辑是否有：竞态条件、资源泄露、异常处理" \
    \
    --readonly --scope "src/models/" \
    "检查数据模型是否有：字段验证、索引建议、类型安全" \
    \
    --readonly --scope "tests/" \
    "评估测试覆盖率和质量，标记缺少测试的关键模块"
```

## 常见问题 Q&A

**Q1：多个 Sub-Agent 可以修改同一个文件吗？**

A：技术上可以但不建议。如果两个 Agent 同时修改同一文件，后完成的会覆盖先完成的修改。解决方案：
- 在命令中明确划分各自的范围（`--scope`）
- 只读任务放心并行，写操作严格隔离

**Q2：Sub-Agent 的数量有限制吗？**

A：Codex 默认限制为最多 5 个并行 Sub-Agent。这个限制出于两个考虑：
1. API 并发请求上限（避免被限流）
2. 上下文管理复杂度（太多结果难以汇总）
建议日常使用 2-3 个即可。

**Q3：Sub-Agent 失败了怎么办？**

A：其他 Sub-Agent 不受影响。失败的 Agent 会返回错误信息，主 Agent 汇总时会标记哪些任务成功、哪些失败。你可以针对失败的任务单独重试。

**Q4：Sub-Agent 可以嵌套吗（Agent 里启动 Agent）？**

A：目前不支持。Sub-Agent 是扁平结构，只能由主 Agent 创建。这避免了递归调度的复杂性。

## 小结

| 要点 | 说明 |
|------|------|
| 核心价值 | 并行执行独立任务，提升效率 |
| 适用场景 | 代码审查、多维度分析、批量操作 |
| 关键原则 | 任务必须互相独立，避免写冲突 |
| 资源消耗 | Token 消耗随 Agent 数量线性增长 |
| 最佳实践 | 2-5 个 Agent，只读任务最适合并行 |
