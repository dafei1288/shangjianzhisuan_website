## 1. 为什么需要功能开发工作流

### 1.1 传统开发 vs AI 辅助开发

```
传统开发：
  需求分析 → 设计 → 编码 → 测试 → 审查 → 部署
  全靠人工，每个环节都可能卡住

AI 辅助开发：
  需求描述 → AI 规划 → 逐步执行 → AI 测试 → AI 审查
  AI 承担编码和测试的重活，人负责需求和审查

关键区别：
  - 传统：人在"做"（写代码）
  - AI辅助：人在"指导"（描述需求、审查结果）
```

### 1.2 Codex 在功能开发中的角色

| 环节 | Codex 能做什么 | 人需要做什么 |
|------|---------------|-------------|
| 需求分析 | 提问澄清模糊点 | 描述业务需求 |
| 任务拆分 | 自动生成开发计划 | 确认计划合理性 |
| 编码 | 生成代码 | 审查代码质量 |
| 测试 | 生成测试用例 | 确认测试覆盖 |
| 调试 | 定位和修复 Bug | 描述问题现象 |
| 审查 | 自动审查代码 | 决定是否采纳建议 |

## 2. 需求到代码：完整流程

### 2.1 描述需求（最关键的一步）

需求描述的质量直接决定生成代码的质量：

```
❌ 模糊的描述：
> 加个收藏功能

✅ 好的描述：
> 需要给用户添加"收藏文章"功能。需求：
> 1. 用户可以在文章详情页点击"收藏"按钮
> 2. 收藏列表在个人中心展示
> 3. 数据库用新表 favorites 存储
> 4. 需要收藏和取消收藏的 API
> 5. 收藏按钮要有实时状态（已收藏/未收藏）
> 6. 收藏列表要分页，每页 20 条
> 7. 使用项目现有的 tRPC + Prisma 技术栈
```

**需求描述模板**：

```markdown
## 功能：[功能名称]

### 背景
为什么需要这个功能？解决什么问题？

### 功能要求
1. 具体的功能点 1
2. 具体的功能点 2
3. ...

### 技术要求
- 使用什么技术栈
- 遵循什么代码风格
- 性能要求

### 约束
- 不能做什么
- 兼容性要求
```

### 2.2 让 Codex 规划开发步骤

```
> 我需要实现以下功能：
> [粘贴需求描述]
> 
> 请先给我一个开发计划，不要直接开始写代码。

📋 Codex 生成的开发计划：

Step 1: 数据库设计
  - 修改 prisma/schema.prisma，添加 Favorite 模型
  - 执行数据库迁移

Step 2: 后端 API
  - 创建 src/server/routers/favorites.ts
  - 实现 add / remove / list 三个接口
  - 添加输入验证

Step 3: 前端组件
  - 创建 FavoriteButton.tsx（收藏按钮）
  - 集成到文章详情页

Step 4: 收藏列表页
  - 创建 profile/favorites/page.tsx
  - 分页加载

Step 5: 测试
  - 后端单元测试
  - 前端组件测试

预计修改文件：8 个
预计代码行数：~300 行

开始执行 Step 1？
```

**为什么先规划再执行？**
- 规划让你可以审查整体方案
- 可以调整步骤顺序或跳过某些步骤
- 避免一步到位导致的失控

### 2.3 逐步执行

```
> 开始

📝 Step 1: 数据库设计
修改 prisma/schema.prisma，添加 Favorite 模型：

model Favorite {
  id        String   @id @default(cuid())
  userId    String
  articleId String
  createdAt DateTime @default(now())

  user      User     @relation(fields: [userId], references: [id])
  article   Article  @relation(fields: [articleId], references: [id])

  @@unique([userId, articleId])  // 防止重复收藏
}

应用此修改？[y] > y

🔧 执行：npx prisma migrate dev --name add-favorites
✅ 迁移成功

> 继续 Step 2

📝 Step 2: 后端 API
创建 src/server/routers/favorites.ts：

export const favoriteRouter = createTRPCRouter({
  add: protectedProcedure
    .input(z.object({ articleId: z.string() }))
    .mutation(async ({ ctx, input }) => {
      return ctx.db.favorite.create({
        data: { userId: ctx.session.userId, articleId: input.articleId }
      });
    }),

  remove: protectedProcedure
    .input(z.object({ articleId: z.string() }))
    .mutation(async ({ ctx, input }) => {
      return ctx.db.favorite.deleteMany({
        where: { userId: ctx.session.userId, articleId: input.articleId }
      });
    }),

  list: protectedProcedure
    .input(z.object({ page: z.number().default(1), limit: z.number().default(20) }))
    .query(async ({ ctx, input }) => {
      return ctx.db.favorite.findMany({
        where: { userId: ctx.session.userId },
        include: { article: true },
        skip: (input.page - 1) * input.limit,
        take: input.limit,
      });
    }),
});

应用此修改？[y] > y
✅ 已创建

[继续逐步执行 Step 3-5]
```

### 2.4 为什么功能开发不能只靠“一句大需求”

很多人第一次用 Codex 做功能开发时，最容易犯的错误就是把一整块需求一次性扔给模型，然后期待它直接产出可提交代码。

这样做的问题在于：

1. 需求边界容易漏
2. 修改范围容易失控
3. 你很难判断哪一步开始偏离了预期
4. 出现问题时，回退和定位成本都更高

所以“先规划、再分步执行、每步确认”并不是为了拖慢速度，而是为了把 AI 开发过程变成可审查、可回滚、可验证的工程流程。

## 3. TDD 模式：先测试后实现

### 3.1 让 Codex 先写测试

```
> 给收藏功能写单元测试（TDD 模式：先写测试，再实现功能）

📝 创建测试文件 src/server/routers/__tests__/favorites.test.ts：

describe('favoritesRouter', () => {
  it('should add a favorite', async () => {
    const result = await caller.add({ articleId: 'article-1' });
    expect(result.userId).toBe('user-1');
    expect(result.articleId).toBe('article-1');
  });

  it('should remove a favorite', async () => { ... });

  it('should list user favorites with pagination', async () => { ... });

  it('should not allow duplicate favorites', async () => { ... });

  it('should return 404 for non-existent article', async () => { ... });

  it('should only show own favorites', async () => { ... });
});

🔧 运行测试：
  ✗ should add a favorite — favoritRouter not found
  ✗ should remove a favorite — favoritRouter not found
  ...
  6 failed（预期，因为还没实现路由）
```

### 3.2 然后实现功能让测试通过

```
> 现在实现 favoritesRouter 让测试通过

📝 实现 src/server/routers/favorites.ts
[生成完整实现]

🔧 运行测试：
  ✅ should add a favorite
  ✅ should remove a favorite
  ✅ should list user favorites with pagination
  ✅ should not allow duplicate favorites
  ✅ should return 404 for non-existent article
  ✅ should only show own favorites

6 passed ✅
```

### 3.3 TDD 的好处（与 Codex 配合时）

| 好处 | 说明 |
|------|------|
| 需求验证 | 写测试前必须明确预期行为 |
| 质量保障 | Codex 生成的代码必须通过测试 |
| 重构安全 | 修改代码后跑测试即可验证 |
| 文档作用 | 测试即文档，描述了功能行为 |

### 3.4 TDD 和“先让 AI 写完再补测试”有什么本质区别

区别不在于测试文件最后有没有出现，而在于测试是在“约束实现”，还是在“事后解释实现”。

如果先让 Codex 把功能写完，再让它补测试，测试很容易只是迎合现有实现；而先写测试，本质上是在提前定义行为边界，让 Codex 必须往目标收敛。

对 AI 辅助开发来说，这点尤其关键，因为模型天然倾向于“尽快给出一个像样答案”，未必会主动替你补足边界条件。

## 4. 代码审查与迭代

### 4.1 让 Codex 审查自己的代码

```
> 审查刚才写的收藏功能代码，从以下维度：
> 1. 安全性  2. 性能  3. 错误处理  4. 代码风格

📋 审查结果：

✅ 优点：
- 使用了事务确保数据一致性（add 操作）
- 有适当的错误处理（404 检查）
- 遵循了项目的 tRPC 路由模式

⚠️ 建议（按优先级）：
1. 🔴 安全：list 接口没有验证 userId 归属
   → 添加 session.userId 校验
   
2. 🟡 性能：收藏列表没有分页优化
   → 添加 count 查询支持前端分页组件
   
3. 🟡 性能：N+1 查询问题
   → list 的 include: { article: true } 应该用 select
   
4. 🔵 风格：错误消息应该统一格式
   → 使用项目统一的 TRPCError 格式

> 修复第 1 和第 3 个问题

📝 修复中...
```

### 4.2 迭代优化

```
第一轮：功能实现（让测试通过）
第二轮：修复审查问题（安全 + 性能）
第三轮：边界情况处理（空列表、网络错误）
第四轮：最终检查（运行完整测试套件）

> 运行所有测试

🔧 npm test
  ✅ 42 tests passed
  ✅ 0 tests failed
  ✅ Coverage: 87%
```

## 5. 常见问题与技巧

### 5.1 需求描述技巧

```
技巧 1：提供上下文
  ❌ "加个搜索"
  ✅ "在文章列表页添加全文搜索，使用 Elasticsearch，
      需要支持标题和内容搜索，搜索结果高亮关键词"

技巧 2：提供约束
  ❌ "优化性能"
  ✅ "首页加载时间从 3s 降到 1s 以内，
      不能增加服务器成本"

技巧 3：提供示例
  ❌ "API 格式要对"
  ✅ "API 返回格式参考现有的 users.ts：
      { success: true, data: {...}, error: null }"
```

### 5.2 常见陷阱

| 陷阱 | 解决方案 |
|------|---------|
| 一步描述太多 | 拆分为小功能，逐步添加 |
| 不确认就接受 | 每步审查 diff 再确认 |
| 忽略测试 | 要求 Codex 先写测试 |
| 不看生成的代码 | 始终在 suggest 模式下审查 |
| 需求变更时从头开始 | 用 "在现有基础上修改..." |

### 5.3 一条更稳妥的人机分工原则

这一章最核心的，不是“让 Codex 多写代码”，而是建立清晰的人机分工：

| 角色 | 更适合负责的内容 |
|------|------|
| 人 | 定义目标、判断取舍、确认边界、最终验收 |
| Codex | 生成样板、补测试、执行修改、整理 diff、辅助审查 |

只要把“需求判断”和“最终责任”全部交给模型，功能开发质量通常会快速下降；但如果把模型限制在可验证的工程步骤里，它会非常高效。

## 6. 实践练习

### ⭐ 基础：用 Codex 开发一个简单功能

1. 选择一个简单功能（如：给 TODO 添加标签功能）
2. 用模板描述需求
3. 让 Codex 规划开发步骤
4. 逐步执行并审查

### ⭐⭐ 进阶：TDD 开发

1. 用 TDD 模式开发一个中等功能（如：评论系统）
2. 先写测试，再让 Codex 实现
3. 要求 Codex 审查代码并修复问题
4. 运行完整测试套件

### ⭐⭐⭐ 挑战：完整功能迭代

1. 开发一个复杂功能（如：文件上传 + 处理）
2. 分三轮迭代：功能→安全→性能
3. 每轮让 Codex 审查并修复
4. 最终测试覆盖率 > 80%

验收标准：
- 每轮迭代都有明确目标，而不是“顺手再改一点”
- 能提供每轮修改后的验证结果
- 最终除了功能可用，还能说明做过哪些风险控制

## 常见问题 Q&A

**Q1：为什么课程不建议一开始就用 `full-auto` 做功能开发？**

A：因为功能开发往往跨多个文件、涉及设计取舍和边界判断，一旦全自动放开，模型很容易在你还没审查方案时就把改动铺开。对大多数项目，先用 `suggest` 或 `auto-edit` 更稳妥。

**Q2：Codex 已经很会写代码了，为什么还要我先给开发计划？**

A：因为你需要先判断“方向对不对”，再判断“代码写得好不好”。没有计划，代码质量再高，也可能是在错误方向上高质量地产出。

**Q3：如果需求中途变化，是不是应该删除前面的结果重新来？**

A：通常没必要。更好的做法是明确告诉 Codex 哪些前提变了、哪些实现保留，让它在现有结果上调整。这样更符合真实项目迭代，而不是每次都从零生成。

**Q4：这章里最值得养成的一个习惯是什么？**

A：每完成一个步骤，就做一次“小闭环验证”：看 diff、跑测试、确认结果。这个习惯比任何提示词技巧都更能稳定提升 AI 辅助开发质量。

## 小结

| 要点 | 说明 |
|------|------|
| 需求描述 | 越具体越好：功能+技术+约束+示例 |
| 先规划后执行 | 让 Codex 出计划，人审查后再执行 |
| TDD 模式 | 先写测试→Codex 实现→测试通过 |
| 代码审查 | 让 Codex 从安全/性能/风格维度审查 |
| 逐步迭代 | 功能→修复→优化，每轮确认 |
