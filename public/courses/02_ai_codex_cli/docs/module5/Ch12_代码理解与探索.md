## 1. 读懂陌生仓库：自上而下方法论

### 1.1 为什么需要方法论

面对一个陌生的代码库，最常见的错误是直接打开源文件逐行阅读。这就像走进一个陌生城市不看地图就开始逛——效率极低。

**正确的方法**：自上而下，逐步深入。

```
Level 1: 项目概览 — 这个项目是做什么的？
Level 2: 架构理解 — 整体结构是怎样的？
Level 3: 核心模块 — 关键模块的职责是什么？
Level 4: 数据流 — 请求从入口到响应的完整路径？
Level 5: 具体代码 — 某个函数的实现细节？
```

### 1.5 Level 4：数据流追踪

```
> 一个用户创建看板任务时，请求从浏览器到数据库的完整路径是什么？

完整路径：

浏览器 → POST /api/trpc/task.create
  → tRPC Router: taskRouter.create()
    → 输入验证：zod schema 验证 title/content/assignee
    → 权限检查：checkPermission(userId, "task", "create")
      → 查询 Redis 缓存（权限数据）
      → 如果缓存未命中：查询数据库 role_permissions 表
    → 数据库操作：prisma.task.create()
      → 写入 tasks 表
      → 写入 task_history 表（操作记录）
    → 事件发布：redis.publish("task:created", taskData)
      → WebSocket 通知在线用户（实时协作）
    → 返回创建的任务数据
```

## 2. 代码审查：让 Codex 当你的 Reviewer

### 2.1 安全审查

```
> 审查 src/server/routers/auth.ts，找出潜在的安全问题，按严重程度排序

发现 3 个安全问题：

🔴 严重 — 密码比较使用了 === 而非 bcrypt.compare
  第 45 行：if (user.password === password)
  风险：时序攻击（timing attack），攻击者可通过响应时间推测密码
  修复：使用 bcrypt.compare(password, user.password)

🟡 中等 — JWT secret 硬编码在源码中
  第 12 行：const SECRET = "my-secret-key"
  风险：源码泄露即 secret 泄露
  修复：使用 process.env.JWT_SECRET

🟡 中等 — 缺少登录频率限制
  风险：暴力破解
  修复：添加 rate limiting（如 express-rate-limit）
```

### 2.2 性能审查

```
> 审查 src/server/routers/task.ts，找出性能问题

发现 2 个性能问题：

🔴 N+1 查询问题 — 第 67 行
  for (const task of tasks) {
    const assignee = await prisma.user.findUnique(...)
  }
  → 100 个任务 = 101 次数据库查询！
  修复：使用 prisma.task.findMany({ include: { assignee: true } })

🟡 缺少数据库索引
  task 表经常按 status + projectId 查询，但没有联合索引
  修复：添加 CREATE INDEX idx_task_status_project ON tasks(status, project_id)
```

### 2.3 代码质量审查

```
> 审查 src/components/TaskBoard.tsx，评价代码质量和可维护性

问题：
1. 组件过大（450 行），应拆分为 TaskColumn、TaskCard、TaskDialog
2. useEffect 依赖数组不完整（缺少 projectId）
3. 直接在组件中调用 API，应提取为自定义 hook useTasks()
4. 硬编码的魔术数字（60 * 60 * 24）应提取为常量

建议重构方案：
  TaskBoard.tsx → 编排层
  ├── TaskColumn.tsx → 列组件
  ├── TaskCard.tsx → 卡片组件
  └── hooks/useTasks.ts → 数据逻辑
```

### 2.4 审查的边界——什么该信，什么不该信

| Codex 审查擅长 | Codex 审查不擅长 |
|----------------|------------------|
| 常见安全模式（SQL 注入、XSS） | 业务逻辑正确性 |
| 代码风格和最佳实践 | 性能的绝对数值（需要实际测量） |
| 明显的 Bug 和错误处理 | 并发和竞态条件的微妙问题 |
| 依赖项的已知漏洞 | 特定框架版本的兼容性问题 |

**原则**：Codex 的审查是**第一道防线**，不是唯一防线。关键代码必须人工复核。

## 3. 解释复杂逻辑：追问技巧

### 3.1 逐层深入

```
# 第一问：概述
> 解释 src/lib/permission.ts 中的 checkPermission 函数

checkPermission 检查用户是否有权限执行某个操作。
它查询用户的角色列表，匹配权限规则，缓存结果。

# 第二问：追问细节
> 权限规则是如何匹配的？给我看具体的匹配逻辑

匹配逻辑在 matchRule 函数中：
1. 资源匹配：支持通配符（"task:*" 匹配 "task:create" 和 "task:delete"）
2. 动作匹配：精确匹配或正则匹配
3. 条件匹配：支持上下文条件（如 "只能操作自己创建的资源"）

# 第三问：追问边界情况
> 如果用户同时拥有 admin 角色和 viewer 角色，一个规则允许一个拒绝，怎么办？

权限是叠加的：任一角色允许即通过。
这是"白名单"模式——只要有一个角色允许，就允许。
如果需要更严格的控制，可以在 AGENTS.md 中指定为"黑名单"模式。
```

### 3.2 用图表理解

```
> 用 ASCII 图画出 checkPermission 的决策流程

checkPermission(userId, resource, action)
    │
    ├─ 1. 检查缓存（Redis）
    │    ├─ 命中 → 返回缓存结果
    │    └─ 未命中 → 继续
    │
    ├─ 2. 查询用户角色（DB）
    │    └─ roles = ["editor", "viewer"]
    │
    ├─ 3. 遍历角色的权限规则
    │    ├─ editor: task:* → ALLOW
    │    ├─ viewer: task:read → ALLOW
    │    └─ 无匹配规则 → DENY
    │
    ├─ 4. 合并结果（任一 ALLOW 即通过）
    │    └─ ALLOW
    │
    └─ 5. 写入缓存（TTL 5min）
         └─ 返回 ALLOW
```

### 3.3 用类比理解

```
> 用生活中的类比解释 RBAC 权限模型

RBAC 就像公司的门禁系统：
  用户 = 员工
  角色 = 部门（技术部、市场部、管理层）
  权限 = 门禁卡能刷开的门
  资源 = 会议室、办公室、档案室

  张三（技术部 + 项目组 A）：
    技术部的门禁卡 → 能进开发办公室、测试实验室
    项目组 A 的门禁卡 → 能进项目 A 的会议室
    合并：能进所有以上区域

  李四（管理层）：
    管理层的门禁卡 → 能进所有区域（超级权限）
```

## 4. 实战工作流

### 4.1 接手新项目的标准流程

```
步骤 1: 项目概览
> 这个项目是做什么的？技术栈是什么？

步骤 2: 架构理解
> 画出项目的架构图，标注各模块的职责和通信方式

步骤 3: 入口追踪
> 找到项目的主入口，追踪一个请求的完整生命周期

步骤 4: 测试理解
> 运行测试，分析测试覆盖了哪些核心逻辑

步骤 5: 数据模型
> 解释数据库模型之间的关系

步骤 6: 识别风险
> 标记出代码中最复杂、最容易出问题的部分
```

### 4.2 用 Git History 辅助理解

```
> 这个文件最近 10 次提交都改了什么？有什么趋势？

最近的改动趋势：
1. 最近 3 次提交都在修复同一个 Bug（#456）
   → 这个 Bug 可能比较顽固，根因可能没找到
2. 上个月有一次大的重构
   → 重构后引入了几个新问题
3. 原始作者是 Alice，最近由 Bob 在维护
   → 可以问 Alice 了解原始设计意图

> 为什么第 23 行用了一个奇怪的 hack？查看 git blame 和相关提交

第 23 行的 hack（// TODO: fix this later）是在 commit abc123 中引入的。
提交信息："临时修复生产环境的超时问题"
原因：数据库查询偶尔超时，用 setTimeout 做了重试
建议：应该用连接池和重试机制替代这个 hack
```

## 常见问题 Q&A

**Q1：Codex 的代码分析准确率有多高？**

A：取决于代码的复杂度和上下文。对常见模式（CRUD、认证、REST API）准确率 > 90%。对复杂业务逻辑、算法密集型代码准确率会下降。建议对关键逻辑进行验证。

**Q2：大型项目（1000+ 文件）Codex 能处理吗？**

A：Codex 可以读取项目中的任意文件，但不能一次性"看"所有文件。策略：
1. 先问目录结构，建立全局认知
2. 逐步深入具体模块
3. 用工具调用（read_file）按需读取文件

**Q3：Codex 会理解代码的注释吗？**

A：会。注释是重要的上下文信息。但如果注释和代码不一致，Codex 可能被误导。建议让 Codex 检查注释和代码的一致性。

**Q4：如何让 Codex 分析运行时行为？**

A：Codex 可以通过 `bash` 工具运行代码，观察运行时行为：
```
> 运行这个函数并打印中间变量的值
> 用断点调试的方式分析这个函数的执行流程
```
