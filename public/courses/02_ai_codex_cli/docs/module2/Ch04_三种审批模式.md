# Ch04：三种审批模式

> 理解 Codex CLI 的三种审批模式：Suggest、Auto-Edit 和 Full-Auto，学会按场景选择。

---

## 学习目标

- 理解三种审批模式的设计动机和信任边界
- 掌握每种模式的具体行为和安全边界
- 学会根据场景选择合适的审批模式
- 理解动态切换和配置持久化

---

## 1. 为什么需要审批模式

### 1.1 核心矛盾

```
AI Coding Agent 能执行命令、修改文件，这带来核心矛盾：

安全性：不能让 Agent 未经确认就删除文件、执行 rm -rf
效率性：每一步都确认会严重影响开发效率

三种审批模式就是不同的平衡点：

  Suggest   ←── 安全 ──────────── 效率 ──→ Full-Auto
  (最安全)                              (最高效)
```

### 1.2 信任层级

```
信任等级 0：不信任 → Suggest（全部手动确认）
信任等级 1：部分信任 → Auto-Edit（文件自动，命令手动）
信任等级 2：完全信任 → Full-Auto（全自动 + 沙箱保护）
```

---

## 2. Suggest 模式（默认，最安全）

### 2.1 行为

```bash
codex --approval suggest
# 或直接 codex（默认就是 suggest）
```

- Codex 分析代码并**建议修改**
- 所有文件修改以 diff 形式展示，需要 y/n 确认
- 命令执行需要用户确认
- 最安全，适合学习和关键代码

### 2.2 交互示例

```
> 重构 utils.ts 中的 formatDate 函数

📖 读取 src/utils.ts
📝 建议：将 formatDate 拆分为三个独立函数

--- a/src/utils.ts
+++ b/src/utils.ts
@@ -15,8 +15,18 @@
-export function formatDate(date: Date): string {
-  // ... 20 行混合逻辑
+export function formatDate(date: Date): string {
+  return `${getYear(date)}-${getMonth(date)}-${getDay(date)}`;
+}
+function getYear(date: Date): string { ... }
+function getMonth(date: Date): string { ... }
+function getDay(date: Date): string { ... }

应用此修改？[y/N/e(编辑)/q(退出)] > 
```

### 2.3 Suggest 模式的四个选项

```
y  — 应用修改
n  — 跳过此修改
e  — 编辑修改（在编辑器中调整 diff）
q  — 退出当前操作
a  — 全部应用（批量操作时）
```

## 3. Auto-Edit 模式（日常推荐）

### 3.1 行为

```bash
codex --approval auto-edit
```

- 文件修改**自动应用**，无需逐一确认
- 命令执行仍需用户确认（重要的安全边界）
- 修改后展示 diff 供回顾

### 3.2 交互示例

```
> 给所有 API 路由添加错误处理中间件

📝 修改 src/routes/users.ts      ✅ 已自动应用
📝 修改 src/routes/auth.ts       ✅ 已自动应用
📝 修改 src/routes/products.ts   ✅ 已自动应用

🔧 执行命令: pnpm build
运行此命令？[y/N] > y

✅ Build 成功
```

### 3.3 为什么命令仍需确认

```
文件修改（自动）：
  → 可以通过 git diff / git checkout 轻松回滚
  → 风险可控

命令执行（需确认）：
  → npm publish（不可逆）
  → rm -rf（不可逆）
  → 数据库迁移（可能不可逆）
  → 风险不可控，必须人工确认
```

---

## 4. Full-Auto 模式（CI/CD 适用）

### 4.1 行为

```bash
codex --approval full-auto
```

- 文件修改和命令执行**全部自动**
- 所有操作在沙箱中运行
- 不需要任何人工确认

### 4.2 安全保护

```
即使在 Full-Auto 模式下，仍有安全层：

Layer 1: 沙箱隔离
  → 文件系统限制在可写目录内
  → 网络访问可被禁用
  → 命令超时自动终止

Layer 2: 危险命令黑名单
  → rm -rf /     → 拦截
  → sudo         → 拦截
  → mkfs         → 拦截
  → curl | sh    → 拦截

Layer 3: AGENTS.md 约束
  → "不要修改 .env 文件"
  → "不要执行数据库迁移"
```

### 4.3 适用场景

```
✅ 适合：
  - CI/CD 自动修复 lint 错误
  - 自动生成测试
  - 非生产环境的批量重构
  - 个人实验项目

❌ 不适合：
  - 生产环境代码修改
  - 涉及敏感信息的操作
  - 数据库 schema 变更
  - 不熟悉的项目
```

## 5. 模式对比与选择

### 5.1 完整对比

| 维度 | Suggest | Auto-Edit | Full-Auto |
|------|---------|-----------|-----------|
| 文件修改 | 需确认 ✋ | 自动 ✅ | 自动 ✅ |
| 命令执行 | 需确认 ✋ | 需确认 ✋ | 自动 ✅ |
| 安全等级 | 最高 🟢 | 中等 🟡 | 最低 🔴 |
| 效率 | 最慢 | 中等 | 最快 |
| 回滚难度 | 无需回滚 | git checkout | 沙箱自动回收 |
| 推荐场景 | 学习/关键代码 | 日常开发 | CI/CD |

### 5.2 选择决策树

```
你在做什么？
├── 学习 Codex / 首次使用 → Suggest
├── 修改生产代码 → Suggest
├── 日常开发（熟悉项目）→ Auto-Edit
├── 大规模重构 → Auto-Edit（频繁 git commit）
├── CI/CD 自动化 → Full-Auto
└── 实验原型 → Full-Auto（关闭沙箱）
```

## 6. 切换方式

### 6.1 三种切换方式

```bash
# 方式 1：启动时指定
codex --approval suggest
codex --approval auto-edit
codex --approval full-auto

# 方式 2：REPL 中动态切换
> /approval auto-edit
审批模式已切换为: auto-edit

# 方式 3：配置文件持久化
# ~/.codex/config.toml
[approval]
mode = "auto-edit"
```

### 6.2 动态切换策略

```
推荐：在 REPL 中根据任务动态切换

开始一个新任务 → /approval suggest（观察 Codex 理解对不对）
确认理解正确 → /approval auto-edit（加速执行）
遇到关键修改 → /approval suggest（手动确认关键步骤）
```

## 7. 实践练习

### ⭐ 基础：体验三种模式

1. 分别用三种模式启动 Codex
2. 执行相同的任务（如"给 README 添加一行"）
3. 观察确认步骤的差异

### ⭐⭐ 进阶：动态切换

1. 用 Suggest 模式开始一个任务
2. 观察几轮后切换到 Auto-Edit
3. 遇到关键操作时切回 Suggest
4. 体验动态切换的灵活性

## 小结

| 模式 | 文件修改 | 命令执行 | 适用场景 |
|------|---------|---------|---------|
| Suggest | 需确认 | 需确认 | 学习、生产代码 |
| Auto-Edit | 自动 | 需确认 | 日常开发 |
| Full-Auto | 自动 | 自动 | CI/CD、实验 |
