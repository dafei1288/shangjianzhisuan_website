# Ch15：Plan→Work→Review 循环

> 理解 Claude Code 的核心工作模式：规划（Plan）、执行（Work）、审查（Review）三阶段循环。

---

## 学习目标

1. 理解三阶段循环的设计原理
2. 掌握规划模式（Planning Mode）的触发与执行
3. 分析执行模式的任务拆分与追踪
4. 理解代码审查代理的工作机制

---

## 1. 三阶段循环概述

### 1.1 为什么需要结构化工作流？

```
没有结构化工作流：
  用户："重构认证模块"
  Claude：直接开始改代码
  → 可能改错方向、遗漏边界情况、没有测试

有结构化工作流：
  Plan：分析需求 → 制定计划 → 用户确认
  Work：按计划执行 → 逐步实现 → 记录进度
  Review：代码审查 → 验证结果 → 反馈改进
```

### 1.2 循环模型

```
         ┌─────── Review ───────┐
         │  代码审查、测试验证    │
         │  发现问题？            │
         │  ├── 是 → 回到 Plan   │
         │  └── 否 → 完成 ✅     │
         │                      │
    Plan ←──────────────────────┘
    │ 需求分析
    │ 方案设计
    │ 任务拆分
    │ 用户确认
    │
    ▼
    Work
    │ 按计划执行
    │ 逐步实现
    │ 记录进度
    └──────────────→ Review
```

## 2. Plan（规划）阶段

### 2.1 触发条件

```
自动触发：
  - 任务复杂度高（涉及 3+ 文件修改）
  - 用户明确要求先规划
  - 检测到 writing-plans Skill

手动触发：
  - 用户说 "先做个计划" / "先规划一下"
  - 使用 /plan 命令
```

### 2.2 规划输出

```markdown
# 实施计划

## 目标
重构认证模块，从 session-based 迁移到 JWT。

## 任务分解

### Task 1: 创建 JWT 工具模块
- 文件: `src/lib/jwt.ts`
- 依赖: 无
- 预计: 30 分钟

### Task 2: 重构认证中间件
- 文件: `src/middleware/auth.ts`
- 依赖: Task 1
- 预计: 45 分钟

### Task 3: 更新登录/注册 API
- 文件: `src/api/auth.ts`
- 依赖: Task 1
- 预计: 30 分钟

### Task 4: 添加 Token 刷新机制
- 文件: `src/api/token.ts`
- 依赖: Task 2, Task 3
- 预计: 20 分钟

### Task 5: 更新测试
- 文件: `tests/auth.test.ts`
- 依赖: Task 2, Task 3, Task 4
- 预计: 40 分钟

## 风险
- JWT secret 管理需要更新环境变量
- 现有 session 可能需要过渡期
```

## 3. Work（执行）阶段

### 3.1 按计划执行

```
执行策略：

线性执行（有依赖）：
  Task1 → Task2 → Task3 → Task4 → Task5

并行执行（无依赖）：
  Task1 → Task2 ┐
               ├→ Task4 → Task5
         Task3 ┘
```

### 3.2 进度追踪

```
执行过程中的状态：

[✅] Task 1: JWT 工具模块 — 完成
[🔄] Task 2: 认证中间件 — 进行中
[⏳] Task 3: 登录/注册 API — 等待
[⏳] Task 4: Token 刷新 — 等待
[⏳] Task 5: 测试 — 等待

每个任务完成时更新状态，用户可以随时查看进度。
```

### 3.3 执行检查点

```
每个任务完成后执行：

1. 运行相关测试 → 确保没有回归
2. 检查文件变更 → 确认修改范围
3. 更新计划状态 → 标记已完成
4. 如果测试失败 → 回滚并报告问题
```

## 4. Review（审查）阶段

### 4.1 自动代码审查

```
所有任务完成后触发审查：

审查维度：
├── 功能正确性：是否实现了需求
├── 代码质量：风格、可读性、复杂度
├── 测试覆盖：是否添加了足够的测试
├── 安全性：是否引入安全隐患
├── 性能：是否影响性能
└── 兼容性：是否破坏现有功能
```

### 4.2 审查代理

```
可以派生一个 Sub-Agent 做代码审查：

审查 Agent 的 System Prompt：
  "你是一个严格的代码审查员。审查以下变更，
   报告问题按严重程度分类（Critical/Warning/Info），
   给出具体的修改建议。"

审查 Agent 的输入：
  - git diff（变更内容）
  - 需求描述（验证是否满足）
  - 项目 CLAUDE.md（检查是否符合规范）
```

### 4.3 审查结果处理

```
审查报告示例：

🔴 Critical (1):
  - src/lib/jwt.ts:15 — JWT secret 硬编码
    建议：使用环境变量 process.env.JWT_SECRET

🟡 Warning (2):
  - src/middleware/auth.ts:42 — 缺少 Token 过期检查
  - src/api/auth.ts:88 — 错误信息过于详细（泄露内部信息）

🟢 Info (1):
  - src/api/token.ts:20 — 可以用 refreshTokens Set 替代 Array

处理方式：
  Critical → 必须修复，回到 Work 阶段
  Warning → 建议修复，用户决定
  Info → 可忽略
```

## 5. 循环控制

### 5.1 循环次数限制

```
Plan → Work → Review → (发现问题) → Plan → Work → Review → ...

限制最大循环次数（如 3 次），防止无限循环。
超过限制后，将未解决的问题报告给用户。
```

### 5.2 用户介入点

```
用户可以在以下节点介入：

1. Plan 阶段后：确认/修改计划
2. Work 阶段中：查看进度，调整优先级
3. Review 阶段后：决定是否继续迭代
```

## 6. 课堂练习

1. **完整循环**：给 Claude Code 一个中等复杂度的任务（如添加日志中间件），观察完整的 Plan→Work→Review 循环。

2. **计划修改**：在 Plan 阶段后修改计划（添加/删除任务），观察 Claude 如何适应。

3. **审查失败**：故意在代码中留一个 bug，验证审查 Agent 是否能发现。

4. **循环控制**：设置最大循环次数为 1，验证超过后是否正确报告给用户。

5. **自定义审查标准**：编写一个 Skill，定义特定项目的代码审查标准。

---

## 小结

Plan→Work→Review 循环是 Claude Code 的核心工作模式，确保复杂任务被系统地分解、执行和验证。规划阶段避免盲目行动，执行阶段保持进度可见，审查阶段保证质量。

## 常见问题 Q&A

**Q1: 学这一章时，最容易把 Plan/Work/Review 循环 和什么概念混在一起？**
A: 最常见的混淆是把它当成单个函数或配置项来看。更准确的理解是：Plan/Work/Review 循环 是 Harness 中的一段职责边界，它要和模型推理、工具执行、上下文状态、权限控制一起协作，单独看代码片段很容易低估它的工程约束。

**Q2: 如果只做教学版实现，这一章哪些能力可以先简化？**
A: 可以先保留最小闭环：输入、处理、输出和错误返回。日志、缓存、并发优化、复杂权限策略和企业级可观测性可以后置，但接口边界要提前留清楚，否则后面扩展时会把核心流程改得很乱。

**Q3: 怎么判断自己真的理解了本章，而不是只看懂了代码？**
A: 用一个新场景复述执行链路：输入从哪里来、经过哪些对象、什么时候调用工具、失败如何传播、结果怎样回到上层。如果能画出这条链路，并指出至少一个边界条件，就说明已经理解了本章的核心。
