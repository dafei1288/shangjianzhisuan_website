## 1. 技能是什么

**技能（Skill）** 是一个自包含的能力包：一个 `SKILL.md` + 可选脚本/参考资料/资源，按需加载给模型使用。

```
对比三种定制手段:

提示模板 (ch10): 固定提示词，/名称 展开          ← 静态
技能 (ch13-15): SKILL.md + 脚本 + 参考文档        ← 能力包
扩展 (ch16-22): TypeScript 代码，注册工具/事件     ← 程序化
```

| 维度 | 技能 | 工具（扩展注册） |
|------|------|-----------------|
| 形态 | 文档 + 脚本 | 代码 |
| 加载 | 按需（渐进式披露） | 注册即常驻 |
| 能力 | 教模型"怎么做" | 替模型"直接做" |
| 典型 | PDF 处理、Web 搜索工作流 | 数据库查询 API |

> 💡 技能适合"流程型"能力（教模型一套步骤 + 调用脚本），扩展适合"原子型"能力（一个可调用工具）。实际项目常组合使用：技能描述工作流，里面调用扩展注册的工具。

## 2. SKILL.md 结构

技能目录：

```
my-skill/
├── SKILL.md              # 必填：frontmatter + 指令
├── scripts/              # 辅助脚本（模型会调用）
├── references/           # 详细文档（按需读取）
└── assets/               # 模板/数据文件
```

SKILL.md 本身：

````markdown
---
name: my-skill
description: 提取 PDF 中的表格并转成 CSV。处理 PDF 文档时使用。
---

# My Skill

## Setup
运行一次：cd /path/to/skill && npm install

## Usage
```bash
./scripts/extract.py input.pdf output.csv
```

## 步骤
1. 用脚本提取表格
2. 检查输出
3. 报告结果
````

### frontmatter 必填字段

| 字段 | 必填 | 说明 |
|------|------|------|
| `name` | ✅ | 小写字母/数字/连字符，≤64 字符 |
| `description` | ✅ | ≤1024 字符，**决定何时被加载**，必须具体 |
| `license` | ❌ | 许可证 |
| `allowed-tools` | ❌ | 预授权工具（实验性） |

> ⚠️ **description 是技能的生命线**：模型只靠描述判断"这个技能适不适合当前任务"。`"Helps with PDFs"` 会被无视，`"Extracts text and tables from PDF files, fills forms, merges multiple PDFs. Use when working with PDF documents."` 才会被调用。

## 3. 渐进式披露（Progressive Disclosure）

这是技能体系最核心的机制：

```
启动时:
  只有每个技能的 name + description 进入系统提示（几十 token）
  完整 SKILL.md 不加载

任务匹配时:
  模型判断"这个技能适用" → 用 read 读取完整 SKILL.md
  → 按指令执行，必要时读 references/ 里的细节
```

```
系统提示（常驻，精简）:
  可用技能：
  - pdf-tools: 提取PDF文本/表格/表单…处理PDF文档时使用
  - web-search: 多引擎搜索…需要实时信息时使用
  - code-review: 静态分析代码…审查PR时使用

（每个技能只占一行描述，而不是整份文档）
```

**价值**：
- 上下文精简：100 个技能也只有 100 行描述
- 按需加载：用到才读全文，模型上下文更干净
- 聚焦：模型读到的 SKILL.md 总是"当前任务相关"的完整指令

## 4. 技能的存放与发现

| 位置 | 作用域 |
|------|--------|
| `~/.pi/agent/skills/` | 全局 |
| `~/.agents/skills/` | 全局（Agent Skills 标准目录） |
| `.pi/skills/` | 项目（需信任） |
| `.agents/skills/`（cwd 向上） | 项目/仓库 |
| Pi 包 `skills/` | 随包分发（ch23） |
| settings.json `skills` 数组 | 显式指定目录 |

**发现规则**：
- `skills/` 下的根级 `.md` 文件 = 单个技能
- 含 `SKILL.md` 的目录 = 递归发现
- `~/.agents/skills/` 忽略根级 `.md`

**复用其他工具的技能**（settings.json）：

```json
{
  "skills": ["~/.claude/skills", "~/.codex/skills"]
}
```

> 💡 生态互通：Claude Code / Codex 的技能目录可以直接被 pi 复用——Agent Skills 是开放标准，技能文件不绑定工具。

## 5. 实战：技能 vs 工具选型决策

写扩展前先判断：这个需求该用技能还是工具？

```
需求来了
   │
   ├─ 是否“教模型一套步骤”？
   │     ├─ 是，且无需新代码能力 → 技能（SKILL.md + 脚本）
   │     └─ 是，但需要可靠的结构化执行 → 技能 + 内部调扩展工具
   │
   ├─ 是否“给模型一个新原子能力”？
   │     └─ 是 → 扩展工具（registerTool，ch17）
   │
   └─ 是否“需要在特定时机介入”？
         └─ 是 → 扩展事件（ch18）
```

**组合示例**：一个“发布流程”需求

```
技能 release/SKILL.md（流程：构建→测试→打 tag→推送）
  └─ 调用扩展工具 release_deploy（原子操作：真正执行部署）
```

> 💡 判断标准一句话：**流程用技能，原子能力用工具，时机介入用事件**。三者组合就是完整的扩展开发观。

## 7. 常见问题 Q&A

**Q1：模型不自动加载技能怎么办？**
A：两种原因：description 不具体（模型判断不适用），或需要强制使用。前者改 description；后者用 `/skill:name` 强制加载。

**Q2：技能和 AGENTS.md 有什么区别？**
A：AGENTS.md 常驻上下文（每次请求都带），适合"始终要遵守的约定"；技能按需加载，适合"特定任务才需要"的长流程。放错位置要么浪费 token，要么模型看不到。

**Q3：技能里的脚本会被自动执行吗？**
A：不会。技能只是指令 + 资源，执行与否由模型决定（它会用 bash 跑脚本）。这正是安全的边界——技能内容应视为"可被模型执行的代码"来审查。

**Q4：`/skill:name 参数` 怎么传参？**
A：参数追加在命令后，会作为 `User: <args>` 附到技能内容末尾。

## 8. 小结

| 要点 | 说明 |
|------|------|
| 技能是什么 | SKILL.md + 脚本/参考/资源 的自包含能力包 |
| 渐进式披露 | 描述常驻、指令按需 read，上下文精简 |
| description | 决定何时被加载，必须具体到触发场景 |
| 存放 | 全局/项目/包，兼容 `~/.claude/skills` 等外部目录 |
| 与扩展分工 | 技能=流程，扩展=原子工具，组合使用 |
