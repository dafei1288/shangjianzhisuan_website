## 1. 需求设计

我们做一个实战技能：**`git-commit`——生成符合规范的提交信息**。

**需求**：
- 模型拿到 `git diff`，生成 Conventional Commits 格式提交信息
- 需要判断提交类型（feat/fix/docs/refactor…）
- 输出格式固定、可复制

**为什么用技能而不是模板**（对比 ch10）：需要读取 diff、分析变更、按规则分类——是多步骤流程，适合技能；模板只适合静态提示。

---

## 2. 编写 SKILL.md

```
~/.pi/agent/skills/git-commit/
├── SKILL.md
└── scripts/
    └── analyze.py        # 分析 diff 的辅助脚本
```

````markdown
---
name: git-commit
description: 根据 git diff 生成 Conventional Commits 规范的提交信息。用户说"生成提交信息""commit message""提交"或准备 git commit 时使用。
---

# Git Commit Message Generator

## 目标
根据当前工作区的 git diff 生成一条规范提交信息。

## 步骤
1. 运行 `git diff --staged` 获取暂存区变更
   - 若无暂存变更，运行 `git diff` 并提示用户是否先 git add
2. 分析变更内容，判断类型：
   - feat: 新功能
   - fix: 修复 bug
   - docs: 文档
   - refactor: 重构（无行为变化）
   - test: 测试
   - chore: 杂项
3. 用脚本辅助：`./scripts/analyze.py <diff文件>`
4. 生成提交信息，格式：
   ```
   <type>(<scope>): <简短描述>

   <正文：为什么这样改，最多3行>
   ```

## 输出要求
- 标题 ≤50 字符
- 先给信息，再问"是否执行 git commit -m"

## 失败兜底
- 无任何变更时，直接告诉用户"工作区干净"并停止
````

### 要点解析

| 部分 | 作用 |
|------|------|
| description 具体化 | 含触发词 + 场景，模型能自动判断 |
| 步骤明确 | 先取 diff → 分类 → 生成 → 确认 |
| 脚本辅助 | 复杂分类逻辑交给代码 |
| 输出要求 | 固定格式，模型不易跑偏 |
| 失败兜底 | 空 diff 时的正确行为 |

## 3. 添加脚本

```python
# scripts/analyze.py
"""粗略统计 diff 变更分布，帮助判断 commit 类型"""
import sys, re
from collections import Counter

def main(path: str):
    with open(path, encoding="utf-8") as f:
        diff = f.read()
    # 统计增删行数
    added = len(re.findall(r"^\+[^+]", diff, re.M))
    removed = len(re.findall(r"^-[^-]", diff, re.M))
    # 判断是否含测试文件
    has_test = bool(re.search(r"test|spec", diff[:2000]))
    print(f"added={added} removed={removed} has_test={has_test}")

if __name__ == "__main__":
    main(sys.argv[1])
```

> ⚠️ 脚本路径：SKILL.md 里的相对路径以**技能目录**为基准（`./scripts/analyze.py`），模型会用 bash 从技能目录运行。

## 4. 添加参考资料（references/）

复杂技能把细节放到 references/，主 SKILL.md 保持精简（渐进式披露的二级）：

```
references/
└── conventional-commits.md   # 完整规范 + 各种示例
```

```markdown
<!-- references/conventional-commits.md -->
# Conventional Commits 速查

## 类型
- feat: 新功能（对应 MINOR 版本）
- fix: 修复（对应 PATCH）
- BREAKING CHANGE: 破坏性变更（对应 MAJOR）
…

## 示例
feat(auth): 增加刷新令牌机制
fix(cart): 修复数量为 0 时崩溃
…
```

SKILL.md 里引导读取：

```markdown
## 参考
拿不准类型或格式时，阅读 [references/conventional-commits.md](references/conventional-commits.md)
```

### 5.2 调试清单

```bash
[ ] pi list 或启动头部能看到技能
[ ] /skill:git-commit 能展开
[ ] 让模型"生成提交信息"能自动加载技能（验证 description）
[ ] 脚本路径正确（模型能运行 scripts/analyze.py）
[ ] 空 diff 时行为正确（失败兜底）
[ ] references/ 链接能读取
```

### 5.3 常见问题

| 症状 | 原因 | 修复 |
|------|------|------|
| 技能不自动加载 | description 不够具体 | 加触发词与场景 |
| 脚本找不到 | 相对路径基准错误 | 用 `./scripts/xxx` 相对技能目录 |
| 模型忽略步骤 | SKILL.md 太啰嗦 | 精简，细节移到 references/ |
| 与别的技能混淆 | name 冲突 | 检查 name 唯一性 |

## 7. 常见问题 Q&A

**Q1：技能里的脚本用什么语言写？**
A：任意（Python/Node/bash…），只要模型能用 bash 运行。注意写明运行前置（`## Setup` 里的安装步骤）。

**Q2：一个技能可以包含多个脚本吗？**
A：可以。SKILL.md 里按用途列出，模型按步骤选用。

**Q3：技能会被压缩影响吗？**
A：不影响。技能是文件，不在对话上下文里，压缩只影响对话消息。

**Q4：如何让技能"禁止"模型做某事？**
A：在 SKILL.md 明确写"禁止/不要"，并给替代做法。技能就是指令，模型会遵守（但对安全敏感操作仍需审查技能来源）。
