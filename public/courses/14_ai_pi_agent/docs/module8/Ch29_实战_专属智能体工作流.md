## 1. 工作流五件套

```
┌────────────────────────────────────────────────┐
│           专属智能体工作流（五层架构）             │
│                                                │
│  ① 宪法层  AGENTS.md        ← 常驻约束（ch09）   │
│  ② 能力层  Skills           ← 按需流程（ch13-15）│
│  ③ 快捷层  Prompt Templates ← 高频指令（ch10）   │
│  ④ 逻辑层  Extensions       ← 程序化能力（ch16-22）│
│  ⑤ 观察层  HUD / Widget     ← 状态可视化（ch20/22）│
└────────────────────────────────────────────────┘
```

| 层 | 手段 | 加载时机 | 职责 |
|----|------|---------|------|
| 宪法层 | AGENTS.md / SYSTEM.md | 每次请求 | 项目约定、角色、规范 |
| 能力层 | Skills | 按需 | 多步骤流程（文档处理、发布…） |
| 快捷层 | Prompt Templates | /名称 触发 | 高频固定指令 |
| 逻辑层 | Extensions | 启动常驻 | 工具、事件、命令、UI |
| 观察层 | HUD / Widget | 常驻 | 状态可视化 |

> 💡 分层原则：**越常驻的越精简**。AGENTS.md 只放"必须每次都遵守"的；流程细节下沉到技能；逻辑封装进扩展。

## 2. 落地案例：团队前端项目

以"前端团队 + 智能体协作"为例，搭建完整工作流。

### 2.1 宪法层：AGENTS.md

```markdown
# 项目智能体宪法

## 技术栈
- React 18 + TypeScript + Vite
- 包管理器: pnpm（禁止 npm install）
- 测试: Vitest（改动必须跑相关测试）

## 代码规范
- 组件用函数式 + hooks
- 样式用 CSS Modules（不用 tailwind）
- 状态管理用 zustand

## 工作流
- 新功能: 先写测试 → 再实现 → 跑测试
- 提交: 必须通过 lint + test
- 文档: 公共 API 改动必须更新 docs/

## 环境
- 本地服务: pnpm dev（端口 5173）
- 构建: pnpm build
```

### 2.2 能力层：技能库

```
.agents/skills/
├── component-gen/SKILL.md    # 按规范生成组件（模板+测试+样式）
├── pr-review/SKILL.md        # PR 审查流程（ch14 风格）
└── release/SKILL.md          # 发布流程（版本号/CHANGELOG/打 tag）
```

### 2.3 快捷层：提示模板

```
.prompts/
├── review.md      # /review — 审查改动
├── fix-bug.md     # /fix-bug — 复现-定位-修复-测试流程
└── weekly.md      # /weekly — 生成本周总结
```

### 2.4 逻辑层：扩展

```
.pi/extensions/
├── permission-gate.ts   # 危险命令确认门（ch21）
├── checkpoint.ts        # 回合自动 git 检查点（ch21）
└── team-report.ts       # 团队日报生成工具（ch17）
```

### 2.5 观察层：HUD

```jsonc
// .pi/pi-agent-hud.json（ch22）
{
  "enabled": ["model", "project", "git", "contextBar", "toolStats", "runningTools"]
}
```

## 3. 验证工作流

### 3.1 验收清单

```bash
[ ] 启动 pi：头部显示 AGENTS.md ✅ / skills ✅ / extensions ✅
[ ] 问"这个项目怎么跑" → 模型按 AGENTS.md 回答（pnpm dev）
[ ] 说"帮我加个组件" → 自动加载 component-gen 技能
[ ] /review → 展开审查模板
[ ] 让模型 rm -rf → 被确认门拦截
[ ] 干一轮活 → 检查点自动提交
[ ] HUD 显示上下文占用与工具统计
```

### 3.2 常见失败与修复

| 症状 | 原因 | 修复 |
|------|------|------|
| 模型不遵守规范 | AGENTS.md 太长/太泛 | 精简到 10 条内，具体可执行 |
| 技能不触发 | description 不具体 | 按 ch14 优化触发词 |
| 扩展不加载 | 项目信任未确认 | `/trust`（ch09） |
| 工作流被绕过 | 约束只写没执行 | 加检查点/拦截（ch21） |

## 4. 沉淀团队模板

把工作流变成"新项目一键复用"：

```
team-pi-template/
├── AGENTS.md              # 项目宪法模板（变量化）
├── .pi/settings.json      # 团队统一设置
├── .agents/skills/        # 团队技能库
├── .pi/extensions/        # 团队扩展（确认门/检查点/报表）
├── .pi/pi-agent-hud.json  # 统一 HUD 配置
└── README.md              # 使用说明
```

新项目初始化：

```bash
cp -r team-pi-template/ my-new-project/
# 按项目修改 AGENTS.md 的 {{变量}}，启动 pi 即获得全套能力
```

> 💡 更进一步：把模板做成 Pi 包或 skill（ch23 / ch30），`pi install` 即得——这就是"工作流产品化"。

## 6. 常见问题 Q&A

**Q1：五层都上会不会太重？**
A：会。原则：**先用宪法层（AGENTS.md）跑通，再按痛点逐层添加**。每加一层都问"没有它行不行"。

**Q2：团队里有人不用 pi 怎么办？**
A：AGENTS.md 是通用格式（Claude Code 也读 CLAUDE.md），技能是开放标准——非 pi 用户至少能受益于宪法与技能。

**Q3：工作流怎么迭代？**
A：把"模型又犯的错"当作改进信号：频繁出错 → 写进 AGENTS.md 或技能；反复手动的操作 → 做成模板或扩展。工作流是活的。

**Q4：安全怎么兜底？**
A：确认门 + 检查点 + 工具白名单（ch21）是三件套；给新成员/CI 用只读模式。
