## 1. 四种模式总览

```
┌────────────────────────────────────────────────────────────┐
│                   pi 的四种运行模式                          │
│                                                            │
│  interactive (默认)         print (-p / --print)           │
│  ┌──────────────────┐      ┌──────────────────────┐        │
│  │ 完整 TUI 交互界面  │      │ 提问→打印答案→退出      │        │
│  │ 编辑器/会话/命令    │      │ 适合脚本/管道/一次调用   │        │
│  └──────────────────┘      └──────────────────────┘        │
│                                                            │
│  json (--mode json)        rpc (--mode rpc)                │
│  ┌──────────────────┐      ┌──────────────────────┐        │
│  │ 所有事件输出为      │      │ stdin/stdout JSONL    │        │
│  │ JSON Lines         │      │ 进程级集成/跨语言      │        │
│  │ 适合调试/日志/订阅   │      │ 适合构建自定义客户端    │        │
│  └──────────────────┘      └──────────────────────┘        │
└────────────────────────────────────────────────────────────┘
```

| 模式 | 命令 | 交互方式 | 典型场景 |
|------|------|---------|---------|
| **interactive** | `pi` | TUI 全交互 | 日常开发（M1-M2 一直在用） |
| **print** | `pi -p "..."` | 一问一答 | 脚本、管道、快速验证 |
| **json** | `pi --mode json` | 事件流（JSON Lines） | 调试、日志、程序订阅事件 |
| **rpc** | `pi --mode rpc` | 命令/响应（JSONL） | 跨语言集成、自建客户端 |

## 2. print 模式：一键问答

```bash
# 基本用法
pi -p "总结当前目录的代码"

# 指定模型
pi -p --model gpt-4o "解释这段代码"

# 读取 stdin 管道
cat README.md | pi -p "总结这份文档"

# 携带文件参数（@ 前缀）
pi @package.json -p "这个包依赖了哪些东西？"

# 附加图片
pi -p @screenshot.png "这张图里有什么？"
```

**print 模式特性**：
- 输出最终答案后退出
- stdin 的内容合并进初始提示（管道友好）
- 无 TUI、无持久化（可加 `--name` 命名会话）

> 💡 万能管道：`git diff | pi -p "帮我 review 这些改动"` 是 print 模式最高频的用法。

## 3. JSON 模式：事件流

```bash
pi --mode json "列出当前目录"
```

输出所有事件为 JSON Lines（每行一个事件）：

```jsonl
{"type":"session_start", ...}
{"type":"agent_start", ...}
{"type":"turn_start", ...}
{"type":"message_update","assistantMessageEvent":{"type":"text_delta","delta":"我"}}
{"type":"message_update","assistantMessageEvent":{"type":"text_delta","delta":"在"}}
{"type":"tool_execution_start","toolName":"ls", ...}
{"type":"tool_execution_end","toolName":"ls", ...}
{"type":"message_end", ...}
{"type":"agent_end", ...}
```

**用途**：
- 调试：看清内部每一步（thinking / 工具 / token 用量）
- 日志：完整记录一次 agent 运行
- 订阅：程序按事件类型响应

```bash
# 只留工具调用事件（配合 jq）
pi --mode json "跑一下测试" | jq 'select(.type == "tool_execution_start")'
```

> 事件类型与 ch18 扩展事件的命名一致——JSON 模式就是"把扩展看到的事件流输出成数据"。

## 4. RPC 模式：进程集成

```bash
pi --mode rpc
```

通过 **stdin/stdout** 交换 JSONL 记录（命令 → 响应/事件），专为**非 Node.js** 或**进程隔离**场景设计：

```
客户端 ──命令──► pi (--mode rpc) ──事件/结果──► 客户端
  ▲                                                │
  └────────────────◄────────────────────────────────┘
```

**典型用法**：

```python
# 任意语言：子进程启动 pi RPC，发送命令，逐行读事件
import subprocess, json

p = subprocess.Popen(["pi", "--mode", "rpc"],
                     stdin=subprocess.PIPE, stdout=subprocess.PIPE, text=True)

def ask(text):
    p.stdin.write(json.dumps({"type": "prompt", "text": text}) + "\n")
    p.stdin.flush()
    # 逐行读 stdout，按事件类型处理…

ask("列出当前目录文件")
```

> ⚠️ 协议注意：RPC 用**严格 LF 分隔**的 JSONL，不要用 Node `readline` 这类会按 Unicode 分隔符切分的读取器。协议细节见 ch27。

**RPC vs JSON 模式**：

| 维度 | RPC | JSON |
|------|-----|------|
| 交互 | 命令/响应（有来有回） | 一次性输入，事件全部输出 |
| 用途 | 构建客户端、跨语言 | 观察、记录、调试 |
| 状态 | 可长驻进程 | 每次运行即结束 |

## 5. 模式选择决策表

| 你的需求 | 选择 |
|---------|------|
| 日常写代码 | interactive |
| 管道里跑一次 | print |
| 看内部发生了什么 | json |
| 自己写程序集成 agent | rpc（跨语言）/ SDK（Node.js，ch25-26） |
| 完整程序化能力（Node） | **SDK 优先**（类型安全、状态直读） |
| 其他语言 | RPC |

> 💡 关键建议：Node.js 项目优先用 SDK（ch25-26），它比 RPC 更安全、更贴近内部状态；只有跨语言或进程隔离需求才用 RPC。

## 7. 常见问题 Q&A

**Q1：print 模式会保存会话吗？**
A：默认不落盘（临时会话）。需要留档时加 `--name` 命名，或显式 `--session-dir` 指定存储目录。

**Q2：JSON 模式能交互吗？**
A：不能。它是“一次性输入 → 全部事件输出”。需要持续对话用 RPC 模式（有来有回）。

**Q3：RPC 模式安全吗？**
A：和任何子进程协议一样，取决于谁有 stdin/stdout 权限。生产用法：专用账号 + 最小权限 + 沙箱（ch21）。

**Q4：四种模式能混用吗？**
A：能。典型组合：RPC 长驻服务 + 内部 print 跑子任务 + JSON 做调试记录。它们共用同一套会话文件与配置。

**Q5：哪种模式最适合“把 pi 接入自己的产品”？**
A：Node.js 用 SDK（ch25-26，类型安全）；其他语言或要进程隔离用 RPC。两者共享同一内核，迁移成本低。
