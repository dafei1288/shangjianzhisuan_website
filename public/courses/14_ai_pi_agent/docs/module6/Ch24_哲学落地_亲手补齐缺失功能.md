## 2. 子代理：tmux 多实例

### 2.1 为什么 tmux

pi 官方推荐：**不要内置子代理，用 tmux 起多个 pi 实例**。

```
┌─────────────── tmux ───────────────┐
│ ┌──────────┐ ┌──────────┐          │
│ │ pi 主会话 │ │ pi 子代理  │  ── 后台  │
│ │ (你交互)   │ │ (独立任务) │  ...     │
│ └──────────┘ └──────────┘          │
└─────────────────────────────────────┘
```

**优势**：
- 完全隔离的上下文与会话
- 全可观测：随时切到子代理窗口看它在干嘛
- 可交互：子代理卡住可以直接介入
- 零实现成本：tmux 本身

### 2.2 实战：把任务委派给子代理

```bash
# 1. 新建子代理窗口，独立目录
tmux new-window -n "sub-task" -c ~/other-project

# 2. 在子代理窗口启动 pi 干活（后台）
tmux send-keys -t sub-task "pi --name '重构工具模块' '重构 src/tools，保持 API 不变'" Enter

# 3. 回到主会话继续自己的事
# 随时切过去看进度
tmux select-window -t sub-task
```

### 2.3 子代理的"委派协议"

简单委派不写代码，靠**明确的会话名 + 约定**：

```bash
pi --name "sub:提取数据" -p "读取 data.csv 输出统计 JSON 到 output/stats.json"
```

> 💡 进阶：用扩展 + tmux 自动编排多 agent（ch28 完整实现）。本章先用 tmux 手动建立心智模型。

## 3. MCP：为什么可能不需要

MCP（Model Context Protocol）是"模型动态获取工具/资源"的协议。pi 的理由：**构建带 README 的 CLI 工具（技能）通常更简单**。

```
MCP 方案:  实现 MCP server → 注册 → 模型通过协议调用
技能方案:  写 SKILL.md + CLI 脚本 → 模型按文档调用（ch14）
```

### 3.1 什么时候技能不够

| 场景 | 技能 | MCP |
|------|------|-----|
| 固定工作流 | ✅ 足够 | 杀鸡用牛刀 |
| 动态工具发现（运行时才知道有哪些工具） | ❌ | ✅ |
| 跨工具共享的协议标准 | 部分 | ✅ |
| 已有大量 MCP server 生态 | — | ✅ 复用 |

### 3.2 用扩展实现 MCP（思路）

```typescript
// 思路示意：把 MCP server 的工具桥接成 pi 工具
pi.on("resources_discover", async () => {
  const tools = await mcpClient.listTools();   // 连 MCP server
  for (const t of tools) {
    pi.registerTool({
      name: `mcp_${t.name}`,
      description: t.description,
      parameters: schemaFromJsonSchema(t.inputSchema),
      async execute(_id, params) {
        return await mcpClient.callTool(t.name, params);
      },
    });
  }
});
```

> 社区已有现成 MCP 扩展可安装（搜 pi MCP 扩展），不必自己造。理解原理即可。

## 4. 计划模式：plan 文件工作流

pi 说"计划写进文件"，而不是占一个 UI 模式：

```markdown
<!-- plan.md -->
# 重构 payment 模块

## 目标
用依赖注入替换单例，保持公共 API 不变

## 步骤
- [x] 1. 梳理现有单例依赖（已完成）
- [ ] 2. 定义接口 PaymentService
- [ ] 3. 重构调用方
- [ ] 4. 跑测试验证

## 风险
- 循环依赖风险在步骤 3
```

### 4.1 让 pi 按计划执行

```bash
# 对话式开始
pi "按 plan.md 执行，每完成一步更新勾选状态"
```

### 4.2 计划驱动的优势

- 计划是**文件**：可 review、可 diff、可归档
- 模型天然遵守：明确步骤清单
- 结合 git：每步一个检查点（ch21），随时回退

## 5. 内置待办：TODO.md

pi 认为"内置 to-dos 会混淆模型"（模型分不清 UI 状态与真实任务）。替代：TODO.md 文件。

```markdown
# TODO

## 当前迭代
- [ ] 完成认证流程重构 (blocked by: #12)
- [x] 修复登录超时

## 下周
- [ ] 性能优化
```

模型读文件 = 完全透明的任务状态；你可以手动改、脚本改、CI 改——任何工具都能操作它。

## 7. 常见问题 Q&A

**Q1：tmux 子代理和真正的多代理框架差在哪？**
A：差在"编排逻辑"（任务分解、结果聚合）。tmux 方案把编排留给人/扩展。需要自动化编排时用扩展实现（ch28 会给一个完整示例）。

**Q2：plan.md 会不会和压缩（ch08）冲突？**
A：不会。plan 是文件，不受上下文压缩影响——这正是"计划写进文件"优于"计划在对话里"的原因之一。

**Q3：MCP 真的不需要吗？**
A：需要时就用（扩展桥接或现成扩展）。pi 的立场是"不内置，但不阻止"——这恰恰是它的优势。

**Q4：TODO.md 谁更新？**
A：模型按你的指令更新、你手动更新、脚本更新都行。推荐每回合让模型"完成后勾选"，保持文件实时。

## 8. 小结

| 缺失 | 替代 | 一句话 |
|------|------|--------|
| 子代理 | tmux 多实例 | 完全隔离 + 全可观测 + 可交互 |
| MCP | 技能 / 扩展桥接 | 简单场景用技能，生态复用再上 MCP |
| 权限弹窗 | 确认门 / 容器 | 安全贴合你的环境（ch21） |
| 计划模式 | plan.md | 计划是可 review 的文件 |
| 内置待办 | TODO.md | 任务状态对所有工具透明 |
| 后台 bash | tmux | 可观测性优先 |
