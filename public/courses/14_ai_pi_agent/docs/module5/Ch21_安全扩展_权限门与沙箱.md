## 1. 威胁模型

智能体可能造成的破坏，按风险排序：

```
① 破坏性命令: rm -rf / sudo 危险操作 / git push --force
② 敏感文件写入: .env / auth.json / node_modules 被误改
③ 数据外泄: 读取密钥并发给外部
④ 供应链: 安装恶意 npm 包 / 执行来路不明的脚本
⑤ 会话劫持: 恶意仓库的 .pi 配置与技能（项目信任机制，ch09）
```

pi 的默认立场：**信任用户，工具全开**（四个内置工具）。安全由你按环境定制——这正是 pi 不内置权限弹窗的原因。

## 2. 危险命令确认门

最常用的第一道防线（ch20 已有雏形，这里完整化）：

```typescript
// permission-gate.ts
import { isToolCallEventType } from "@earendil-works/pi-coding-agent";

const DANGEROUS = [
  /^rm -rf/i,
  /sudo\s/,
  /git push --force/i,
  /:(){:|:&};:/,          // fork bomb 等
];

export default function (pi: ExtensionAPI) {
  pi.on("tool_call", async (event, ctx) => {
    if (!isToolCallEventType("bash", event)) return;

    const cmd = event.input.command;
    if (DANGEROUS.some((re) => re.test(cmd))) {
      const ok = await ctx.ui.confirm("危险命令", `允许执行吗？\n\n${cmd}`);
      if (!ok) return { block: true, reason: "Rejected by permission gate" };
    }
  });
}
```

**设计要点**：
- 正则黑名单 vs 白名单：黑名单简单但总有漏网；白名单（只允许显式命令）更安全但束缚
- 对 `!!` 用户命令同样生效（`user_bash` 事件，见 §5）
- 记录拦截日志，便于审计

## 3. 路径保护

阻止工具读写敏感路径：

```typescript
import { isToolCallEventType } from "@earendil-works/pi-coding-agent";

const PROTECTED = ["node_modules", ".env", "auth.json", ".git/"];

pi.on("tool_call", async (event, ctx) => {
  // 覆盖 write / edit / read / bash
  const path =
    isToolCallEventType("write", event) || isToolCallEventType("edit", event) || isToolCallEventType("read", event)
      ? event.input.path
      : isToolCallEventType("bash", event)
        ? extractPaths(event.input.command)
        : null;

  if (path && PROTECTED.some((p) => path.includes(p))) {
    const ok = await ctx.ui.confirm("路径保护", `操作被保护路径拦截: ${path}\n允许吗？`);
    if (!ok) return { block: true, reason: "Path protection" };
  }
});
```

> 💡 路径保护配合 ch17 的 `--tools` 白名单：只读模式（read/grep/find/ls）下模型根本无法调用写工具——双重保险。

## 4. 工具白名单

```bash
# 只读模式（审查代码最常用）
pi --tools read,grep,find,ls -p "审查当前目录"

# 显式白名单：只留内置 read/bash + 扩展工具 my_tool
pi --tools read,bash,my_tool

# 关掉全部内置，只用扩展工具
pi --no-builtin-tools
```

**运行时动态切换**（ch17 的 setActiveTools）：

```typescript
pi.registerCommand("lockdown", {
  handler: async (_a, ctx) => {
    pi.setActiveTools(["read", "grep", "find", "ls"]);
    ctx.ui.notify("Locked to read-only", "warning");
  },
});
```

## 5. 用户命令拦截（user_bash）

`!` / `!!` 是**用户**执行的命令，走 `user_bash` 事件（不是 tool_call）：

```typescript
import { createLocalBashOperations } from "@earendil-works/pi-coding-agent";

pi.on("user_bash", (event, ctx) => {
  // event.command / event.excludeFromContext(!!) / event.cwd

  // 包装内置 bash（如统一 source 环境）
  const local = createLocalBashOperations();
  return {
    operations: {
      exec(cmd, cwd, opts) {
        return local.exec(`source ~/.profile\n${cmd}`, cwd, opts);
      },
    },
  };

  // 或完全替换（如转发到 SSH 远程执行）
  // return { operations: remoteBashOps };
});
```

## 6. 容器化沙箱

需要强隔离时，把 pi 整个装进容器（官方 docs/containerization.md）：

| 方案 | 特点 |
|------|------|
| **Gondolin** | pi 官方推荐的沙箱（基于镜像启动） |
| **Docker** | 通用容器，自建镜像 |
| **OpenShell** | 壳级沙箱方案 |

```
宿主机 ──► 容器内运行 pi
            - 文件系统隔离（只能碰挂载卷）
            - 网络可限制
            - 权限最小化
```

> 💡 取舍：容器化最安全但体验有损（终端交互、git 凭证传递）；命令确认门 + 白名单轻量够用。建议：个人机器用确认门，多人/CI 用容器。

## 7. git 检查点（自动备份）

把"试错"变成"可回滚"：

```typescript
// checkpoint.ts —— 每个回合结束自动提交
pi.on("turn_end", async (_e, ctx) => {
  const { execSync } = await import("node:child_process");
  try {
    execSync("git add -A && git commit -m 'pi-checkpoint' --no-verify", { stdio: "pipe" });
  } catch { /* 无变更或非 git 仓库 */ }
});
```

**升级版**（stash 恢复）：

```typescript
// 开始前 stash 工作区，结束时恢复，失败可回退
pi.on("agent_start", () => { execSync("git stash push -m pi-before"); });
pi.on("agent_end", () => { execSync("git stash pop"); });
```

> ⚠️ 检查点会污染提交历史（每回合一个 commit）。生产用法：stash 方案 或 独立分支 + 完成后 squash。

## 9. 常见问题 Q&A

**Q1：确认门会不会太烦？**
A：会。解决方案：黑白名单分层（普通命令放行、危险命令确认、极危险直接阻断）、按项目记忆决定（trust 机制扩展）。

**Q2：tool_call 里改了参数，还会重新校验吗？**
A：不会（ch18 讲过）。所以路径保护等检查务必在改写后、执行前做——顺序：先检查再决定是否改写。

**Q3：扩展本身被恶意修改怎么办？**
A：扩展有完整系统权限（这是 pi 的明确设计）。保护手段：审查来源、只装信任包、项目信任机制、容器隔离。

**Q4：有现成的安全扩展吗？**
A：社区有（GitHub 搜 pi extension security）；也可以基于本章代码自己造。记住：**安全是场景化的**，抄来的策略未必适合你的环境。
