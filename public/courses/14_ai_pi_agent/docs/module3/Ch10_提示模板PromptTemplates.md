# Ch10：提示模板 Prompt Templates

> 高频指令的"快捷键"：把常用的长提示词存成模板文件，`/模板名` 一键展开，支持 `{{变量}}` 参数，还能打包分享。

![Ch10 提示模板题图](../../visuals/chapters/ch10-hero.png)

## 学习目标

学完本章后，你将能够：

1. 理解提示模板的机制：`/名称` 展开为提示内容
2. 创建带 `{{变量}}` 参数的模板
3. 在正确的位置存放模板（全局 / 项目 / 包）
4. 设计自己的高频指令模板库

## 1. 什么是提示模板

提示模板是一个 **Markdown 文件**，内容是"可复用的提示词"。输入 `/模板名` 时，pi 把文件内容展开进输入框。

```
典型痛点:
每次都要打: "Review this code for bugs, security issues, and performance problems. Focus on: 认证逻辑"
用模板后:  /review 认证逻辑
```

```markdown
<!-- ~/.pi/agent/prompts/review.md -->
Review this code for bugs, security issues, and performance problems.
Focus on: {{focus}}
```

展开效果：

```
/review 认证逻辑
→ 输入框变为: Review this code for bugs... Focus on: 认证逻辑
```

> 💡 模板的价值：把"好的提问方式"沉淀成可复用资产，团队/个人共享，让每一次提问质量一致。

## 2. 模板语法

### 2.1 基本结构

```markdown
# 模板名（文件名即模板名，如 review.md → /review）

## 系统提示补充（可选）
写一些希望模型始终遵守的约束…

## 正文
你要执行的任务描述，可用 {{变量}} 占位

## 输出要求
1. 输出格式…
2. 必须包含…
```

### 2.2 变量

| 写法 | 说明 |
|------|------|
| `{{focus}}` | 位置参数，`/模板名 值` 传参 |
| `{{a}}` `{{b}}` | 多个变量，按顺序传入 |

```markdown
<!-- review.md -->
按 {{style}} 风格 review 这段代码，重点关注 {{area}}
```

```bash
/review 简洁 性能
# → 按 简洁 风格 review 这段代码，重点关注 性能
```

## 3. 存放位置与优先级

| 位置 | 作用域 | 说明 |
|------|--------|------|
| `~/.pi/agent/prompts/` | 全局 | 所有项目可用 |
| `.pi/prompts/` | 项目 | 团队共享 |
| Pi 包内 `prompts/` | 包 | 随包分发（ch23） |

命名规则：**文件名即模板名**（`review.md` → `/review`）。子目录同样生效：

```
~/.pi/agent/prompts/
├── review.md          # /review
├── fix-bug.md         # /fix-bug
└── code/
    └── explain.md     # /code/explain（斜杠嵌套）
```

## 4. 模板库设计建议

### 4.1 我的高频模板清单（示例）

| 模板名 | 用途 |
|--------|------|
| `/review` | 代码审查（参数：关注点） |
| `/explain` | 讲清楚某段代码 |
| `/commit` | 生成规范 commit message |
| `/refactor` | 重构（参数：目标） |
| `/docs` | 生成/更新文档 |
| `/test` | 生成测试用例 |

### 4.2 模板质量要点

1. **具体**：明确任务 + 约束 + 输出格式，比"帮我看看"强 10 倍
2. **带上下文**：说明项目背景，模型少猜
3. **给例子**：few-shot 示例显著提升输出质量
4. **可变量化**：把会变的部分设计成 `{{变量}}`，不变的部分写死

```markdown
<!-- commit.md -->
生成一条符合 Conventional Commits 的提交信息。

要求：
- 类型用 feat/fix/docs/refactor/test/chore
- 正文描述"为什么"而非"做了什么"
- 不超过 3 行

变更内容：
{{changes}}
```

## 5. 实战场景：审查模板的完整示例

把前面知识点组合成一个真实模板（review）：

```markdown
<!-- ~/.pi/agent/prompts/review.md -->
# 代码审查

你是一位资深代码审查者。请审查 {{focus}} 相关改动。

## 审查维度
1. 正确性：边界条件、错误处理
2. 安全：注入、敏感信息泄露
3. 性能：明显热点、重复计算
4. 可维护性：命名、职责、测试

## 输出格式
- 问题清单（严重度 P0-P3 排序）
- 每项附：位置 + 问题 + 修复建议（带代码）
- 无问题时明确说“通过”

## 约束
- 不修改任何文件，只输出审查结论
- 不确定的地方标注 [待确认]
```

使用效果：

```bash
/review 登录认证
# → 展开为完整审查指令，focus = 登录认证
```

> 💡 注意：把“输出格式”和“约束”写进模板，审查质量会稳定得多——这就是模板 vs 口头提问的差距。

## 7. 常见问题 Q&A

**Q1：模板和技能（Skills）有什么区别？**
A：模板是"固定提示词"（每次展开相同内容）；技能是"能力包"（SKILL.md + 脚本 + 参考资料，按需加载，ch13-15）。简单复用用模板，复杂流程用技能。

**Q2：模板里能引用文件内容吗？**
A：模板本身是静态文本。动态内容通过 `{{变量}}` 传入；需要读取文件的场景，配合 `@文件` 或让模型自己 read。

**Q3：`/模板名 参数` 中间有空格怎么处理？**
A：参数以空格分隔传给多个 `{{变量}}`；模板名与参数之间用空格。变量顺序即出现顺序。

**Q4：模板会不会被自动加载占用上下文？**
A：不会。模板只在 `/名称` 展开时才进入输入，不常驻上下文——这也是它和 AGENTS.md 的本质区别。

## 8. 小结

| 要点 | 说明 |
|------|------|
| 机制 | `/名称` 展开 Markdown 模板内容进输入框 |
| 变量 | `{{name}}` 位置参数，`/模板名 值` 传入 |
| 位置 | 全局 `~/.pi/agent/prompts/`、项目 `.pi/prompts/`、包内 |
| 命名 | 文件名即模板名，支持子目录嵌套 |
| 设计 | 具体 + 带约束 + 给例子 + 变量化，沉淀高频指令 |
