# Ch29: 类型系统扩展方向

## 学习目标
- 理解静态类型与动态类型的本质区别与各自权衡
- 掌握类型推断的基本原理（Hindley-Milner 简介）
- 能够为 JimLang 设计可选类型注解的语法与检查器结构

## 核心概念

**动态类型**（JimLang 当前状态）：变量没有固定类型，类型在运行时确定。灵活，但错误只能在运行时发现。

**静态类型**：变量在编译期绑定类型，类型错误在运行前就能发现。代码更安全，IDE 支持更好，但编写时需要更多标注。

**渐进类型（Gradual Typing）**是两者的折中：允许部分代码有类型注解，部分代码保持动态。TypeScript 对 JavaScript 的扩展就是典型案例。JimLang 可以走同样的路线。

**类型推断**：不需要程序员标注所有类型，编译器自动推导。例如：

```
var x = 42;        // 推断 x: Int
var y = x + 1.0;   // 推断 y: Float（Int + Float → Float）
```

Hindley-Milner 算法是函数式语言（ML、Haskell）类型推断的理论基础，核心是**合一（Unification）**：将类型变量与具体类型绑定，传播约束直到所有类型确定或发现矛盾。

**为 JimLang 添加可选类型注解的语法设计**：

```
// 无注解（保持动态）
fun add(a, b) { return a + b; }

// 有注解（启用类型检查）
fun add(a: Int, b: Int): Int { return a + b; }

// 变量注解
var name: String = "Jim";
var count: Int = 0;

// 可空类型
var node: Node? = nil;
```

**类型检查器的位置**：在 Parser 生成 AST 之后、Compiler/Interpreter 执行之前，插入一个 `TypeChecker` Pass。

## 关键代码

```java
// 类型表示
public sealed interface Type permits Type.Int, Type.Float,
        Type.Bool, Type.Str, Type.Nil, Type.Fun, Type.Any, Type.Nullable {
    record Int() implements Type {}
    record Float() implements Type {}
    record Bool() implements Type {}
    record Str() implements Type {}
    record Nil() implements Type {}
    record Any() implements Type {}  // 动态类型，跳过检查
    record Nullable(Type inner) implements Type {}
    record Fun(List<Type> params, Type ret) implements Type {}
}

// 类型环境：变量名 → 类型
public class TypeEnv {
    private final Map<String, Type> bindings = new HashMap<>();
    private final TypeEnv parent;

    public TypeEnv(TypeEnv parent) { this.parent = parent; }

    public void define(String name, Type type) {
        bindings.put(name, type);
    }

    public Type lookup(String name) {
        if (bindings.containsKey(name)) return bindings.get(name);
        if (parent != null) return parent.lookup(name);
        throw new TypeError("Undefined variable: " + name);
    }
}

// 类型检查器（简化版）
public class TypeChecker implements Expr.Visitor<Type> {
    private TypeEnv env = new TypeEnv(null);

    @Override
    public Type visitBinaryExpr(Expr.Binary expr) {
        Type left = expr.left.accept(this);
        Type right = expr.right.accept(this);

        // Any 类型跳过检查（动态部分）
        if (left instanceof Type.Any || right instanceof Type.Any) {
            return new Type.Any();
        }

        return switch (expr.operator.type()) {
            case PLUS, MINUS, STAR, SLASH -> {
                if (left instanceof Type.Int && right instanceof Type.Int)
                    yield new Type.Int();
                if ((left instanceof Type.Float || left instanceof Type.Int)
                        && (right instanceof Type.Float || right instanceof Type.Int))
                    yield new Type.Float();
                throw new TypeError("Arithmetic requires numeric types, got "
                        + left + " and " + right);
            }
            case EQUAL_EQUAL, BANG_EQUAL -> new Type.Bool();
            default -> throw new TypeError("Unknown operator");
        };
    }

    @Override
    public Type visitCallExpr(Expr.Call expr) {
        Type calleeType = expr.callee.accept(this);
        if (calleeType instanceof Type.Any) return new Type.Any();
        if (!(calleeType instanceof Type.Fun fun)) {
            throw new TypeError("Cannot call non-function type: " + calleeType);
        }
        // 检查参数数量与类型
        if (expr.args.size() != fun.params().size()) {
            throw new TypeError("Expected " + fun.params().size()
                    + " args, got " + expr.args.size());
        }
        for (int i = 0; i < expr.args.size(); i++) {
            Type argType = expr.args.get(i).accept(this);
            checkAssignable(fun.params().get(i), argType, "argument " + i);
        }
        return fun.ret();
    }

    private void checkAssignable(Type expected, Type actual, String context) {
        if (expected instanceof Type.Any || actual instanceof Type.Any) return;
        if (!expected.equals(actual)) {
            throw new TypeError("Type mismatch in " + context
                    + ": expected " + expected + ", got " + actual);
        }
    }
}
```

## 常见问题 Q&A

**Q1: 渐进类型系统有什么缺点？**

A: 声音性（soundness）难以保证。当动态类型和静态类型混合时，运行时仍需类型检查。TypeScript 就是这样的——它不保证运行时类型安全。

**Q2: 为什么不让 JimLang 完全静态类型？**

A: 完全静态类型需要大量类型注解，增加用户负担。渐进类型允许从动态开始，按需添加类型注解，更友好。

**Q3: 类型检查能发现所有 bug 吗？**

A: 不能。类型检查只能发现类型相关的错误。逻辑错误、数组越界、空指针等仍需测试。类型检查是安全网，不是银弹。

## 小结

| 要点 | 说明 |
|------|------|
| 动态 vs 静态 | 灵活 vs 安全，各有权衡 |
| 渐进类型 | 折中方案：部分动态 + 部分静态 |
| 类型推断 | 编译器自动推导类型，减少标注 |
| TypeChecker | AST 遍历器，验证类型约束 |
| 声音性 | 渐进类型难以完全保证 |
