# Ch28: 性能测试与优化

## 学习目标
- 掌握基准测试的正确方法，避免常见的测量陷阱
- 理解常量折叠与内联缓存两种经典优化技术
- 了解 JIT 编译的基本原理与适用场景

## 核心概念

**基准测试**不能简单地用 `System.nanoTime()` 包裹一次调用。JVM 有 JIT 热身期，需要先运行若干次让代码"热起来"，再测量稳定后的耗时。推荐使用 JMH（Java Microbenchmark Harness）框架。

以 `fib(35)` 为基准，典型结果：

| 模式 | 耗时（参考值） |
|------|--------------|
| 解释器（树遍历） | ~2000 ms |
| 字节码 VM | ~400 ms |
| 优化后 VM | ~150 ms |

**常量折叠（Constant Folding）**：在编译期计算常量表达式，避免运行时重复计算。

```
// 源码
var x = 2 * 3 + 1;
// 编译期折叠后等价于
var x = 7;
```

在 AST 优化阶段遍历节点，若两个子节点都是字面量，直接替换为计算结果。

**内联缓存（Inline Cache）**：动态语言中方法查找开销大（每次都要在类的方法表中搜索）。内联缓存在调用点记录上次查找的结果，下次调用时先检查类型是否相同，相同则直接使用缓存的方法地址，跳过查找。

**性能瓶颈分析**：通常瓶颈在于：
1. 方法查找（OOP 场景）→ 内联缓存
2. 装箱/拆箱（数值运算）→ 值类型优化
3. 内存分配频率过高 → 对象池 / 减少临时对象

**JIT 编译简介**：解释执行字节码仍有分发开销。JIT 在运行时将热点字节码直接编译为机器码，消除解释开销。实现 JIT 需要代码生成（如使用 ASM 库生成 JVM 字节码，或使用 GraalVM Truffle 框架）。

## 关键代码

```java
// 常量折叠：在编译器的 AST 优化 Pass 中实现
public class ConstantFolder implements Expr.Visitor<Expr> {

    @Override
    public Expr visitBinaryExpr(Expr.Binary expr) {
        Expr left = expr.left.accept(this);
        Expr right = expr.right.accept(this);

        // 两个操作数都是数字字面量，直接折叠
        if (left instanceof Expr.Literal(Double l)
                && right instanceof Expr.Literal(Double r)) {
            double result = switch (expr.operator.type()) {
                case PLUS  -> l + r;
                case MINUS -> l - r;
                case STAR  -> l * r;
                case SLASH -> r != 0 ? l / r : Double.NaN;
                default    -> Double.NaN;
            };
            if (!Double.isNaN(result)) {
                return new Expr.Literal(result);
            }
        }
        return new Expr.Binary(left, expr.operator, right);
    }
}

// 内联缓存：在方法调用指令中缓存上次查找结果
public class InlineCache {
    private JimClass cachedClass = null;
    private JimMethod cachedMethod = null;

    public JimMethod lookup(JimInstance instance, String methodName) {
        JimClass klass = instance.getKlass();
        if (klass == cachedClass) {
            return cachedMethod;  // 缓存命中，直接返回
        }
        // 缓存未命中，执行完整查找
        JimMethod method = klass.findMethod(methodName);
        cachedClass = klass;
        cachedMethod = method;
        return method;
    }
}

// 简单基准测试（生产环境建议用 JMH）
public class Benchmark {
    public static void main(String[] args) {
        String fibSource = "fun fib(n) { if (n < 2) return n; return fib(n-1)+fib(n-2); } fib(35);";

        // 热身
        for (int i = 0; i < 3; i++) runVM(fibSource);

        // 正式测量（取 5 次平均）
        long total = 0;
        for (int i = 0; i < 5; i++) {
            long start = System.nanoTime();
            runVM(fibSource);
            total += System.nanoTime() - start;
        }
        System.out.printf("VM fib(35) 平均耗时: %.1f ms%n", total / 5.0 / 1e6);
    }
}
```

### 性能优化速查表

| 优化技术 | 阶段 | 效果 | 实现难度 |
|---------|------|------|----------|
| 常量折叠 | 编译期 | 中 | 低 |
| 死代码消除 | 编译期 | 低 | 低 |
| 内联缓存 | 运行时 | 高 | 中 |
| 尾调用优化 | 编译期 | 高 | 中 |
| JIT 编译 | 运行时 | 极高 | 极高 |

**优化原则**：先 Profile（找到瓶颈），再 Optimize（针对性优化），最后 Verify（确认效果）。

## 常见问题 Q&A

**Q1: 为什么不直接用 JIT？**

A: JIT 实现复杂度极高（需要代码生成、热点检测、逆优化等）。对于教学语言，常量折叠和内联缓存已经能带来显著的性能提升。

**Q2: 常量折叠能优化多少？**

A: 取决于代码中常量表达式的比例。科学计算程序可能 30% 的表达式可折叠，业务代码可能不到 5%。

**Q3: 怎么确认优化是否有效？**

A: 反汇编优化前后的字节码，对比指令数量。然后用基准测试确认性能提升。两者缺一不可。
