## 1. 为什么需要结构化错误处理

### 1.1 返回值方式的局限

最简单的错误处理是返回特殊值：

```
fun divide(a, b) {
    if (b == 0) return nil;  // 用 nil 表示错误
    return a / b;
}

var result = divide(10, 0);
if (result == nil) {
    print "Error!";
}
```

问题：
- 调用方必须每次检查返回值，容易遗漏
- 嵌套调用时错误要一层层手动传递
- 无法区分不同类型的错误

### 1.2 异常机制的优势

```
fun divide(a, b) {
    if (b == 0) throw "division by zero";
    return a / b;
}

try {
    var result = divide(10, 0);
    print result;  // 不会执行
} catch (e) {
    print "Caught: " + str(e);  // Caught: division by zero
}
```

优势：
- 错误自动沿调用栈向上冒泡，无需手动传递
- 业务逻辑和错误处理代码分离
- 错误载荷可以是任意 Value，灵活表达错误信息

## 2. 核心概念

**实现原理**：`throw` 语句在 Java 层抛出一个 `JimError`（继承自 `RuntimeException`），它携带一个 `Value` 作为错误载荷。这个异常会沿 Java 调用栈向上冒泡，直到被某个 `try/catch` 对应的 Java `catch` 块捕获。若一直未被捕获，则到达解释器顶层，打印错误信息并终止。

这种实现方式的优雅之处在于：**错误传播完全借助 Java 的异常机制**，不需要在解释器每一层手动检查返回值。

### 2.1 错误传播路径

```
Jim 代码                  Java 层
─────────────────────────────────────────
fun a() { throw "err"; }  → throw new JimError("err")
fun b() { a(); }          → b() 调用 a()，JimError 冒泡
fun c() { b(); }          → c() 调用 b()，JimError 继续冒泡

try { c(); }              → Java try 块
catch (e) { ... }         → Java catch (JimError e) 拦截
```

## 3. 关键代码

### 3.1 JimError 定义

```java
// JimError：Jim 语言的运行时错误载体
public class JimError extends RuntimeException {
    public final Value value;

    public JimError(Value value) {
        super(null, null, true, false); // 禁用栈跟踪，提升性能
        this.value = value;
    }
}
```

为什么禁用栈跟踪？`fillInStackTrace()` 是一个昂贵操作（需要遍历 Java 调用栈），而 JimError 的栈信息由解释器自己维护，不需要 Java 层的栈跟踪。

### 3.2 throw 语句

```java
// 解释器处理 throw 语句
@Override
public Void visitThrowStmt(Stmt.Throw stmt) {
    Value value = evaluate(stmt.value);
    throw new JimError(value);
}
```

### 3.3 try/catch 语句

```java
// 解释器处理 try/catch 语句
@Override
public Void visitTryCatchStmt(Stmt.TryCatch stmt) {
    try {
        executeBlock(stmt.tryBlock, new Environment(environment));
    } catch (JimError error) {
        // 创建新环境，将捕获的错误绑定到 catch 变量
        Environment catchEnv = new Environment(environment);
        catchEnv.define(stmt.catchVar.lexeme, error.value);
        executeBlock(stmt.catchBlock, catchEnv);
    }
    return null;
}
```

## 4. 高级用法

### 4.1 自定义错误对象

```
class AppError {
    init(code, message) {
        this.code = code;
        this.message = message;
    }

    toString() {
        return "[" + str(this.code) + "] " + this.message;
    }
}

fun validateAge(age) {
    if (age < 0) throw AppError(400, "年龄不能为负数");
    if (age > 150) throw AppError(400, "年龄不合理");
    return true;
}

try {
    validateAge(-5);
} catch (e) {
    print "错误码: " + str(e.code);    // 400
    print "错误信息: " + str(e.message); // 年龄不能为负数
}
```

### 4.2 嵌套 try/catch

```
fun riskyOperation() {
    try {
        // 内层可能抛出错误
        var result = 10 / 0;
    } catch (e) {
        print "内层捕获: " + str(e);
        throw "包装后重新抛出: " + str(e);  // 重新抛出
    }
}

try {
    riskyOperation();
} catch (e) {
    print "外层捕获: " + str(e);
    // 内层捕获: division by zero
    // 外层捕获: 包装后重新抛出: division by zero
}
```

### 4.3 错误冒泡穿过函数调用

```
fun level3() { throw "来自 level3"; }
fun level2() { level3(); }
fun level1() { level2(); }

// 错误从 level3 → level2 → level1 → 这里被捕获
try {
    level1();
} catch (e) {
    print e;  // 来自 level3
}
// 关键：level2 和 level1 完全不需要知道错误处理的存在
```

## 5. 设计讨论：为什么没有 finally

许多语言（Java、JavaScript）有 `finally` 块，无论是否抛出异常都会执行。JimLang 暂不实现 finally，原因：

1. **实现复杂度**：需要在 Java 层模拟 finally 语义（try-with-resources 或手动 try-finally）
2. **替代方案**：可以用 `try/catch` + 显式清理代码达到类似效果
3. **教学取舍**：finally 的边缘情况多（catch 内 throw、finally 内 return），容易分散注意力

作为扩展练习，可以尝试在 `Stmt.TryCatch` 中添加 `finallyBlock` 字段，并在解释器中实现。

## 7. 小结

| 要点 | 说明 |
|------|------|
| throw | 借助 Java 异常机制实现零成本传播 |
| try/catch | Java 层 catch (JimError e) 拦截 |
| 错误载荷 | 任意 Value（字符串/数字/实例）|
| catch 环境 | 新环境绑定错误变量，不污染外层 |
| 性能 | 禁用 Java 栈跟踪提升性能 |

## 常见问题 Q&A

**Q1: 为什么 throw 用 Java 异常实现？**

A: 异常的栈展开机制正好满足 throw 的需求——跨越多层调用直接跳到 catch。自己实现栈展开会很复杂。

**Q2: 为什么错误载荷是 Value 而不是专门的 Error 类？**

A: 简单灵活。`throw "error"` 和 `throw 404` 都合法，降低用户心智负担。实际项目中可以 throw 实例对象模拟 Error 类。

**Q3: 为什么没有 finally？**

A: finally 增加实现复杂度（需要处理 try/catch/finally 三条路径）。作为教学语言，try/catch 已足够演示核心机制。
