# Ch25: 垃圾回收 — 标记清除

## 学习目标
- 理解为什么动态语言需要垃圾回收
- 掌握标记-清除（Mark-Sweep）算法的两个阶段
- 了解 GC 触发时机、根对象的概念和自适应阈值策略
- 理解标记-清除的优缺点以及常见的优化方向

## 核心概念

JimLang 在运行时会动态创建字符串、列表、函数对象等堆对象。如果不回收不再使用的对象，内存会持续增长直到耗尽。垃圾回收（GC）的任务就是自动识别并释放这些"死亡"对象。

### 为什么需要 GC

```
JimLang 运行时内存模型：

┌─────────────┐     ┌──────────────────────────┐
│  Stack       │     │  Heap                     │
│  (局部变量)   │────→│  ObjString "hello"        │
│              │────→│  ObjList [1, 2, 3]        │
│              │     │  ObjString "dead" ← 无引用 │
│  Globals     │────→│  ObjFunction main()       │
│  (全局变量)   │     │  ObjString "orphan" ← 无引用│
└─────────────┘     └──────────────────────────┘

问题："dead" 和 "orphan" 没有任何引用指向它们
  → 占用内存但永远不会被使用
  → 必须自动回收，否则内存泄漏

Java/C++ 的做法：
  Java: 自动 GC（程序员不需要手动 free）
  C/C++: 手动 malloc/free（忘记 free 就泄漏）

JimLang 选择：自动 GC（标记-清除算法）
```

### 标记-清除算法

#### Mark-Sweep GC 过程图

```text
Stage 1: Mark

Roots:
  stack / globals / callframes
      │
      ├── ObjA ──> ObjB
      │
      └── ObjC

Heap:
  ObjA  ObjB  ObjC  ObjDead1  ObjDead2

标记后:
  ObjA = black
  ObjB = black
  ObjC = black
  ObjDead1 = white
  ObjDead2 = white

Stage 2: Sweep

遍历整个堆:
  black -> 保留并清除标记位
  white -> 释放内存
```

**标记-清除算法**分两个阶段：

**标记阶段（Mark）**：从所有**根对象**出发，沿引用链递归标记所有可达对象。根对象包括：
- 操作数栈中的所有值
- 全局变量表中的所有值
- 当前所有 CallFrame 中引用的函数对象

**清除阶段（Sweep）**：遍历堆上所有已分配对象，回收未被标记的对象，同时清除存活对象的标记位，为下次 GC 做准备。

```
标记阶段（从根出发，沿引用链遍历）：

Root: globals = { a → [1,2,3], name → "hello" }
      stack   = [ "world" ]

       a ──→ ObjList [1,2,3]    ✅ 标记
                  │
                  ├─ 1 (int, 非对象)
                  ├─ 2 (int, 非对象)
                  └─ 3 (int, 非对象)

     name ─→ ObjString "hello"  ✅ 标记

     stack[0] → ObjString "world" ✅ 标记

     堆上其他对象：
       ObjString "dead"         ❌ 未标记（无引用）
       ObjString "orphan"       ❌ 未标记（无引用）

清除阶段（遍历堆链表）：

  遍历所有对象：
    "hello" ✅ → 清除标记位，保留
    [1,2,3] ✅ → 清除标记位，保留
    "world" ✅ → 清除标记位，保留
    "dead"  ❌ → 回收！释放内存
    "orphan"❌ → 回收！释放内存

GC 后堆状态：
  heap → ObjString("hello") → ObjList([1,2,3]) → ObjString("world") → null
```

### 触发时机与自适应阈值

```
触发机制：

每次分配新对象时检查：
  bytesAllocated > gcThreshold ?
    是 → 触发 GC → 标记 → 清除 → 更新阈值
    否 → 直接返回新对象

自适应阈值策略：
  GC 后：gcThreshold = max(bytesAllocated * 2, 1MB)
  
  为什么是两倍？
    → 太小（如 1.1x）：GC 太频繁，影响性能
    → 太大（如 10x）：GC 不频繁，但内存占用高
    → 2x 是经验和实践的平衡点

示例：
  GC 前已分配: 1.1MB（触发 GC）
  GC 后存活: 0.4MB
  新阈值: max(0.4MB * 2, 1MB) = 1MB
  下次 GC 在分配量达到 1MB + 0.4MB = 1.4MB 时触发
```

## 为什么这里选择标记-清除，而不是引用计数

学生第一次学 GC 时，最自然的替代想法通常是：每个对象记录“有多少引用指向我”，计数变成 0 就释放，不就行了吗？

引用计数直观，但它有一个致命问题：处理不了循环引用。

例如：

1. 对象 A 引用 B
2. 对象 B 引用 A
3. 外部已经没有任何变量再指向它们

这时 A 和 B 的引用计数都不是 0，但它们实际上已经永远不可达了。标记-清除之所以经典，就在于它问的不是“有多少引用”，而是“从根出发还能不能走到你”。

这也是 GC 设计里非常关键的认知切换：**垃圾不是没人引用的对象，而是从程序活跃根集合出发不可达的对象。**

## GC 这一章真正要建立的思维模型

这门课讲 GC，不是为了让学生记住“Mark 然后 Sweep”四个英文单词，而是要建立完整的可达性视角：

1. 程序运行时有一组根对象
2. 根对象通过引用图连接到一部分堆对象
3. 这张图之外的对象，就是这次 GC 能回收的对象

只要这个模型真正建立起来，三色标记、分代回收、增量 GC 这些后续主题都会顺理成章；如果这个模型没立住，后面的优化术语都会像孤立知识点。

## 关键代码

```java
public abstract class Obj {
    public boolean marked = false;  // GC 标记位
    public Obj next;                // 堆对象链表（串联所有已分配对象）

    public abstract ObjType type();
    public abstract void markChildren(GC gc);  // 递归标记子对象
    public abstract int objectSize();           // 对象占用字节数
}

public class GC {
    private final VM vm;
    private Obj heapHead;          // 堆链表头
    private long bytesAllocated = 0;
    private long gcThreshold = 1024 * 1024; // 初始阈值 1MB
    private int gcCount = 0;

    // 分配新对象
    public Obj allocate(Obj obj) {
        bytesAllocated += obj.objectSize();
        obj.next = heapHead;       // 插入链表头部（O(1)）
        heapHead = obj;

        if (bytesAllocated > gcThreshold) {
            collectGarbage();
        }
        return obj;
    }

    private void collectGarbage() {
        long before = bytesAllocated;

        // ── 标记阶段 ──
        markRoots();

        // ── 清除阶段 ──
        Obj prev = null;
        Obj current = heapHead;
        while (current != null) {
            if (current.marked) {
                current.marked = false; // 清除标记，准备下次 GC
                prev = current;
                current = current.next;
            } else {
                // 未标记 = 不可达 = 回收
                Obj unreached = current;
                current = current.next;
                if (prev != null) prev.next = current;
                else heapHead = current;
                bytesAllocated -= unreached.objectSize();
            }
        }

        // 更新阈值
        gcThreshold = Math.max(bytesAllocated * 2, 1024 * 1024);
        gcCount++;

        System.out.printf("[GC] #%d: %dKB → %dKB (释放 %dKB)%n",
            gcCount, before / 1024, bytesAllocated / 1024,
            (before - bytesAllocated) / 1024);
    }

    private void markRoots() {
        // 根 1: 操作数栈
        for (Object val : vm.getStack()) {
            if (val instanceof Obj obj) markObject(obj);
        }
        // 根 2: 全局变量
        for (Object val : vm.getGlobals().values()) {
            if (val instanceof Obj obj) markObject(obj);
        }
        // 根 3: CallFrame 中的闭包
        for (CallFrame frame : vm.getFrames()) {
            if (frame.closure instanceof Obj obj) markObject(obj);
        }
    }

    private void markObject(Obj obj) {
        if (obj == null || obj.marked) return;  // 避免循环
        obj.marked = true;
        obj.markChildren(this);  // 递归标记子对象
    }
}
```

### ObjList 的 markChildren 实现

```java
public class ObjList extends Obj {
    public final List<Object> elements;

    @Override
    public void markChildren(GC gc) {
        for (Object elem : elements) {
            if (elem instanceof Obj obj) {
                gc.markObject(obj);  // 递归标记列表中的对象元素
            }
        }
    }

    @Override
    public int objectSize() {
        return 16 + elements.size() * 8; // 对象头 + 元素引用
    }
}
```

### ObjClosure 的 markChildren 实现

```java
public class ObjClosure extends Obj {
    public final ObjFunction function;
    public final ObjUpvalue[] upvalues;

    @Override
    public void markChildren(GC gc) {
        gc.markObject(function);       // 标记函数对象
        for (ObjUpvalue uv : upvalues) {
            gc.markObject(uv);         // 标记捕获的上值
        }
    }
}
```

## 算法分析

### 时间复杂度

```
标记阶段: O(存活对象数)
  → 遍历所有根对象，递归标记可达对象

清除阶段: O(总对象数)
  → 遍历堆链表上所有对象（包括已死亡的）

总计: O(总对象数)

优化空间：如果存活对象少、死亡对象多，
可以用"标记-复制"代替"标记-清除"，只复制存活对象。
```

### 标记-清除的优缺点

| 维度 | 优点 | 缺点 |
|------|------|------|
| 实现 | 简单直接 | — |
| 内存 | 不需要额外空间 | 产生内存碎片 |
| 停顿 | — | STW（Stop-The-World），暂停所有执行 |
| 碎片 | — | 频繁分配释放后，内存不连续 |

### 常见 GC 算法对比

| 算法 | 优点 | 缺点 | 使用者 |
|------|------|------|--------|
| 标记-清除 | 简单 | 碎片 + STW | JimLang, Lua |
| 标记-复制 | 无碎片 | 需要双倍空间 | Java 新生代 |
| 标记-整理 | 无碎片 | 移动对象开销大 | Java 老年代 |
| 引用计数 | 无停顿 | 循环引用问题 | Python, PHP |
| 分代 GC | 高效 | 实现复杂 | JVM, V8 |

## 常见问题 Q&A

**Q1: 为什么不使用引用计数？**

A: 引用计数有一个致命问题——无法处理循环引用：
```
var a = [];
var b = [a];
a.append(b);  // 循环引用：a → b → a
// 引用计数：a 和 b 的计数都不为 0，但它们已经不可达了
// 标记-清除：从根出发无法到达 a 和 b，会被正确回收
```

**Q2: GC 期间程序能继续运行吗？**

A: 标记-清除是 STW（Stop-The-World）的——GC 运行时程序暂停。对于 JimLang 这种教学语言可以接受。生产级 GC（如 JVM）使用增量标记和并发清除来减少停顿。

**Q3: 什么时候 GC 不够用？**

A: 如果程序持续分配大量长生命周期对象（如缓存），标记-清除可能导致频繁 GC 但回收很少。这时需要分代 GC（将堆分为新生代和老年代）来优化。

## 小结

| 要点 | 说明 |
|------|------|
| 核心思路 | 可达即存活：从根出发能访问到的保留，访问不到的回收 |
| 标记阶段 | 从根遍历引用链，标记所有可达对象 |
| 清除阶段 | 遍历堆链表，回收未标记对象 |
| 触发时机 | bytesAllocated > gcThreshold 时触发 |
| 自适应阈值 | gcThreshold = max(存活 * 2, 1MB) |

## 三色标记算法

### 为什么需要三色标记

基础的标记-清除有一个问题：**标记阶段的递归深度可能很深**（如链表 10000 个节点），导致栈溢出。三色标记将递归改为迭代，并且可以与用户程序并发运行（增量 GC）。

### 三色抽象

将堆上的对象分为三种颜色：

```
白色（White）：尚未被标记的对象（GC 结束后白色对象被回收）
灰色（Gray）：已被标记，但子对象尚未全部处理（待处理队列）
黑色（Black）：已被标记，且子对象也已全部标记（完成处理）

初始状态：所有对象都是白色

标记过程：
  1. 将所有根对象标记为灰色
  2. 从灰色队列取一个对象
  3. 将其所有子对象标记为灰色
  4. 将该对象标记为黑色
  5. 重复 2-4 直到灰色队列为空
  6. 剩余白色对象即为死亡对象

标记过程图示：

Step 0（初始）:
  Root → [A] → [B] → [C]
              ↓
             [D]

  所有对象：A(白), B(白), C(白), D(白)
  灰色队列：空

Step 1（标记根）:
  Root → [A] → [B] → [C]
              ↓
             [D]

  A(灰), B(白), C(白), D(白)
  灰色队列：[A]

Step 2（处理 A）:
  Root → [A] → [B] → [C]
              ↓
             [D]

  A(黑), B(灰), D(灰), C(白)
  灰色队列：[B, D]

Step 3（处理 B）:
  Root → [A] → [B] → [C]
              ↓
             [D]

  A(黑), B(黑), D(灰), C(灰)
  灰色队列：[D, C]

Step 4（处理 D 和 C）:
  Root → [A] → [B] → [C]
              ↓
             [D]

  A(黑), B(黑), D(黑), C(黑)
  灰色队列：空 → 标记完成

最终：没有白色对象，全部存活 ✅
```

### Java 实现：三色标记

```java
/**
 * 三色标记 GC
 * 用 GrayWorkList（灰色工作队列）替代递归标记
 */
public class TriColorGC {
    private final VM vm;
    private Obj heapHead;
    private long bytesAllocated = 0;
    private long gcThreshold = 1024 * 1024;
    private int gcCount = 0;

    // 三种颜色状态
    private enum Color { WHITE, GRAY, BLACK }

    // 灰色工作队列（可以用 ArrayDeque 或栈）
    private final ArrayDeque<Obj> grayWorkList = new ArrayDeque<>();

    public void collectGarbage() {
        long before = bytesAllocated;

        // ── 初始化：所有对象设为白色 ──
        Obj current = heapHead;
        while (current != null) {
            current.color = Color.WHITE;
            current = current.next;
        }

        // ── 标记阶段：三色标记 ──

        // Step 1: 将所有根对象标记为灰色
        markGrayRoots();

        // Step 2: 处理灰色队列直到为空
        while (!grayWorkList.isEmpty()) {
            Obj obj = grayWorkList.pollFirst();  // 取出一个灰色对象
            // 将其所有子对象标记为灰色
            for (Obj child : obj.getChildren()) {
                if (child != null && child.color == Color.WHITE) {
                    child.color = Color.GRAY;
                    grayWorkList.addLast(child);
                }
            }
            // 将当前对象标记为黑色
            obj.color = Color.BLACK;
        }

        // ── 清除阶段：回收白色对象 ──
        Obj prev = null;
        current = heapHead;
        int freed = 0;
        while (current != null) {
            if (current.color == Color.WHITE) {
                // 白色 = 不可达 = 回收
                Obj unreached = current;
                current = current.next;
                if (prev != null) prev.next = current;
                else heapHead = current;
                bytesAllocated -= unreached.objectSize();
                freed++;
            } else {
                // 黑色 = 存活，保留（不用重置颜色，下次 GC 会重置）
                prev = current;
                current = current.next;
            }
        }

        // 更新阈值
        gcThreshold = Math.max(bytesAllocated * 2, 1024 * 1024);
        gcCount++;

        System.out.printf("[GC#%d] 三色标记: %dKB → %dKB (释放 %d 对象)%n",
            gcCount, before / 1024, bytesAllocated / 1024, freed);
    }

    /**
     * 将所有根对象标记为灰色并加入工作队列
     */
    private void markGrayRoots() {
        // 根 1: 操作数栈
        for (Object val : vm.getStack()) {
            if (val instanceof Obj obj && obj.color == Color.WHITE) {
                obj.color = Color.GRAY;
                grayWorkList.addLast(obj);
            }
        }
        // 根 2: 全局变量
        for (Object val : vm.getGlobals().values()) {
            if (val instanceof Obj obj && obj.color == Color.WHITE) {
                obj.color = Color.GRAY;
                grayWorkList.addLast(obj);
            }
        }
        // 根 3: CallFrame 中的闭包和上值
        for (CallFrame frame : vm.getFrames()) {
            markGray(frame.closure);
            if (frame.closure instanceof ObjClosure closure) {
                for (ObjUpvalue uv : closure.upvalues) {
                    markGray(uv);
                }
            }
        }
    }

    private void markGray(Obj obj) {
        if (obj != null && obj.color == Color.WHITE) {
            obj.color = Color.GRAY;
            grayWorkList.addLast(obj);
        }
    }
}
```

### 递归标记 vs 三色标记对比

```
递归标记（本章主文）:
  优点：代码简单（递归天然遍历树）
  缺点：栈深度 = 引用链深度，链表 10000 节点会 StackOverflow
  无法并发：递归过程无法中断

三色标记（本节扩展）:
  优点：迭代实现，无栈溢出风险；灰色队列大小 = 引用宽度（通常很小）
  优点：可以增量执行（每次处理几个灰色对象，然后恢复用户程序）
  缺点：实现稍复杂（需要维护颜色状态和工作队列）

灰色队列最大大小分析：
  二叉树场景：最大灰色数 = 树宽 = O(log N)
  链表场景：最大灰色数 = 1（每次只处理一个）
  → 内存开销很小
```

### 增量 GC（选读）

三色标记天然支持增量执行——每次只处理几个灰色对象：

```java
/**
 * 增量 GC：每帧处理 N 个灰色对象
 * 与用户程序交替执行，减少停顿
 */
public class IncrementalGC {
    private static final int WORK_PER_STEP = 10;  // 每步处理 10 个对象

    public void step() {
        for (int i = 0; i < WORK_PER_STEP && !grayWorkList.isEmpty(); i++) {
            Obj obj = grayWorkList.pollFirst();
            for (Obj child : obj.getChildren()) {
                if (child != null && child.color == Color.WHITE) {
                    child.color = Color.GRAY;
                    grayWorkList.addLast(child);
                }
            }
            obj.color = Color.BLACK;
        }

        if (grayWorkList.isEmpty()) {
            sweep();  // 标记完成，进入清除阶段
        }
    }
}
```

## GC 调优实战

### 不同阈值策略的对比

```
测试场景：循环创建 10000 个临时字符串

阈值 1.5x:
  GC 触发 15 次，总停顿 45ms
  峰值内存 2.1MB

阈值 2.0x（默认）:
  GC 触发 11 次，总停顿 35ms
  峰值内存 2.8MB

阈值 3.0x:
  GC 触发 7 次，总停顿 25ms
  峰值内存 4.2MB

阈值 5.0x:
  GC 触发 4 次，总停顿 20ms
  峰值内存 7.0MB

结论：阈值越大 GC 次数越少，但内存峰值越高
  推荐：桌面应用 2x，嵌入式设备 1.5x，服务器 3x
```
